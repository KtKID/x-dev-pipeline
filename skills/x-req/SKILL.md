# x-req

把 spec 的 feat 拆成若干 task，每个 task 一份开发 checklist。checklist 的任务行回指 spec 里的场景和 tech-design 的具体用例：做完一行，按回指场景的 GIVEN/WHEN/THEN 及用例判据验证；全部任务行通过后，核对分配的场景、承接用例和关键约束测试的完整覆盖。

## 产物

开发验证产物统一遵循 [共用报告约定](../x-dev/references/test-reporting.md)：任务记录链接一份当次代码改动测试报告，完整用例结果、改动覆盖率与未覆盖位置在该报告维护，原始证据集中放附件。拆解时只分配用例与责任范围。

在 `docs/spec/<spec-name>/tasks/<task-name>/dev-checklist.md` 生成——task 归属主场景所在的 spec（跨多份 spec 时放哪见 [spec 范围](../x-explore-for-spec/references/spec-scope.md)，其他 spec 的场景回指带 spec 名前缀），一个 task 一份 checklist，task 目录名用 `task-<功能名>`。本轮全部 task 的 checklist 合并后覆盖选中的场景、受影响的回归及适用关键约束的全部承接用例；该 spec 其他 feat 和场景保持原状态。每份 checklist 在任务表下方带一棵**影响文件树**：用简化树状图标出本 task 在仓库中要改动的全部文件，`U` 新增 / `M` 修改 / `D` 删除。

## 核心原则

1. **feat 是拆分主轴。** 一个 task 承接一个或一组紧密相关 feat 的本轮场景。同一 feat 可以分批交付，每批明确选中的场景及保留行为；共享约束注明责任范围。
2. **场景回指，不复述。** 任务行只写 `feat02 场景3` 这样的回指，GIVEN/WHEN/THEN 留在 spec 里做唯一事实源，checklist 不复制它们。声明 `spec_version: 3` 的旧契约包沿用原来的 Scenario ID 格式，由旧引擎处理。
3. **场景、用例、任务逐项对应。** 本轮全部 task 的任务行合并后覆盖明确选中的场景及受影响回归，并承接 tech-design 中这些场景及适用关键约束的全部用例。一个场景可有多条用例，共享用例分别对应各场景的判据；逐项核对完整覆盖与具体 task/行的责任。
4. **分好并行组和依赖。** 每行写并行组和依赖，规则见下面的「分组」。同组内按行序做，被依赖的行排前面。task 之间的先后（如公共数据 task 在前）在交付报告里说明。
5. **设计先行。** 涉及文件以 tech-design 的模块、协议与数据流为依据：每个文件都能在设计的影响范围里找到归属。设计缺项或与代码现状冲突时退回 x-tech-design，不擅自代设计。

## 就绪检查

拆解前核对以下项目，需求问题交 x-explore-for-spec，测试设计与流程缺项交 x-tech-design，补齐受影响来源后再拆解：

按用户当前目标核对本轮选中范围、验证证据和完成条件；用户目标已调整时先回 x-explore-for-spec 增量同步受影响条目。任务只承接本次必要工作，MVP 任务以取得约定验证证据为完成依据。spec 长期累积，3 个 feat / 10 个场景仅作为单轮审阅的建议容量，任务按可独立验收的范围分批。

1. spec.md 存在且结构完整：标题 + 概述 + feat 列表；本轮关键约束有明确用户确认依据，提议未混入已确认内容。旧 spec 无 C 章节时按现有已确认场景/约束、既有编号或章节定位核对，不为套模板强造 C 或改编号，也不由缺章节推断“无约束”。本轮新增约束或原有行为有歧义时回 x-explore-for-spec 澄清，未确认提议不能作为既定验收要求。
2. 新 spec 从 `feat01` 起接续编号，增量沿用已有编号，退役编号保留，序号唯一且允许空缺；本轮场景覆盖选中目标的正常流程及必要边界、失败路径，覆盖依据可定位。MVP 聚焦影响验证结论可信度的条件并保留已确认约束；场景按独立验收路径划分和计数，同一路径的多项共同结果计为一个场景，等价输入可合并，既有 spec 的依据可从需求及 GWT 核实。
3. 本轮选中的场景有明确结果；仍有实质取舍时交 x-explore-for-spec 确认后再拆解受影响范围，独立且已确认的范围可继续。该 spec 中的其他待决项保持原状态。
4. 同目录存在 `tech-design.md`：覆盖本轮选中的场景和适用约束，没有仍在等用户拍板的边界取舍。tech-design 本身不需要用户确认。缺失或有未决取舍时，补齐受影响设计；独立的范围可先拆解。
5. 以 spec 本轮拆解范围的全部场景为应覆盖集合，逐个找到 tech-design 的编号用例主定义，核对场景回指、为什么测、数据准备、执行流程及全部预期/适用禁止结果的观察点。一个场景的多条用例完整列出，共享用例分别核对各场景判据；人工/审查用例同样有步骤和判据。仅登记 feat、用例名称或场景 ID 而缺上述定义时列为缺项，报告具体场景及缺失内容，交 x-tech-design 补齐后再拆解。
6. 本轮适用的 C 编号均能在 tech-design 中追到 D 机制和完整编号用例；缺覆盖、范围冲突或待确认项先交来源负责方补齐，不带入开发。
7. 需求变化后再拆解时，按 [需求变化同步](../x-tech-design/references/change-sync.md) 处理：只重开或新增受影响的任务行，其他行保持原状态。

## 拆解规则

1. 先分组：把 feat 按"能独立交付的一组"划分成 task，公共数据/契约单独成 task 排在最前。
2. task 内每个 feat 按"能独立执行并验证"拆成若干任务行，常见顺序：公共数据/契约 → 核心功能 → 边界与异常 → 集成验证。
3. 场景回指列写 `feat01 场景2` 格式；同一行引用多个场景用逗号分隔（`feat02 场景1, 场景4`）。纯技术支撑行（脚手架、配置、目录初始化）写 `None`，此类行保持最少。承接场景或约束测试的行，在「任务」列引用全部对应的用例编号及拟验证层级（如 `（用例 T1、T2；集成）`），适用时附 C/D 编号（如 `（C1；D01；用例 T1、T2；集成）`）；场景回指列仍只放场景。测试理由、数据、流程和判据统一回指 tech-design 主定义。共享用例明确负责执行的 task/行及其他相关行的引用关系。
4. 涉及文件以 tech-design 的模块与数据流为依据、代码调查核实，写到具体路径；设计未覆盖的文件先退回 x-tech-design 补设计，不绕过。确实定不下来的写最小目录或 glob，并在任务说明里写清定位动作。
5. 风险列：按 [x-qdev 风险规则](../x-qdev/references/risk-rules.md) 第 2–5 条的口径判断，这一行要新增或修改权限规则、迁移或批量改写已有数据、新写防并发或防重复的处理、或影响做了就收不回的操作，就标 `高:<一句依据>`，其余写 `None`。只是普通的读写数据库不算高风险。高风险行的验证不允许只有 unit 测试。头部 `risk:` 按任务行算出，不凭感觉填：先数高风险行：2 个及以上 Q3，1 个 Q2；没有高风险行时，有场景回指 Q1，没有任何场景回指 Q0。x-qa-gate 按它决定审查强度。
6. 能直接转成测试的场景，验证就写成一行测试任务（标注 unit/smoke/e2e）；场景的 THEN 与已确认约束的预期/禁止结果共同构成判定标准。自动化行为的任务说明先写测试并确认预期原因失败，再实现；独立集成验证行保留在实现后，不在该行伪造红灯。不可自动化或既有实现已满足时注明取证方式，不要求造失败。
7. **影响文件树。** 汇总本 task 的涉及文件，在任务表下方画一棵以仓库根为起点的简化树：文件路径后标 `U`/`M`/`D`，`#` 后写一句改动说明；同一目录、同一标记、说明相同的文件可合并成一行（`/` 分隔）；定不下来的 glob 写目录级节点并注明定位动作。树与「涉及文件」列一一对应，不引入表外文件。

## 分组：派给几个工人

一个并行组交给一个工人（子 agent），在自己的分支上按行序做完。

**硬规则（`xdev validate` 会核对，不满足就报错）**

- 涉及文件有交集的行必须同组。两个工人同时改同一个文件，合并时要么冲突，要么后合的盖掉前一个。
- 要用到别的行做出来的东西（接口、数据结构、公共函数）时，在依赖列写那一行的编号，多个用逗号分隔（`T1, T3`），没有写 `None`。同组内被依赖的行排在前面；组之间的依赖不能成环。

**软规则（你来定，不为并行而拆）**

文件不重叠的行**可以**分给不同工人，也可以合在一组。每多一组，就多一次派单、一次验收、一次合并；拆开省下的时间要大于这些开销才拆。

- 本 task 合计只是几处小改动（源码文件合计不超过 3 个，或一个工人很快能做完）→ 一组。
- 每组都要有一块能独立验收的完整功能（至少一个场景的实现和它的测试），不把同一个场景的实现和测试拆到两组。
- 组数不超过可用的工人数；用户没说时最多 3 组。
- 在 checklist 头部 `> 分组理由：` 写一句：几组、为什么。

`xdev graph` 会列出"按文件交集必须合并的最小分组"和派工顺序，在它的基础上决定要不要再合并。

## 工作流

1. 读完 spec.md 全文，完成就绪检查。
2. 读取同目录 `tech-design.md`，按设计的模块、协议与数据流确定每个 feat 落在哪些文件，再用代码调查核实现状、确认与现有功能的共享点；设计与代码现状冲突时退回 x-tech-design。
3. 分组 feat 成 task，用 `python3 <x-dev-skill-dir>/scripts/xdev.py scaffold docs/spec/<spec>/tasks/<task>/` 建目录和 checklist（`<x-dev-skill-dir>` 是同一插件里 x-dev skill 的目录；头部的 spec、tech-design、创建日期和拆解基线由脚本自动填好，不手填），完整读取 checklist 后逐个填充：task 内按实现顺序填表，按「分组」写并行组、依赖和分组理由，按任务行算出 risk，再按规则 7 生成影响文件树，删除占位符和空示例。
4. 运行 `xdev.py validate <task-dir>` 和 `xdev.py graph <task-dir>`，脚本报的问题全部修完；再做下面的人工自检。
5. 报告 task 列表（明确每个 task 选中的 feat/场景）、本轮每个场景 → 全部承接用例 → task/行及适用 C→用例→task/行的分配覆盖（只引用 ID/主定义链接）、各 checklist 行数、高风险行、派工计划（`xdev graph` 的批次、组数和分组理由）、task 间先后建议，及下一步（交给 x-dev）。checklist 头部记录本轮承接范围和来源；拆解基线由脚本写入，需求后来变了，`xdev impact` 能据此找出要同步的地方。

## 自检

`xdev validate` 已经机械核对：头部字段齐全、任务表列齐全、场景 / C / D / 用例编号真实存在、涉及文件存在或在影响文件树标了 U、涉及文件有交集的行同组、依赖存在且无环、risk 与任务行一致、拆解基线覆盖每份涉及的文档。下面只列脚本判断不了的：

- 从 spec 本轮范围逐个列出的每个场景，都有 tech-design 用例承接并分配到具体 task/行？
- 场景用例的理由、数据准备、执行流程及全部预期/适用禁止结果的观察点可定位？共享用例逐场景核对判据，各场景的全部用例均已承接？
- 适用的每条 C 及其全部用例都已分配到具体 task/行，行内用例编号在 tech-design 可定位且层级一致？
- 每个 task 承接的 feat/场景明确，分批交付责任和共享约束可核对？
- 有没有任务行超出 spec 概述声明的范围（"顺便"改了别的）？
- 影响文件树与「涉及文件」列一一对应（无树外文件、表内文件无遗漏），标记只用 U/M/D？
- 涉及文件都能在 tech-design 的模块/影响范围里找到归属？
- 高风险行都标了依据，且验证不只 unit？
- 分组按软规则决定，分组理由写清了？同组内行序即实现顺序？
- checklist 里没有复制 spec 的 GIVEN/WHEN/THEN 或概述正文？

## 完整示例（节选）

输入是 reading-club 的小组管理 spec，2 个 feat、共 8 个场景由 1 个 task 承接。示例假设 tech-design 已定义：用例 T1–T3 分别承接 feat01 场景1–3，用例 T4–T8 分别承接 feat02 场景1–5，用例 T9 共享验证两者的场景1；测试理由、流程和各场景观察点在主定义维护。其中 `tasks/task-group-management/` 覆盖 feat01、feat02，它的 checklist 长这样：

> 状态：待实现
> 执行者：未知
> tech-design: docs/spec/reading-club/tech-design.md
> 本轮范围：feat01 场景1-3、feat02 场景1-5
> 范围依据：用户 2026-08-15 确认的 spec 增量
> 拆解基线：docs/spec/reading-club/spec.md@3f2a1c0d9e21 · docs/spec/reading-club/tech-design.md@8b41d77a0c3f
> risk: Q1
> 分组理由：1 组：只改 3 个源码文件，T1、T2 都改 src/groups.py
> 创建: 2026-08-15

**状态**：`[ ] ⏳` 未开始 / `[ ] ▶️` 进行中 / `[ ] 🟡` 待验证 / `[x] 🟢` 验证通过 / `[!] 🔴` 验证失败 / `[x] ✅` 已完成 / `[ ] ↗️` 已升级

| # | 任务 | 场景回指 | 涉及文件 | 风险 | 并行组 | 依赖 | 状态 |
|---|---|---|---|---|---|---|---|
| T1 | 先测试后实现小组创建：名字、所选书必填校验，生成邀请码（用例 T1–T3；unit） | feat01 场景1-3 | src/groups.py, tests/test_groups.py | None | A | None | [ ] ⏳ |
