# x-bug2rag 判断细则

> 本文件是 `SKILL.md` 第 2 轮"判断"的对照参考。每类给出"记"和"弃"的边界例子，帮助对齐"失败机制泛用性"的尺度。

## 判断核心：失败机制 ≠ bug

判断的是**机制的泛用性**，不是 bug 的严重程度。同一条 bug 可能：

- 暴露一个泛用机制（记）。
- 只是某个业务规则没写对（弃，归 spec）。
- 只是某次运维事故（弃，归 ops）。
- 同时暴露多个机制（拆成多条记）。

判断时把项目名、库名、业务名词换掉，经验依然成立 → 记；换掉就说不通 → 弃。

## 进/弃边界对照

### 1. 状态机

| 判定 | 例子 |
|---|---|
| 记 | 订单从"已完成"恢复时被接受为"进行中"，违反状态转换规则。机制：恢复只校验数据形状不校验转换合法性。 |
| 记 | 工作流跳过审批节点直接到结束态，绕过必经状态。机制：状态跳跃未拦截。 |
| 弃 | 订单状态字段叫 `STATUS_DONE` 而不是 `COMPLETED`。这是命名/领域事实，不是机制。 |

### 2. 并发/时序

| 判定 | 例子 |
|---|---|
| 记 | 客户端重试与首个请求并发，产生两笔副作用。机制：失败重试与首次交错。 |
| 记 | 消息乱序到达导致状态机跳变。机制：无序处理破坏时序不变量。 |
| 弃 | 某次因为 Kafka 分区数配错导致乱序。这是配置事故，机制被掩盖，且换环境不成立。 |

### 3. 幂等/唯一

| 判定 | 例子 |
|---|---|
| 记 | 无幂等键，重试直接执行副作用产生重复扣款。机制：缺少幂等去重。 |
| 记 | 唯一约束在应用层校验后并发插入仍冲突。机制：检查-then-insert 的 TOCTOU。 |
| 弃 | 业务要求每个用户每天只能领一次券。这是业务规则，归 spec，不是机制。 |

### 4. 边界/默认值

| 判定 | 例子 |
|---|---|
| 记 | 空集合时 `list[1]` 抛异常，绕过"取第二个或默认值"契约。机制：边界输入绕过默认值。 |
| 记 | 分页 `page=0` 被当成第一页，但内部从 0 还是从 1 开始未对齐。机制：off-by-one 边界。 |
| 弃 | 某接口返回的 `pageSize` 最大 100。这是限额，归 spec/API 文档。 |

### 5. 权限/越权

| 判定 | 例子 |
|---|---|
| 记 | 用户切换身份后旧权限缓存残留，新身份获得旧权限范围。机制：身份切换后权限状态未失效。 |
| 记 | 通过改 URL 中的 `userId` 访问他人数据。机制：横向越权未校验资源归属。 |
| 弃 | 某角色叫 `admin` 而不是 `owner`。这是命名/领域事实。 |

### 6. 资源生命周期

| 判定 | 例子 |
|---|---|
| 记 | 超时分支提前返回，未关闭数据库连接，长期运行耗尽连接池。机制：超时分支漏清理。 |
| 记 | 异常路径未释放锁，后续请求永久阻塞。机制：异常路径资源泄漏。 |
| 弃 | 某次因为连接池大小配成 10 导致打满。这是容量规划问题，机制被掩盖。 |

### 7. 持久化一致性

| 判定 | 例子 |
|---|---|
| 记 | 写主表后写索引前崩溃，恢复后索引与正文不一致。机制：多阶段提交无原子保证。 |
| 记 | WAL 与数据文件写顺序未保证，崩溃恢复后状态偏移。机制：崩溃恢复窗口。 |
| 弃 | 某次因为磁盘满导致写失败。这是运维事故，不是机制。 |

### 8. 数据敏感

| 判定 | 例子 |
|---|---|
| 记 | 错误信息把 SQL 原文（含参数）回显给客户端。机制：错误信息泄漏敏感数据。 |
| 记 | access token 被写进日志。机制：secret 进入日志通道。 |
| 弃 | 某接口返回的手机号没脱敏。这是产品需求，归 spec；机制层面脱敏怎么做不是经验。 |

## 抛弃信号的快速复核

判定为"弃"时，逐项核对是否命中以下信号之一，并在回执里写明：

| 信号 | 典型表现 |
|---|---|
| 纯领域事实 | 业务规则、API 限额、产品约束、命名约定 |
| 一次性运维/环境 bug | 磁盘满、机器挂、配置手抖、网络分区一次性事件 |
| 编程常识 | 判 null、基本边界检查、类型转换、循环条件 |
| 时效性强/易腐烂 | 某库某版本 bug、某平台特定行为、临时 workaround |
| 补不齐必填字段 | 场景/错误实现/正确实现/可观察差异任一说不清 |

补不齐字段时优先**回问用户**补全，而不是直接抛弃——很多 bug 描述一开始只有现象，机制需要追问才能挖出来。

## 字段填写要点

- **关键词**：召回语义锚点。写功能名词 + 状态 + 动作，3-6 个，逗号分隔。避免项目专属词。
- **Risk**：一句具体失败机制，结构是"条件 + 后果"。禁止"要小心""可能有 bug"这类空话。
- **场景**：触发条件、上下文、前置状态。读者要能据此构造输入。
- **错误实现**：常见错误做法，写"怎么错的"，不写"为什么错"。
- **正确实现**：对的实现长什么样，写法对照错误实现。
- **可观察差异**：错实现 vs 对实现的可观察区分点——这是召回后构造反例的关键。
- **分类**：上述 8 类之一。
- **来源**：项目/报告/issue 编号，可选，用于溯源。

可观察差异是最容易写糊的字段。好的写法是"输入 X 时，错实现产生 A，对实现产生 B"；差的写法是"行为不同"——后者召回后 LLM 还是不知道怎么构造反例。
