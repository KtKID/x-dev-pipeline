# qdev 单文档对账

用于明确指定的 `task-<name>.md`。先读取完整文档、用户要求/确认记录及被回指的 spec/模块功能文档、变更索引、设计、用例和执行记录。常规 task 继续按 SKILL.md 的 checklist/report 契约检查。

## 来源映射

| 对账来源 | qdev 对应位置 |
|---|---|
| 功能预期与关键约束 | ①回指的 spec 或模块功能正文/移除要求及用户来源；旧独立任务沿用①的既有主定义与基线 |
| 承接范围 | 用户明确范围、①记录的分配依据及其可读基线 |
| 设计与用例主定义 | 外部 tech-design 的路径/ID，或本任务②局部设计、③局部用例 |
| 计划与实际文件 | ②计划涉及文件、④实际涉及文件及本次执行的改动范围记录 |
| 功能变化与索引 | ①的新增/修改/删除回指，功能文档中的正文、移除记录及 changelog，⑤的同步状态 |
| 执行证据与结论 | ⑤指向的统一测试报告：用例明细、改动覆盖率、未覆盖位置、实际基线、附件与回执；⑤保留交付摘要与未决索引 |

按⑤链接读取唯一测试报告，依 [共用报告约定](../../x-dev/references/test-reporting.md) 核对专项、回归、人工与技术检查的完整用例明细及附件。核对当次 diff 范围、交付版本、改动行/相关分支覆盖率、未覆盖位置和未采集项，回执说明实际复查来源。旧任务继续读取原⑤和已有执行记录。

预期、测试集合和实际结果各有不同来源。应覆盖集合来自已确认①/外部需求与分配依据，计划集合来自③，实际集合来自⑤指向的测试报告，分别建立后对照。作者全绿声明、公共回执及创建日期须有相应的预期、基线与执行证据支持。

qdev 中用户明确的原始任务要求及已有结论提供本次需求依据和执行授权。核对用户来源、承接范围、功能回写和实现前基线；局部方案按任务授权、已有设计及规范核对，普通方案和文档同步由 agent 记录并执行。分阶段审批用于完整主线；qdev 中需要额外决定的事项限于实质性歧义和超出授权的关键变化，具体来源与实际结论须可查。

功能主定义按“功能文档”指针定位：spec 采用原 feat/场景/C，模块说明采用稳定章节及可观察要求。新功能或变化追到该正文的更新、确认及前后基线，changelog 用作变化索引。删除项同时核对旧版本定义、当前移除记录和保留行为。局部 D/用例及旧独立任务的 feat/场景/C 以文件路径限定，同号外部条目引用时带来源。已有编号/章节定位继续沿用。

## 九项对应检查

1. **结构与唯一定位**：①需求与变更、②精简技术设计、③测试用例与变化、④技术实现、⑤验证结果及其测试报告入口可定位，功能文档/范围/设计/报告指针对应同一任务与交付基线。模块文档模式接受“无 spec”及功能章节指针。旧五段/四段记录按原章节和既有指针映射，继续核查已有事实；缺本轮需要的设计/用例主定义或资料时标未核实，不能靠重排标题取得通过。新建 task 的头部四行（所属 spec、状态、执行者、创建）齐全，「所属 spec」链接可打开，且 task 文件位于该 spec 的 `tasks/` 下；历史 `docs/task/` 下的旧 task 按原位置核对。
2. **内容基线**：比较确认时、测试/实现时及当前的功能、约束、设计/用例预期与编号。读取已有版本或内容快照；内容哈希需能定位相应可读内容。变化须有权威来源及重新对齐记录；来源、旧内容或基线缺失标未核实。
3. **场景与变更回指**：spec 按各自主定义逐项展开 feat/场景引用及区间，采用 SKILL.md 的完整解析规则；模块文档按路径/章节核对触发条件、可观察结果和边界。新增项追到新定义，修改项比较前后定义，删除项追到旧版本及当前移除要求；退役编号按历史定位核对。局部和外部同号分别定位，悬空、歧义及未解析残余列出。
4. **本 task 覆盖**：从①确认的承接范围及功能主定义建立应覆盖场景、模块行为、移除要求和 C/用例集合，比较③及⑤的实际覆盖。引用整个 feat 默认核对其有效场景及本次适用移除要求；部分改动依用户明确范围及理由，不扩成 spec 全包。一个 C 的全部适用用例均须承接，跨 task 共享项核对责任来源。③的用例新增/修改/删除/沿用分别核对，退役用例有需求依据，移除结果与保留行为有对应验证；覆盖数、变化数和框架执行数分别统计。缺范围依据标覆盖未核实。
5. **技术支撑与 D 回指**：局部用例或技术支撑的依据可定位，D 编号存在于明确的设计来源；仅核对引用，机制符合性由 x-verify-tech 验收。qdev 没有 checklist 行或 None 列时按实际形态处理，保留真实功能覆盖要求。
6. **每个结果的证据**：统一测试报告及集中附件映射到所有应覆盖场景、模块行为、移除要求、C 和有效用例的前提/触发及预期/禁止结果。核对实际取证理由、命令/工作目录/退出码/执行与跳过数、观察和来源，复查改动覆盖率的基线、分母、缺口及适用性。退役用例核对处置依据与替代验证。缺某结果证据、只构建、零测试或替换被验证机制均如实列明。
7. **人工与风险记录**：人工步骤、观察、结果和来源可核查，局部自动化用例按声明层级核对真实链路。发现鉴权、迁移、并发或不可逆等超出 qdev 范围的工作，单列范围问题与应交接方；核查已有证据，不降低其验证要求或宣称整体通过。
8. **改动范围与文档同步**：②计划文件与④实际文件、执行时的本任务差异记录对应；差异有设计/范围依据。新增/修改/删除已回写功能正文或移除记录，changelog 与 task 双向链接可定位，文档状态与实际交付一致。按用户授权范围核对，保留无关脏文件的边界；不强制补独立 checklist 或影响文件树。旧档案按当时已确认的文档同步要求及已有来源核对。
9. **状态与结论**：开发用例及回归结果真实、完整且与⑤结论一致；分别列失败、阻塞、未执行、缺证据、待确认和矛盾。统计场景与用例，省略虚构的 checklist 行数。记录公共验收回执的实际状态，当前 x-verify-spec 回执以及尚待取得的 x-verify-tech 回执分别列为核查进度，交付对账可先完成；开发证据缺失仍阻止通过，公共回执与当前输入基线矛盾仍报告。

## 结论

采用 SKILL.md 的“对账通过 / 对账未完成 / 对账不通过”及问题去向。来源可核查、适用检查一致、开发验证与回归真实闭合时对账通过；它证明交付记录闭合，技术验收单独记录。

只返回本轮回执与必要清单，由 qdev 主 agent 收录统一测试报告并在⑤同步状态。保持任务正文、测试、设计与状态原样，复查使用已有执行记录。
