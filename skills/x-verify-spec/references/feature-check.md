# 功能检查

一句话：**开发做完以后，另派一个子 agent 只查一次：任务文档和本轮设计文档写的都做完了没有，测试是不是真的在测。** 查过就不再查第二遍。范围只到本轮 spec 和 tech-design；全项目的约束（`engineering` spec）、开发规范 R1–R7、代码规范、死代码、性能不在这里查，交给定期巡检（`x-code-audit`）。

它回答两个问题：

> 1. 本轮场景、约束和设计都做到了吗？有没有漏做、有没有多做？
> 2. 生产代码要是被改错了，这些测试会不会变红？

x-dev、x-qdev 都用。多 agent 协作时，全部合并后对整个 task 做一次，工人不做。

## 什么时候做、什么时候不做

1. 开发阶段做完以后：全部行 `[x] 🟢`，`xdev coverage` 通过（全量测试全绿、改动行覆盖率 100%），Web 验收做完。然后做功能检查，再跑 `xdev check`。
2. **不做**：checklist 头部 `risk: Q0`；qdev 只记了变更、没写场景（①写着“未写场景，无需确认”）。`xdev check` 也不要求回执。
3. **重做**：之后代码或测试改过（修问题、补测试、需求变化同步后改了实现），就要先重跑 `xdev coverage`（开发者修完已经跑过就不用再跑），再重做功能检查。`xdev check` 发现回执比最后一次覆盖率记录旧，就报 FEATURE_CHECK_STALE。重做就是按同一份派工单整份再查一遍；另附上一份回执，只用来接着编号、确认上次的问题都没了。先派工，等新回执回来再覆盖旧回执。

## 派谁

用当前环境里便宜、快的模型（如 haiku），新开一个子 agent。它不带主 agent 的对话历史，只跑一个 turn，只读，不改文件。

## 派工单

主 agent 照下面的模板派工，只把尖括号里的内容换成实际路径和命令，不增删别的话。检查内容和回执格式写在本文件里，子 agent 自己读，不由主 agent 在派工时转述或补充。

```text
你做一次功能检查。照 <本文件的完整路径> 的「检查内容」和「回执格式」两节做，只读，不改文件，只跑一个 turn。

task：<task 名>
交付文档：<dev-checklist.md 或 qdev task.md 的路径>（看「本轮范围」、任务行的场景回指和涉及文件、「结果 / 用例对应」表）
场景和约束：<spec.md 路径> 的 <本轮 feat 和场景编号、本轮用到的 C 编号>
本轮设计和用例：<tech-design.md 路径> 的 <本轮 D 编号和用例编号>（qdev 写 task.md 的②③）
用户原话：<讨论记录或 qdev ①的位置；没有单独记录就写“以 spec 场景为准”>
（qdev 的对应位置：本轮范围看①，涉及文件看②④，用例对应看⑤）
代码改动：在 <仓库根目录> 运行 git diff <代码基线> 和 git status --short
要检查的测试文件：<照抄 xdev check 报 FEATURE_CHECK / FEATURE_CHECK_STALE 时列出的完整清单，清单是“无”就写“无”>
人工验证记录：<证据目录下的 manual-*.md 路径，没有就写“无”>
上一份回执：<重做时填它的路径，第一次写“无”>
```

要检查哪些测试文件以 `xdev check` 为准：没有回执、回执没列全或过期时，它都会列出完整清单，派工单照抄。算不算测试文件按路径判断：路径里有 `tests/`、`test/`、`__tests__/`、`spec/`、`fixtures/`、`testdata/`，或文件名形如 `test_*`、`*_test.*`、`*.test.*`、`*.spec.*`、`conftest.py`，并且是代码文件。

子 agent 的回执原样存为证据目录里的 `feature-check.md`，重做时覆盖旧的。只存这一份，不另建审查报告或回执副本。然后运行 `xdev check`。

## 检查内容

### 一、功能做对了没有

先读场景，再读约束：场景是要做的事，约束只限制怎么做。对照用户原话、本轮场景的 THEN、本轮用到的 C（包括用户定的“架构：”约束）、本轮 tech-design 的 D，以及交付文档写的改动范围，看代码改动。

| 问题类型 | 是什么 |
|---|---|
| 漏了要的 | 某个场景的 THEN、本轮 C 的要求或禁止结果、本轮 D 的设计，代码里没有做到；只满足了约束、场景没做完，也算 |
| 做了没要的 | 改了场景没提的行为、改了既有公开接口，或者改动超出了交付文档写的涉及文件 |

本轮没用到的约束和设计、`engineering` 的全项目约束、开发规范 R1–R7 不在这里查，交给定期巡检。

代码本身没做到场景要的结果，测试也没测到这一点时，报“漏了要的”一条就够，不再另报测试问题。

一个测试同时符合下表几类时，报更具体的那一类；“没测到场景要的结果”只在其他类都不符合时用。

### 二、测试是不是真的在测

对每个新增或改动的测试函数，先找出它调用了项目里的哪个函数、类、接口或命令，再按下表逐项看。

| 问题类型 | 是什么 | 典型样子 |
|---|---|---|
| 重写了生产逻辑 | 测试调用了项目代码，但期望值是照抄业务规则算出来的（哪怕用的是从生产代码 import 的常量），或者测试里另写了一份规则拿来对比 | `expected = days * 0.5` 或 `expected = days * DAILY_FINE` 照抄罚款公式；测试里自己写了一个 `calc_fine()` 再和生产结果比 |
| 没调用项目代码 | 测试根本没调用项目里的被测函数：测的是测试文件里自己定义的函数、复制进来的类，或一个和项目无关的替身（这种情况归这一类，不归“重写了生产逻辑”） | 把生产函数复制到测试文件里测；import 的是测试目录下的同名模块 |
| 绕过要测的流程 | 调了项目代码，但跳过了场景要验证的入口或步骤 | 场景是“借第 6 本被拒”，测试直接往数据库写 6 条借阅记录再查，没调借书入口；直接调内部私有函数，跳过了校验 |
| mock 掉了被测对象 | 被测函数本身被 mock 或打桩了 | `patch("loan.borrow.check_limit", return_value=False)` 之后测借书被拒 |
| 只断言调用不断言结果 | 只检查“被调用了”“没报错”“不是 None”，没检查场景要的结果 | `mock.assert_called_once()`；`assert result is not None`；整个测试没有断言 |
| 断言恒真 | 期望值来自被测代码自己，或者无论实现对错都成立 | `assert f(x) == f(x)`；期望值由同一次调用得出；断言 `len(xs) >= 0` |
| 吞掉失败 | 失败被藏起来了，测试永远绿 | `try: ... except: pass`；`skip` / `xfail`；`if result:` 包着断言；中途 `return` |
| 数据测不出对错 | 选的数据让错误的实现也能通过 | 上限是 5 本，测试只借 2 本；边界场景没测边界值；期望值恰好等于默认值 |
| 没测到场景要的结果 | 用例对应表里这个测试对应的场景 THEN 或 C 禁止结果，测试没有断言到（漏了某个预期结果，或测的不是场景说的那件事） | 场景要求“拒绝且到期日不变”，测试只断言了返回错误 |
| 人工记录不全 | 人工验证记录没有步骤，或没有写实际看到的结果 | 只写了“已验证，正常” |

**不算问题**（不要报）：

- mock 网络、时钟、随机数、第三方服务，或者被测函数下面的存储层、数据库访问，只要被测的那个函数本身真实运行，断言的是它的结果。
- 用测试工具函数或 fixture 准备输入数据。
- 期望值是手写的常量（如 `assert fine == 1.5`），这正是推荐写法。
- 同一个场景拆成几个小测试分别断言。
- 交付文档头部状态、行状态这类记账：由主 agent 和 `xdev check` 管。
- 覆盖率、测试是否通过、用例对应表里的文件和函数是否存在：`xdev coverage` 和 `xdev check` 已经核对过。

拿不准时，在心里做一次“改坏试验”：把生产代码里相关的判断删掉，或者把返回值改错，看这个测试还会不会通过。会通过，就是问题。

### 严重度

- **P0**：用户会拿到错误结果、丢数据、越权或用不了。要写出位置和能复现的依据，依据不全就降为 P1。
- **P1**：漏了要的、做了没要的，或第二部分表里的任何一类测试问题。
- **P2**：上面几类都不算的改进建议。只登记，不修。

属于上面任何一类的，至少是 P1。不能因为“现在的代码碰巧是对的”降成 P2：测试是用来防止以后有人把代码改错的，现在对不对不是降级的理由。

| | 例子 | 等级 |
|---|---|---|
| 反例（不能判 P2） | tech-design 的 D04 写“被拒时借阅记录的 Due、Renewed、Returned 都不变，借阅记录条数不变”，被拒的测试只比了三个字段，没比记录条数。现在的 Renew 不会新增记录，所以结果碰巧没错 | P1，没测到场景要的结果：以后有人在被拒路径里多加一条记录，测试不会变红 |
| 正例（P2） | 测试函数名叫 `TestRenew2`，看名字不知道测的是哪个场景；或者几个测试里重复写了同样的准备数据，可以抽成一个辅助函数 | P2，不影响测试能不能抓到错 |

## 回执格式

```text
功能检查回执 · <task> · 结论：通过 / 不通过 · P0 ×a · P1 ×b · P2 ×c
已检查：<每个测试文件的路径，用顿号分隔>（共 N 个测试函数）

| 编号 | 位置 | 严重度 | 问题类型 | 证据 | 怎么改 |
|---|---|---|---|---|---|
| issue-1 | tests/test_fine.py::test_fine_amount | P1 | 重写了生产逻辑 | tests/test_fine.py:12 `expected = days * 0.5` | 期望值写成手算的常量 1.5 |

穷尽声明：已检查范围内没有其他问题。
```

- 有 P0 或 P1 就是“不通过”；只有 P2 或没有问题是“通过”。
- 编号从 issue-1 起按顺序排，后面修复和处置都用这个编号。重做时接着上一份回执的最大编号往后排，不重用旧编号，免得「问题与处置」里旧的不采纳记录对上新问题。
- 没有问题时，表格只留表头。
- “已检查”必须列出派工单给的每个测试文件，写完整路径，用顿号分隔，`xdev check` 会逐个精确核对；派工单写“无”时写“已检查：无”。

## 主 agent 怎么处理

- **通过**：回执存好，P2 在「问题与处置」各记一行 `issue-N · P2 · 📝 登记，不修`，然后跑 `xdev check`。
- **不通过**：把回执里的 P0、P1 按编号退回开发者一次修完（见 [验收问题怎么修](../../x-dev/references/acceptance-fix.md)）。修完已重跑 `xdev coverage`，再按「什么时候做」第 3 条重做功能检查，最后跑 `xdev check`。最多 3 轮，轮数和卡住时的情况都记在「问题与处置」，停下告诉用户卡在哪。
- **认为某条报错了**：不修，在「问题与处置」写一行 `功能检查 · issue-N · 不采纳：<理由>`，编号和回执里的一致。回执里每条 P0、P1 都已经修好（新回执里没有了）或写了不采纳理由，`xdev check` 才放行。不采纳没有第二个人复核，所以要格外慎重。
