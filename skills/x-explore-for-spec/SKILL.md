# x-explore-for-spec

在同一个 skill 内完成探索、取舍和需求文档维护。每次核对目标、现状、范围、关键约束与验收条件；已有明确答案直接采用。一份 spec 管一块数据，长期维护在 `docs/spec/<spec名>/spec.md`；按什么划分见 [spec 范围](references/spec-scope.md)。每确认一批有价值且独立成立的结论，就更新对应条目。

## 1. 从实际问题探索，筛选值得记录的结论

先读取用户要求、`docs/spec/README.md` 边界表及相关 spec、相关代码或界面，确认实际行为和已有约定。模糊目标从一个真实例子切入，关注使用者、操作、卡点和期望结果。讨论深度随实际不确定性展开；已有依据足以确定本次行为时，直接进入增量写入。

按使用者能独立识别的功能分 feat；同一功能的主路径、边界和失败处理归在一起。逐项核对哪些结论值得进入长期文档：

- **有来源**：来自用户明确要求、实际确认或本次适用的既有约定，来源可定位。观察到的代码行为用于核实与发现冲突，需求依据来自确认过的目标和约定。
- **有作用**：直接实现用户目标、解决会影响结果的取舍，或明确关键约束与验收判据。补充边界有实际触发依据和具体影响。
- **有新增信息**：优先补齐或修订已有条目，等价结论合并；正文保存行为、约束和理由，探索过程留在对话。

价值筛选用于收敛补充内容。用户明确要求、已确认约束和有效历史行为完整保留；实质变更依据用户最新明确决定。仅有泛化收益的设想留在讨论中；用户明确要求保留的后续功能可作为计划中的 feat，标明范围与状态。

MVP 记录待验证假设、最小功能、适用环境与判断证据，边界选择聚焦验证结论的可信度。功能语言面向实际使用者；开发工具、API、基础库可描述调用方能观察的输入输出契约，内部实现由 x-tech-design 承接。

## 2. 只追问实际缺口

围绕会改变本次范围、行为或验收的缺口，用具体输入和结果澄清。每轮聚焦一个关键取舍，收到答复后再决定下一问；已明确的部分同时继续核对与写入。

- 需要用户选择时使用宿主提供的选项式提问工具，如 `request_user_input_async`、`request_user_input` 或 `AskUserQuestion`，遵守工具当前模式限制。注明关联 feat 和情境，提供 2–3 个互斥选项及结果差异；描述经历或具体数值时用开放问题。宿主仅支持对话时直接提问。
- 以用户实际提交的答案为准。预选、跳过和尚未回复均保持待决；相关行为继续等待确认，独立的已确认条目可以先写。
- 用户仅要求讨论时，在对话中交付结论。用户要求写入、更新 spec 或已授权相应开发时，按授权范围逐批落盘，沿用已有确认记录；落盘的增量仍按第 3 节给用户确认。

例如“导出当前列表”涉及当前页 20 条与全部筛选结果 80 条，应确认导出范围；用户已经指定全部筛选结果及展示列时，直接采用这项结论。

## 3. 每确认一批，就增量更新所属 spec

**先定归属：这次需求写进哪几份 spec。** 读 `docs/spec/README.md` 的边界表，按 [spec 范围](references/spec-scope.md) 逐条场景问"变化的是谁的数据"，得出每条场景的去处（加到已有 / 新建 / 只记变更 / 问用户）。判断方法和例外都以那份文件为准，这里不重复。写入前在对话里列出归属表（spec、去处、场景），并随本批 spec 增量一起给用户确认。

新建文档使用本 skill 的 [spec 模板](templates/spec.md)。已有文档先读取全文及当前改动，定位相应 feat、场景和约束，再局部编辑。

1. **选择可独立成立的增量。** 一条行为的前提、操作和结果已经明确即可写入；其他 feat 的待决项继续探索。相互依赖的取舍在结论完整后一起写入，保留本次范围内具体待决项及其阻塞对象。
2. **更新原定义。** 已有行为直接修订原场景，保留稳定编号；新增功能接续 feat 编号，新增场景接续所属 feat 的编号。相同结论沿用原定义，需求变化保留来源与变更摘要。
3. **保留历史定位。** 既有 feat、场景和 C 编号保持稳定，编号允许空缺。删除功能留下带原编号的退役记录、依据和移除后的要求；新条目使用尚未使用的编号。既有 Scenario ID 或章节定位继续沿用。
4. **区分需求确认与交付状态。** 新确认行为标为待实现或变更中；已有交付状态沿用实际证据。计划中的 feat 与待决项分开标识，本轮只承接已确认且选中的场景。已有设计或任务的行为、约束变化后，按 [需求变化同步](../x-tech-design/references/change-sync.md) 列出影响清单（编号、动作、原因），随本批增量交接。
5. **记录这一批的差异。** 变更记录只追加新增、修改或退役条目、确认来源和实际状态。已有 task 时链接其范围；尚无 task 时在 spec 简记本轮目标、选中场景、验证证据和完成条件。下次继续讨论时先读取这些记录。

每批写入后核对改动与用户结论对应，原有独立内容、约束及引用保持有效，再继续下一项探索。单轮审阅可参考 3 个 feat / 10 个场景，按清晰程度分批；spec 的累计容量按实际功能增长，出现拆分信号时按 spec 范围规则在交付时提出。

## 4. 用最少内容表达可验收行为

每个 feat 写功能名称和一句用途说明。场景采用 Given/When/Then：前提、操作、可观察结果；选择达成本次目标所需的正常、边界和失败路径。同一路径的多项共同结果写在一起，等价输入可合并，独立路径分别保留。

每条新增或实质修改的场景给出一行 `依据与价值：<用户要求或适用约定及来源>；<对目标、约束或验收的具体作用>。` 旧文档的“必要性”或其他等价来源说明继续沿用，共同依据可以引用。具体预期由确认过的行为决定。

关键约束正文在 spec 一处维护，稳定编号为 `C1`、`C2` 等，写清适用范围、可观察判据及禁止结果，关联相应场景。约束来源和原意有歧义时继续澄清，已确认的部分保持有效。用户给出的具体场景保留在 feat 下，约束通过 ID 引用。

示例：用户确认导出筛选结果和展示列，已有约定要求下载失败后保留筛选。当前可写入正常导出和失败保留两个场景；特殊字符输入确实存在时补内容完整性场景。导出历史、自动重试等新增能力进入各自的范围讨论。

## 5. 按本轮范围交接

交接包含归属表（涉及的每份 spec 路径及去处：加到已有 / 新建 / 只记变更）、影响清单（已有设计或任务时）、这批新增或修改的 feat/场景/C、需求来源与可读取内容基线、本轮完成条件，以及影响本轮的待决项。产品行为、必要约束和验收条件都明确的范围可进入 [x-tech-design](../x-tech-design/SKILL.md)；其他条目保持各自状态。

已有明确输入也完成目标、现状、范围、约束与验收核对。技术设计和任务拆解按选中场景承接，已确认的未来 feat 持续保留在所属 spec。后续阶段遵循用户本轮授权；仅写需求的任务以增量文档和未决说明交付。
