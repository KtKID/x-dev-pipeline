# x-feat-doc

让读者打开一个模块目录，就能知道它能做什么、为什么这样设计、怎么使用、各脚本和关键函数怎样完成工作，以及哪些 spec 定义了这些功能。

## 输入与产物

输入是用户指定的模块目录。结合所在仓库确定项目根目录，读取适用的 `AGENTS.md` 和已有模块说明。目录缺失或范围有歧义时，先向用户确认目标。

产物集中在模块目录的一份 `readme.md` 中，spec 索引作为其中的章节。已有 `README.md` 等大小写变体时沿用原文件名。用户明确指定文件名时遵循用户要求。

本技能的写入范围是模块说明文档。源码、配置、spec 和开发记录用于核对事实。

调用示例：

```text
x-feat-doc packages/message-history
```

## 1. 查清模块当前能做什么

围绕目标目录读取入口、主要处理过程、配置、测试和已有说明，按需查看调用它的地方。先查实际入口，再整理使用方式；目录名只作为查找线索。

整理三类信息：

- **功能描述**：谁在什么情况下使用它，能得到什么结果，以及影响使用的重要限制。
- **设计理念**：这样安排解决了什么问题，优先考虑了什么，接受了什么代价。
- **使用方式**：从哪里进入，需要准备什么，最短操作步骤，以及成功后能看到什么。

代码提供当前做法的依据；设计文档、决策记录和用户说明提供设计理由的依据。从代码推导出的理由标为“可能的考虑，待确认”。缺少设计理由时，向用户询问具体选择背后的考虑，并继续编写已有依据的部分。

使用步骤、命令、配置项和默认值对照当前入口核查。适合在当前授权和环境中执行的操作实际验证；其余内容注明检查依据及“步骤待验证”。保留影响使用的前提、限制和必要的失败处理。

## 2. 找到构建模块的 spec

在项目 `docs/` 下查找相关 spec，优先查看 `docs/spec/`。用模块相对路径、功能名称、入口名称等搜索，完整读取命中的相关章节。按需沿着 `tech-design.md`、task、开发报告和源码核对归属。

建立“spec 中的功能 → 模块中的对应行为”的关系，并为每项关系留下可点击的依据：

- spec 中有明确功能定义，设计或开发记录指向目标目录，当前代码实现了对应行为：列入“已核对的 spec”。
- spec 与代码功能吻合，构建来源仍缺少明确记录：列为“待确认的关联”，写清已有依据和待确认点。
- 只有相似名称或关键词：继续核对内容，关联明确后再收录。
- spec 描述了规划中的能力：在关联说明中标明“规划”，并说明模块当前的实现范围。

spec 索引使用 Markdown 文件链接，优先链接到相关功能章节；一行写清它定义了什么，以及与模块的关系。设计、task、开发报告和必要的源码链接放在该行的依据中。仅作为外部依赖的 spec 注明其作用，历史来源按需标明“历史”。

检索后仍缺少可核对的 spec 时，写明检索范围和“spec 来源待确认”，保留已有依据的模块说明。spec 与当前实现有差异时，正文说明当前行为，差异列入待确认项。原 spec 保持原有内容。

## 3. 说明同目录代码和关键函数

在 readme 中新增“代码说明”章节，覆盖 readme 同层的代码文件，并按模块边界纳入子目录源码，写清覆盖范围。每个脚本或源文件都有说明及源码链接；沿实际调用关系解释文件之间怎样配合。

按文件组织以下内容，简单文件可用短段落合并说明：

- **功能**：这个文件负责哪件事，在什么情况下被调用。
- **实现原理**：收到什么，按什么顺序处理，最终返回什么或改变什么；用大白话讲清关键过程。
- **设计取舍**：当前做法带来什么好处、接受什么代价、适合什么情况。理由沿用已有依据，推导出的考虑标为待确认。
- **关键函数**：逐个说明入口、主要处理、重要状态变化和失败恢复等关键函数；类中的关键方法一并覆盖。每项给出准确函数名、源码链接、用途、主要输入和结果，以及影响理解的关键处理或限制。小型辅助函数可合并说明；纯声明等文件注明其作用。

设计取舍的简单例子（仅示意写法）：

> 文件按顺序逐个处理，容易保证先后顺序，也方便找到出错的那一步；代价是文件很多时总耗时较长。同时处理多个文件可以缩短等待时间，需要额外安排处理顺序和失败后的恢复。

模块整体的设计理由集中在“设计理念”，各文件只展开具体做法和局部取舍，共用理由通过章节链接引用。关键函数说明以当前函数体和调用位置为依据，保留影响使用的条件与失败结果。

## 4. 用大白话写 readme

按 [模块说明模板](templates/readme.md) 编写，结构为：功能描述、设计理念、使用方式、代码说明、spec 索引，以及按需保留的待确认项。

文风要求：

- 开头用一两句话说清模块能帮读者完成什么。每段讲一件事，优先使用具体动作和可观察的结果。
- 设计理念讲“为什么这样安排”和关键取舍。例：“先保存记录再处理，失败后可以继续”。
- **禁止堆技术词汇。** 必要术语首次出现时紧接一句通俗解释。命令、配置键和文件名保留准确写法。
- 正文展开读者理解和使用所需的关键过程及函数。完整字段清单和逐行代码细节通过源码链接查阅。
- 使用方式给一条最短可用路径，复杂内容链接到已有指南；调用方使用的模块写最小调用示例。
- spec 索引集中维护文件关系，功能和设计的完整定义通过链接引用。

篇幅以快速读懂为目标。根据模块复杂度保留必要的前提、限制和取舍，删除空章节、占位符和重复解释。

## 5. 交付第一版草稿供检查

把第一版写入模块的 readme，开头标明“草稿，待用户检查”。已有说明按当前事实整合，保留仍有效的操作、限制和链接。

需要用户补充的内容集中放在“待确认”章节，说明问题、现有依据和答案会影响哪段说明。优先询问设计理由、模块边界和 spec 归属等会改变文档结论的问题；已有用户说明直接沿用。

交付前检查：

- 功能、设计理念和使用方式都有依据，推测与待验证内容有明确标记。
- 覆盖范围内每个脚本都有功能、实现原理、设计取舍和关键函数说明，函数名及其输入、结果与当前代码一致。
- 命令、入口、文件链接及章节定位准确，spec 索引的关联程度与证据一致。
- 用词通俗，必要术语有解释，读者能按使用方式识别成功结果。
- spec 索引就在同一份 readme 中，本轮改动集中于说明文档。

在对话中提供文档路径、简短内容预览、检查结果和待确认问题，请用户审查第一版。按用户反馈修订同一份 readme；取得确认后更新草稿标记，保留尚未解决事项的实际状态。
