# L5 架构审查

看跨模块的结构：模块之间怎么依赖、同一份信息是不是只在一处维护、以前定下的设计还守不守着。**依赖图和重复定义交给脚本找，AI 只看脚本报出来的点和下面的检查项。**

## 脚本做什么（`audit.py l5`）

- **依赖图**：按 import 画出项目内模块之间的依赖。
- **循环依赖**：图里的环，写出完整路径（a → b → a）。直接成为 P1 问题。
- **分层**：项目根目录有 `.x-code-audit.json` 且写了 `layers`（从上到下，例如 `[["api"], ["service"], ["repo"]]`）时，找下层依赖上层的地方。直接成为 P1 问题。没写就跳过，报告里记一句。
- **重复定义**：全大写的常量、枚举类，同一个名字在两个以上文件里定义。值不一样的标“已不一致”，交给子 agent 确认。

## 子 agent 做什么

读脚本结果、`docs/spec/engineering/spec.md`（有的话）、各 spec 里“架构：”开头的约束和 tech-design 的 D 规则，按检查项逐项给结论：

| 检查项 | 看什么 |
|---|---|
| 同一信息只在一处维护 | 脚本报的重复定义：是不是同一件事（是的话已不一致就是 P1，还一致是 P2），还是名字碰巧相同 |
| 模块放对地方 | 业务规则有没有跑进工具层、数据访问有没有混进接口层 |
| 没有绕过既有抽象 | 项目已有的仓库类、配置模块、服务门面，有没有被绕过、另造一套 |
| 以前定的约束还守着 | engineering 约束、“架构：”约束、D 规则、[共用开发规范](../../x-tech-design/references/development-rules.md) R1–R7，现在的代码还满足吗。核对方法按 [x-verify-tech](../../x-verify-tech/SKILL.md) 第 1–2 节：先列约束，再对照代码，能写检查命令就真跑 |
| 没有多余的抽象 | 只有一个实现的接口、只做转发的一层；要回答得出“删掉它谁会坏”，答不出才算问题 |

定期巡检只看上次巡检以来变过的模块牵涉到的依赖和约束；用户说“全量”才看全部。
