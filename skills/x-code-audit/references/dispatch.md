# 派子 agent 和回执格式

脚本做完机械部分后，剩下要 AI 判断的工作被 `audit.py start` 拆成一个个**单位**（见报告「检查进度」表里“谁查”是“子 agent”的行）。每个单位派一个子 agent，**互不依赖的单位一次全派出去，并行跑**。

- 一个单位只做一层、一个范围（一个模块，或一批死代码候选）。范围小，子 agent 才不会顾此失彼。
- 用便宜的模型（sonnet）。
- 子 agent 不改代码、不改报告，只把回执写到自己的文件里。几个子 agent 同时写同一份报告会互相覆盖，所以由主 agent 最后用 `audit.py merge` 合进报告。
- 你这个环境派不了子 agent 时，主 agent 自己按单位逐个做，回执格式一样。

## 派工单

照抄下面的格式，只填尖括号里的内容，不另加规矩（规矩都在细则文件里）：

```text
你在做代码巡检 <检查 ID> 的一部分。只做下面这一个单位，不改任何代码和报告。

- 项目根目录：<路径>
- 层：<L2 / L3 / L4 / L5 / L6>
- 单位：<模块目录，或 L2 的候选清单>
- 细则：完整阅读 <x-code-audit 目录>/references/<这一层的细则文件>，按其中的检查项逐项做
- 分级：<x-code-audit 目录>/references/severity.md
- 回执格式：<x-code-audit 目录>/references/dispatch.md 的「回执格式」一节
- 回执写到：<项目根目录>/reports/audit/audit-<检查 ID>.parts/<单位编号>.md

做完后最后一条消息只写回执文件路径和问题数。
```

## 回执格式

```markdown
# 回执

- 单位：U3
- 层：L4
- 范围：src/library/loan
- 模型：<你的模型名>

## 检查项

| 检查项 | 结论 | 位置 |
|---|---|---|
| 职责单一 | 有问题 | `src/library/loan.py` 的 `renew()`，第 40 行 |
| 对外接口说清楚 | 没问题 | `src/library/loan.py` 的 `list_loans()` |
| 测试真在测 | 没法判断 | 没有找到这个模块的测试 |

## 问题

### 续借函数里顺带发了邮件

- 严重度：P2
- 是什么：`renew()` 续借成功后直接调邮件服务发通知，续借和发通知两件事写在同一个函数里。
- 影响：以后改通知方式（比如改发短信）要动续借代码，容易把续借改坏；测续借时也得先准备好邮件服务。
- 位置：`src/library/loan.py` 的 `renew()`，第 40–46 行
- 证据：第 44 行 `send_mail(member.email, ...)`；`tests/test_loan.py` 里测续借的 3 条用例都 mock 了 `send_mail`
- 怎么改：把发通知挪到调用 `renew()` 的地方，或者让 `renew()` 返回结果、由通知模块订阅
```

规则：

- **检查项**：细则文件里这一层的每个检查项都要有一行，名字照抄。结论只写 没问题 / 有问题 / 没法判断。“有问题”的要在「问题」里有对应的一条；“没法判断”的在位置一栏写为什么判断不了。
- **不重复报**：写问题前先看一眼报告的「问题」一节，脚本或别的单位已经报过的同一个问题不再写一条，检查项照样写“有问题”，位置一栏写“已由 U3 报过”（填报过它的单位）。你发现脚本报的结论不对（比如严重度偏高、影响写错），照样新写一条问题，在证据里说明哪里不对。
- **位置**：写文件和函数，能写行号就写，格式照上面。脚本会核对文件、函数、行号是否真实存在，编造的会被查出来。
- **问题**：每条都要有 严重度、是什么、影响、位置、证据、怎么改。是什么和影响用大白话写，按 [severity.md](severity.md)「写问题时怎么说清楚」。
- 没有问题时，「问题」一节写“未发现问题”。
