# 问题分级

巡检的每个问题都按这里定 P0、P1、P2。**P0 最严重。** 只看“会造成什么后果、离后果有多近”，不看这个问题是哪一层查出来的、修起来难不难。

| 等级 | 一句话 | 判断标准 |
|---|---|---|
| P0 | 已经在出事，或者正常使用就会出事 | 用户会看到错误结果；数据会丢、会错、会串到别人那里；越权或泄露；核心流程跑不通；正常访问量下就会超时或把资源占满 |
| P1 | 已经造成了实际损害，只是范围有限；或者下一次改动很可能出事 | 照着说明文档做会失败；同一信息多处维护、而且已经不一致；循环依赖或分层被打破；类型检查报错；请求量稍大就会明显变慢（比如循环里查库）；测试看着通过、其实测不出错 |
| P2 | 现在没坏，但会慢慢变坏 | lint 没配或缺规则；CI 没跑检查；死代码；模块职责混杂；接口和错误情况没说清楚；同一信息多处维护但还一致；说明文档缺内容但没写错 |

拿不准的时候，问自己：**“不修的话，下个月最可能发生什么？”** 用户会受影响，P0；开发者会被坑，P1；只是越来越难维护，P2。

## 各层常见问题对到哪一级

这是常见情况的参考，遇到不一样的按上表判断。

| 层 | P0 | P1 | P2 |
|---|---|---|---|
| L1 机器检查 | — | 类型检查报错；lint 报的是会出错的问题（未定义变量、用错的比较） | 工具没配、缺规则、CI 没跑；只是风格类报错 |
| L2 死代码 | — | 死代码里有和在用代码同名、容易被误用的旧实现 | 没人用的函数、类、文件、导出、配置项 |
| L3 文档对代码 | 照着文档做会删数据、泄露密钥或弄坏环境 | 文档写的函数、命令、配置项、默认值和代码对不上，照着做会失败或得到不同结果 | 链接失效；新功能没写进说明 |
| L4 模块审查 | 模块里有会让用户看到错误结果的问题（一般该交 x-cr，巡检顺手发现也照实报） | 测试看着通过其实测不出错；错误被吞掉，失败被当成成功 | 职责混杂；接口和错误情况没说清楚 |
| L5 架构审查 | — | 循环依赖；下层依赖上层；同一信息多处定义且已不一致；绕过既有抽象另造一套 | 模块放错地方；同一信息多处定义但还一致；只有一个实现的多余抽象 |
| L6 性能 | 正常访问量下就会超时或占满资源 | 循环里查库、调接口；热路径上的重复计算；访问量稍大就明显变慢 | 只在数据很少的地方的低效写法 |

## 写问题时怎么说清楚

每个问题都要用大白话回答三件事，让没看过这段代码的人也能明白：

- **是什么**：哪里不对。比如“`list_loans()` 会用请求里的读者编号去查，而不是用登录的读者”。
- **影响**：不修会怎样，谁会遇到、会看到什么。比如“任何读者改一下请求参数，就能看到别人的借阅记录”。
- **位置**：文件、函数、行号，比如 `src/library/loan.py` 的 `list_loans()`，第 53 行。

不要只写“存在安全隐患”“耦合度高”这种空话，要说清楚具体会发生什么。
