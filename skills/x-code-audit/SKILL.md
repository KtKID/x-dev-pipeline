# x-code-audit · 代码巡检

每个任务的验收只查本轮的任务文档和设计。全项目会慢慢变坏的地方，比如规范没人管、死代码越积越多、说明文档过期、模块越写越乱、架构跑偏、越来越慢，靠这里查。

两种用法走同一条路：

- **定时巡检**：每晚跑，只查上次巡检以来变了的地方。
- **查一个模块**：用户点名模块或目录（“审查一下 src/library/loan”），六层都只在这个模块里跑。

## 六层

**前一层能查出来的，后一层不再查；能用脚本或工具判断的，不让 AI 读代码去猜。** AI 只做脚本做不了的那一小块，而且一次只看一个模块。

| 层 | 查什么 | 谁来查 | 细则 |
|---|---|---|---|
| L1 机器检查 | lint、类型检查、格式化：配没配、规则全不全、CI 跑没跑、现在跑一遍过不过 | 脚本，不读业务代码 | [l1-tooling.md](references/l1-tooling.md) |
| L2 死代码 | 0 引用的函数、类、文件、导出 | 工具找（Python 用脚本自带的引用扫描，JS/TS 用 knip，Go 用 staticcheck）；子 agent 只确认工具拿不准的 | [l2-dead-code.md](references/l2-dead-code.md) |
| L3 文档对代码 | 模块说明里的函数名、链接、文件名、配置项、默认值，和描述的行为 | 名字、链接、默认值由脚本逐条核对；子 agent 只核对描述行为的句子 | [l3-docs.md](references/l3-docs.md) |
| L4 模块审查 | 一个模块内部：职责、对外接口、错误处理、测试是否真在测 | 子 agent，一个模块一个 | [l4-module.md](references/l4-module.md) |
| L5 架构审查 | 循环依赖、下层依赖上层、同一信息多处定义、绕过既有抽象、以前定的约束 | 依赖图和重复定义由脚本找；子 agent 只看脚本报的点和固定检查项 | [l5-architecture.md](references/l5-architecture.md) |
| L6 性能 | 循环里查库或调接口、重复计算、数据结构不合适、阻塞等待、资源不释放 | 子 agent，一个模块一个 | [l6-perf.md](references/l6-perf.md) |

## 流程

下面的命令都在项目根目录运行，`audit.py` 指 `<本 skill 目录>/scripts/audit.py`。

### 1. 开一次巡检

```bash
python3 audit.py start                              # 定时巡检：上次巡检以来变了的；第一次跑就是全量
python3 audit.py start --module src/library/loan    # 只查一个模块，可以给多个 --module
python3 audit.py start --layers L2                  # 只跑某几层，比如“查查死代码”
python3 audit.py start --full                       # 全量
```

它会生成一个 8 位随机的**检查 ID**，并在项目的 `reports/audit/` 下写好报告骨架 `audit-<检查 ID>.md`：开头是检查 ID、代码版本、范围（哪些模块、哪些文件）、要跑的层，下面是「检查进度」表，列出这次要做的每个**单位**（一层 × 一个范围）。整次巡检只有这一份报告，后面所有结果都写进它。

### 2. 先跑脚本部分

```bash
python3 audit.py scripts <检查 ID>
```

它跑完 L1、L2、L3、L5 的脚本部分，结果和问题直接写进报告。工具拿不准的死代码、要核对行为的说明，会被登记成新的子 agent 单位。

### 3. 并行派子 agent

```bash
python3 audit.py units <检查 ID>     # 列出所有还没做的子 agent 单位
```

**这些单位互不依赖，一次全派出去并行跑**，不要一个做完再派下一个。每个单位派一个便宜的子 agent（sonnet），派工单照抄 [dispatch.md](references/dispatch.md) 的模板，只填范围和路径，不另加规矩。子 agent 只读代码，把回执写到 `reports/audit/audit-<检查 ID>.parts/<单位>.md`，不改代码、不改报告。

派不了子 agent 的环境，主 agent 自己按单位逐个做，回执格式一样。

### 4. 合并

```bash
python3 audit.py merge <检查 ID>
```

把所有回执合进报告：检查项写进「检查记录」，问题写进「问题」，**按 P0 → P1 → P2 排序**并重新编号 A1、A2…，然后删掉回执目录。最后只剩一份报告。

### 5. 证明查过了

```bash
python3 audit.py verify <检查 ID>
```

它用脚本核对，不再派 AI 重查：

- 检查进度里每个单位都做完了，检查记录里都有它；
- 每个子 agent 单位，细则里的检查项都有结论（没问题 / 有问题 / 没法判断），“有问题”的都有对应的问题条目；
- 每个问题都有 是什么、影响、位置、证据；位置里写的文件、函数、行号都真实存在；
- 问题按 P0 → P2 排好。

不过就按提示补，补完再跑。全过后报告状态改成“完成”，下次定时巡检从这次的代码版本往后查。

然后主 agent 随机挑一条子 agent 报的问题，打开对应代码看一眼是否属实。不属实，就把那个单位标回“待查”重派。

### 6. 写结论、交付

在报告的「结论」里写每层的结果（有问题 / 没问题 / 未完成）和问题数，再用一两句话说最严重的问题。然后告诉用户：报告路径、检查 ID、P0 有哪几条。

不改代码、配置和文档。要修时：

- 一般问题：交 x-fix 按报告修。
- 结构性问题（模块搬家、拆分合并、分层调整）：先由用户拍板，再走 x-qdev 或完整主线。
- 文档问题：用 x-feat-doc 重写对应模块的说明。

## 问题怎么写

严重度按 [severity.md](references/severity.md) 定，**P0 最严重**。每个问题都用大白话写清：

- **是什么**：哪里不对；
- **影响**：不修会怎样，谁会遇到、会看到什么；
- **位置**：文件、函数、行号；
- **证据**：代码片段、跑过的命令和输出；
- **怎么改**：一句话的修改方向。

报告格式见 [report-template.md](references/report-template.md)。

| 规范、死代码、文档过期、模块和架构的质量、性能 | 本 skill |

## 不做的事

- 不用 AI 逐行审 lint 能管的规范（命名大小写、缩进、行长、未使用的导入）。lint 没配，就报“该配哪条”。
- 不报没有证据的个人偏好。说“过度抽象”要回答得出“删掉这一层谁会坏”。
- 定时巡检不重查没变的模块。
