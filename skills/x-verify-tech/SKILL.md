# x-verify-tech

回答“本次实现是否遵守技术设计、共用规范和架构约束”。结论只覆盖明确范围、代码基线和实际取得的证据。

管线内不单独调用：x-qa-gate 的 reviewer 做 q4-design lens 时按第 1–2 节做，结果并入审查回执。用户单独要求时，按全文做并直接在对话里给回执。

## 输入

- 设计：tech-design 的 D 条目，或 qdev ②的局部方案；需要用户拍板的取舍附答复来源。
- 范围：task / feat / D 条目，或 `git diff <代码基线>` 的文件。
- 规范：[共用开发规范](../x-tech-design/references/development-rules.md) R1–R7、本 spec 和 `engineering` spec 关键约束里“架构：”开头的架构约束（没有就跳过）、项目 `AGENTS.md` 等附加规则。

缺设计来源或取舍还在等用户拍板时，相关项记“未验证”并列出要确认的问题，不从实现反推设计。

## 1. 先列约束，再找实现

先读设计和规范，不看实现就写出约束清单：保留 `D01` 等编号，无编号的用章节或行号定位。每项写来源、为什么适用、预期是什么、打算怎么查。R1–R7 和架构约束逐条判断是否适用，设计漏写不能成为跳过的理由；落实方案不确定就列为设计缺口。

需要时读 spec 的场景和 C 来确定行为含义，但不复制功能验收。

## 2. 对照代码，能跑的就跑

约束清单定了以后，再找真实入口、模块、schema、状态读写、配置和现有测试。

| 核对对象 | 怎么查 |
|---|---|
| 模块边界与依赖（R1）、架构约束里的分层/依赖规则 | 对照公开入口、允许的依赖和实际 import/调用；有现成的循环依赖或分层检查工具就跑，没有就做代码审查，列出依赖链和位置。局部搜索没命中不能证明全范围没有 |
| 协议与校验（R2–R3） | 从权威 schema 追到生产者、消费者、边界校验和错误传播；只声明了类型不能证明入口真的校验了 |
| 数据、概念与状态（R4–R5、R7） | 追数据所有者、权威存储和全部读写；核对派生值、缓存、索引的更新和失效顺序 |
| 具名配置（R6） | 定位权威配置、单位、默认值和实际使用点，查重复的字面值 |
| 架构约束里的其他条目（命名、目录、技术选型、禁止事项） | 逐条对照 diff，写明文件和理由 |

能机器验证的实际运行；语义判断写出文件/符号、调用或读写链和理由，标为代码审查。静态检查全绿不能代替数据归属这类语义判断。动态机制（幂等、并发、重试、恢复）需要测试证据，读代码不够；现有测试没覆盖到的，写成问题交 x-fix 补测试，本技能不改测试和代码。

## 3. 结论

- 每项只有 **通过 / 失败 / 未验证**；一项含多个约束时全部有证据才通过。不适用要写具体理由，缺工具、缺证据不是不适用。
- 失败给出违约位置和最小反例；未验证写缺什么、怎么补。
- 整体：有失败就是失败；无失败有未验证就是未验证；全部通过才是通过。

在 x-qa-gate 里，失败项按 q4-design lens 的候选格式（`lens · task · severity · loc · msg · 证据`）返回：设计或架构约束没落实是 P1，会导致错误结果或数据损坏是 P0。

单独使用时的回执：

```text
🔧 技术核对 <通过/失败/未验证> · <范围> · 代码基线 <commit> · 通过 N · 失败 M · 未验证 K
| 约束 | 来源 | 结果 | 位置与证据 |
```
