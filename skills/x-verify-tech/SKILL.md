# x-verify-tech

回答“本次实现是否遵守技术设计与适用规范”。结论只覆盖明确范围、代码基线和已取得的证据；测试通过不等于全面正确证明，也不能保证没有漏洞。

## 输入与权限

- 项目根目录：明确可访问路径；项目文件路径相对此根目录。
- 设计路径/章节、内容基线与依据：tech-design 的条目，或按下述 qdev 模式提供的局部设计；需要用户拍板的取舍记录实际答复来源，已有记录直接复用。
- 本次范围：task/feat、设计条目或明确 diff 基线/文件范围及承接来源；包括受影响的共享约束，不自行扩成全仓验收。
- 适用规范：项目 `AGENTS.md`、相关 `.agents/skills`、开发规范的路径与已知约束；无附加规范也注明。按需提供 spec 路径及基线以澄清行为依据。
- 授权边界与测试报告入口：是否允许新增验收测试、可用隔离环境/数据和外部副作用限制；优先使用任务提供的统一 `test-report.md`，独立验收按 [共用报告约定](../x-dev/references/test-reporting.md) 建立该报告与附件。只读委派返回增量回执，由主 agent 收录。

缺输入先列具体缺项和影响；确认缺失、来源冲突或需求/设计歧义的受影响项记为未验证，向用户列出需确认的问题，其余项继续。不从实现猜预期，不修改已确认设计或自动启动其他技能。

缺可核查的设计来源，或相关取舍仍在等用户拍板时，相关项为未验证，不能仅靠 spec 场景或测试绿灯宣称技术符合性通过。C/D/用例编号按各自权威来源定位；旧设计没有 C 映射时沿用其已有 D、场景/约束 ID 或章节定位，不强制补编号，发现真实机制或测试覆盖缺口才报告。

### qdev 局部设计输入

明确指定 x-qdev task Markdown 时读取完整文档，以其②精简技术设计及头部指向的外部设计作为技术依据，③提供局部用例或权威用例回指，①回指的 spec/模块功能正文及移除记录提供行为和约束依据，旧独立任务沿用①的既有主定义与基线，④⑤帮助定位范围与执行线索。

本模式中，用户明确的原始任务要求及已有结论提供小任务范围内的执行授权；普通局部方案按该授权、既有设计与规范核查。②允许由 agent 在实现前自行记录简短方案，技术验收核对其依据、范围、基线和实际实现。tech-design 不需要用户确认；qdev 中需要用户决定的是写了场景的 spec 增量（只记变更的不用），以及实质性歧义和超出授权的关键变化。

- 外部设计条目保持权威来源；②只说明本次沿用与局部差异。局部 D/用例以文件路径限定，和外部同号条目分别定位。
- 沿用条目核对原设计来源与本次适用理由；普通局部实现安排核对用户原始要求/已有结论、任务授权、既有设计、规范和实现前的可读基线；按 [qdev 风险规则](../x-qdev/references/risk-rules.md) 有一条答"是"的改动属于超出 qdev 的范围问题，单列。作者写“已确认”或当前代码符合其自行补写设计不能充当依据。
- qdev 设计和用例的权威位置分别可以在②③。本轮证据仍由本技能实际运行相关检查取得，⑤旧结果作为线索。旧四段任务可取已有外部确认设计及用例；缺本轮设计/预期来源时保留未验证，不从实现反推补齐。
- 复用下文 R1–R7、基线与逐项结果规则。返回本轮检查增量与技术回执，由 qdev 主 agent 收录到⑤指向的统一测试报告；保持任务文档、业务代码和设计原样，新增测试仍受明确授权限制。

只在授权项目测试范围内新增验收测试或隔离测试文件，本轮证据写入统一报告与附件。保持业务实现、已有断言、排除项、阈值、设计/spec、任务状态及 issue ledger 原样，发现问题返回处置线索。安装依赖、搭平台及外部副作用按任务授权处理。持久化测试仅使用隔离临时夹具数据并清理。

## 1. 先列设计约束，再找实现

先读适用的外部或 qdev 局部设计和规范，尚不据实现建立预期。复用 [x-tech-design 开发规范](../x-tech-design/references/development-rules.md)，不另抄一份规则。该链接相对本技能目录解析；设计及规范中的项目路径相对项目根目录，其他文档的相对引用按其声明的基准解析。记录解析后的可访问路径；共用资源缺失时查找可访问的 x-tech-design 安装/仓库位置，不凭记忆补规范，仍不可读的项标未验证并列最小补法。

从本次范围提取约束清单：保留 `D01` 等已有编号；无编号用章节/行号定位，不回写设计。每项写来源、适用原因、预期/不变量和拟用方法。逐条核对共用规范 R1–R7 及项目附加规则；相关规则不能因设计漏写而跳过，无法确定落实方案时列设计缺口。小改动引用沿用基线，只检查差异及受影响约束。

按需读取 spec 的具体 feat/场景及已确认 C 约束来确定行为、边界或数据含义；沿用明确设计来源的 C→D→用例映射，核对保障约束的技术机制（如幂等、结果核对和并发控制），不复制功能验收全集，不代替功能验收。无法确定预期时列具体回指、分歧与影响，请用户确认，不用技术假设补需求。

## 2. 对照代码并复用检查

约束清单确定后，再定位真实入口、模块、schema、状态读写、配置和现有测试。读取项目已安装工具、测试配置与已有检查命令，先检查现有断言是否覆盖该约束，再运行相关检查/测试；开发报告和旧绿灯仅作线索，不能冒充本轮执行结果。

| 核对对象 | 可操作方法（判定标准来自设计与共用规范） |
|---|---|
| 模块边界与依赖（R1） | 对照公开入口、允许依赖和实际 import/调用；优先运行现成循环/内部访问检查，无工具则明确做代码审查，列出依赖链、内部访问位置及覆盖局限。局部搜索无命中不能证明全范围无循环 |
| 协议与校验（R2–R3） | 从权威 schema 追生产者、消费者、边界校验和错误传播；核对 TS Zod 的运行时校验与类型推导、Python Pydantic 的实际校验入口，跨语言查生成/同步及漂移证据。仅声明模型/类型不能证明入口校验生效；已有不同方案依技术设计核对差距，不自动替换 |
| 数据、概念与状态（R4–R5、R7） | 追数据所有者、值的权威存储和全部相关读写；对照派生值及缓存/索引/快照的更新、失效、重建与提交顺序。说明名称映射的语义依据，区分协议定义源和值来源；不靠字符串搜索判断唯一来源 |
| 具名配置（R6） | 定位权威配置、单位/默认值、覆盖方式及实际使用点；对照边界行为与重复字面值，不把普通索引当业务阈值 |

可机验的相关项实际运行；语义项给出文件/符号、调用或读写链及判断理由，明确标为代码审查，不能伪称自动验证。静态检查全绿不能代替协议权威性、数据归属等语义审查。

## 3. 按风险补少量针对性验证

优先复用外部设计或 qdev③已编号用例的主定义，引用用例 ID 并检查其实际断言/观察是否验证相应 D 机制；不要另抄测试正文或改低验收标准。为现有证据未覆盖的约束选择能观察违约的方法，主要使用项目已装测试框架。按适用风险选择真实边界集成、非法/边界输入、持久化失败、重复请求、并发或恢复；不要求每个任务全套工具/用例，也不搭新的测试体系。动态机制的证据不能由静态阅读替代。

获授权后可新增少量验收测试或隔离测试文件；补充探针以报告内局部编号标识，回指原 C/D/用例，不冒充或重定义主用例。若需扩充正式测试设计，列缺口交设计负责方维护其权威主定义（外部 tech-design 或 qdev②③），本技能不改设计。expected 必须回指设计、规范或 spec，不从被测输出生成；不 mock 掉待验证机制（如验存储却替换持久化层），其他替身须说明替代边界和证据限制。故障注入须保留待验证的真实处理路径。

核实命令、工作目录、选择范围、退出码、实际执行/跳过数和关键断言/观察。零测试、关键用例跳过、错误退出、超时、环境故障或只测替身均不能通过；确定违约/断言反例记失败，未执行到有效验证或证据不足记未验证。缺工具/环境/授权时不自动安装或改断言，列未验证项和最小补法。测试总数不能代替逐项证据映射。对于“成功但回执丢失后重试”，须验证结果未知不会被当作失败、去重/结果核对路径真实执行及最终副作用数量；只验证重试函数返回成功不足以证明机制。一个 C 的一条用例通过也不等于全部约束或功能需求覆盖，业务覆盖对账仍由 x-verify-spec 核对。

## 4. 逐项交付证据与结论

按 [共用报告约定](../x-dev/references/test-reporting.md) 复查当次代码改动的统一测试报告、用例明细及原始附件。核对覆盖采集版本、diff 范围、改动行与相关分支、未覆盖位置和未采集项；本轮新增/复跑检查按执行编号纳入同一报告。已有完整过程引用来源并补本轮结果，原始输出集中放附件。

使用 [增量回执模板](templates/verify-tech-report.md) 返回设计/规范条目、适用性、代码位置、用例/执行编号、技术判断与局限。主 agent 将结果收录到测试报告的用例和验收节；独立验收直接维护该统一报告。失败给最小反例或实际违约证据，未验证给缺项及最小补法。

记录代码基线（Git HEAD 加工作区差异/相关文件内容哈希，不能只记 HEAD）、设计/规范及使用的 spec 基线；新增测试的路径和最终内容也纳入基线。执行证据注明环境及来源；报告中的方法、命令和结果必须实际发生。代码或相关输入改变后重跑受影响证据，不能沿用旧通过。

- 适用项只有 **通过 / 失败 / 未验证**；一项含多个约束时全部有充分证据才通过，部分缺失须拆行或记未验证。
- 不适用单列具体理由，不伪装通过；工具缺失、未实现、未执行或缺证据不是不适用。
- 整体结论：任一失败为 **失败**，同时保留未验证清单；无失败但有未验证为 **未验证**；全部适用项通过且范围/基线可核实才为 **通过**。没有适用项时说明原因，不宣称验收通过。

回执包含范围、统一测试报告入口、待收录增量或已写入位置、逐项结果和限制、待确认问题及新增测试路径。范围外缺陷可另列提示，后续处置交主 agent。

## 委派输入

父 agent 委派时给自足输入，不要求子 agent 猜父会话；委派本身不扩展测试或副作用授权：

```text
任务：使用 x-verify-tech 验收技术符合性，不修改业务实现或设计。
技能入口：<可访问的 SKILL.md；共用规范及模板也须可访问>
项目根目录：<路径>
设计：<外部 tech-design 或 qdev②路径/条目、基线、沿用依据；需用户拍板的取舍附答复来源>
用例：<外部主定义或 qdev③路径/用例 ID>
范围：<task/feat/设计条目或 diff 基线及文件；承接来源>
规范与 spec：<适用规范路径/约束；按需使用的 spec 路径/基线>
授权与输出：<允许新增测试的范围、隔离环境/数据、副作用限制；统一测试报告及附件路径、是否只读返回增量>
返回：<本轮用例/执行增量、技术回执、整体结论、局限/待确认项、新增测试路径>
```
