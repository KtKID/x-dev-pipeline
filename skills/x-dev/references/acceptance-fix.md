# 验收问题怎么修

x-verify-spec 验收不通过时，问题退回开发者自己修：常规 task 是 x-dev 的主 agent，qdev 是做这个 task 的 agent。多 agent 协作时已经过了开发阶段，由主 agent 修，不再分组派工。

## 要修的问题

- 功能检查回执（证据目录的 `feature-check.md`）里的 P0、P1，编号沿用回执的 `issue-<n>`。
- `xdev check` 列出的要改代码或测试的问题，按顺序编号 V1、V2…。

哪些问题由开发者修、哪些交给别人，以 [x-verify-spec「问题去向」](../../x-verify-spec/SKILL.md#问题去向) 为准。两类可以同一轮一起修。

## 做法

1. 数「问题与处置」（qdev 是⑤的同名节）里已有几行 `修复第 N 轮`。已满 3 轮：不再修，写一行 `修复卡住：<积压问题编号和原因>，等用户决定（继续 / 改需求 / 放弃）`，停下告诉用户卡在哪。
2. 本轮至少有一条要修时，先写一行 `修复第 N 轮：<本轮问题编号>`（N 接着往下数，一份问题清单整体算一轮，修到一半中断也算），再开始修。一条都不用修就不写。
3. P0 全修；P1 逐条修，或认为报错了就写一行 `功能检查 · issue-N · 不采纳：<理由>`（`xdev check` 认这个写法）。不采纳没有第二个人复核，要格外慎重。
4. 一次修完本轮全部问题。每修一个 P0，留一条能复跑的反例测试。修复动到配置、命令行、公开接口、协议或数据格式时，原来能用的输入要继续能用：新配置字段给默认值；spec 明确要不兼容的，按 spec 写迁移验收。
5. 修完跑每条的反例测试，再跑 `xdev coverage`（全量测试全绿、改动行覆盖率 100%）。新加的反例测试登记进用例对应表，同样遵守 x-dev「测试是硬规则」。
6. 每条处置一行写进「问题与处置」，不另建修复文件：

   ```markdown
   - issue-1 · P0 · ✅ 已修：扩展 SQLSTATE 分类 · 反例 tests/test_classify.py::test_sqlstate_retry
   - 功能检查 · issue-2 · P1 · 不采纳：<理由>
   - V1 · ✅ 已修：src/loan/renew.py:12-14 没覆盖，补 tests/test_renew.py::test_renew_edge
   ```

7. 代码或测试改过，按 [功能检查](../../x-verify-spec/references/feature-check.md)「什么时候做」第 3 条重做功能检查（整份再查一遍，附上一份回执用来接着编号），再跑 `xdev check`。
8. 修的过程中不改 checklist 状态列，验收通过后再升 `[x] ✅`。

## 按问题类型修

- **漏做 / 多做**：补上场景要的行为，或删掉多做的部分。公开接口签名变了在处置里标出来。
- **测试问题**（重写了生产逻辑、没调项目代码、绕过要测的流程、mock 掉被测对象、只断言调用、断言恒真、吞掉失败、数据测不出对错、没测到场景要的结果、人工记录不全）：默认只改测试，不为了测试好写去改生产代码。测试改对后暴露出生产代码真有错，一并修，处置里如实写。
- **V 项**：只修让检查不过的地方：测试失败、编译错误、没覆盖的行（补测试）、缺真实链路用例（补 smoke 或集成测试）。V 项不能豁免。悬空引用、范围遗漏、SPEC_CHANGED 这类文档或分配问题不在这里修，交 x-req / x-tech-design。
- 不为了通过去改用例对应表的结果、删用例、降低断言或加没有理由的覆盖率排除标记。
