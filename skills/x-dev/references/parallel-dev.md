# 多 agent 协作开发

一句话：**主 agent 按 `xdev graph` 的批次把并行组派给工人子 agent；每组做完由另一个 agent 验收；主 agent 按依赖顺序一组一组合并。**

checklist 只有一个并行组时不用这套：主 agent 自己按 x-dev 的 SKILL.md 做完，或者派一个工人做完，省主 agent 的上下文。x-qdev 不用这套。

## 三个角色

| 角色 | 由谁担任 | 做什么 | 不做什么 |
|---|---|---|---|
| 主 agent | 调用 x-dev 的 agent | 派单、派验收、合并、回写 checklist 状态、改共享文件 | 不替工人写这组的代码 |
| 工人 | 子 agent，一组一个 | 按派工单做完这组的行，交回执 | 不改派工单以外的文件，不写 checklist 状态列 |
| 验收 agent | 另一个子 agent，不能是做这组的工人；能换 harness 就换 | 对这组跑 x-verify-spec 和 x-verify-tech，交回执 | 只读，不修代码 |

## 主 agent 的步骤

1. **开工前**
   - `xdev validate <task>` 必须通过。
   - `xdev impact <task>` 必须报"没有变化"。有变化时按 [需求变化同步](../../x-tech-design/references/change-sync.md) 同步，再运行 `xdev baseline`。
   - 用 `xdev graph <task>` 取得派工批次。
2. **派单**：每组从当前主干拉一个分支 `dev/<task>/<组>`，能用 worktree 就给它一个独立 worktree，然后写派工单（见下）派给工人。同一批的组同时派；下一批要等它依赖的组合并以后再派。
3. **派验收**：工人交回后，派验收 agent 对这组的行跑 x-verify-spec 和 x-verify-tech。
4. **验收不通过**：把验收回执交回**原来那个工人**，在它原来的会话里接着修。每组各自计轮数，最多 3 轮；3 轮还不过，就停下这一组升级给用户，其他组照常进行。task 级的 `reports/.fix-counter` 留给合并后的整体验收和 x-qa-gate，不用来计各组的轮数。
5. **合并**：按批次顺序一组一组合进主干，每合一组跑一次全量测试。合并冲突或测试不过，就打回**后合的那一组**，让它在最新主干上重做，这也算一轮。
6. **共享文件**：工人回执里"集成时处理"的项（spec 变更记录、索引、依赖锁文件等），由主 agent 在合并后统一改。
7. **checklist 状态与派工记录**：checklist 状态列只由主 agent 写。工人在回执里报每行的状态和证据，主 agent 核对后回写。主 agent 在 dev-report 的「派工记录」一节记每组的分支、工人、验收轮数和当前状态，中断后能接着做。
8. **工人报回的问题**，主 agent 从下面三种处理里选一种：
   - 范围内能解决的：调整派工单，比如补一个文件，同时在 checklist 补上该文件，重跑 `xdev validate` 和 `xdev graph`，确认没有和别的组撞文件。
   - 需求或设计的问题：交来源负责方（x-explore-for-spec / x-tech-design）。
   - 和本 task 无关的：登记成后续任务。
9. **中途 spec 变了**：`xdev impact` 会列出受影响的任务行。只停这些行所在的组，其他组继续。同步完、记了新基线后，重新派受影响的组。
10. **全部合并后**：对整个 task 再跑一次 x-verify-spec 和 x-verify-tech，然后按 checklist 头部的 `risk` 处理：Q2 / Q3 交 x-qa-gate；Q0 / Q1 由主 agent 把行升为 `[x] ✅` 并交付。

## 派工单模板

```text
派工单 · <task> · 组 <A>
- 分支：dev/<task>/A（基于 <commit>）
- 任务行：T1、T2（按行序做）
- 只许改的文件：<这些行"涉及文件"的并集>；可以新建这些行自己用的测试文件
- 依据：<spec 路径>、<tech-design 路径>；要通过的用例：T1、T2 …
- 测试命令：<本组用例的命令>；交付前再跑：<回归命令>
- 不许碰：checklist 状态列、spec、tech-design、变更记录和索引
- 交付：按「工人回执」格式
```

## 工人的规则

工人按 x-dev SKILL.md 的逐行开发规则做（先写测试、有效红灯、不 mock 掉被验证的机制……），再加上下面这些：

| 遇到的情况 | 工人怎么做 |
|---|---|
| 改派工单里列出的文件 | 正常改 |
| 要给自己这几行新建测试文件 | 可以建，回执里列出来 |
| 要改派工单以外的文件（哪怕只改一行） | 不改。停下这一行，报回：要改哪个文件、为什么、打算怎么改 |
| 发现 spec 或 tech-design 有问题（写错、缺用例、和代码冲突） | 不自己补设计。停下受影响的行，报回 |
| 发现别的组范围内的 bug | 不修，记进回执的"报回问题" |
| 要改共享文件（spec 变更记录、索引、依赖锁文件） | 不碰，写进回执的"集成时处理" |
| 同一行失败多次，原因不清楚 | 不改目标、不降低断言，停下这一行报回 |
| 停下了一行，但同组的其他行不依赖它 | 继续做其他行 |

## 工人回执

```text
组 A · 分支 dev/<task>/A@<commit>

| 行 | 状态 | 证据 |
|---|---|---|
| T1 | 🟢 | reports/<task>/<batch>/evidence/... |
| T2 | 🔴 停下 | 见报回问题 1 |

新建文件：tests/xxx.test.ts
报回问题：
1. T2：要改 src/shared/date.ts（不在派工单里），因为 ……，打算 ……
集成时处理：
- spec 变更记录加一行：……
```

## 验收 agent 回执

按 x-verify-spec 和 x-verify-tech 各自的回执格式，范围写清是"组 A 的 T1、T2，分支 dev/<task>/A@<commit>"。主 agent 把回执收进这个 task 的统一测试报告。
