# 多 agent 协作开发

一句话：**主 agent 按 `xdev graph` 的批次把并行组派给工人子 agent；每组做完由另一个 agent 验收；主 agent 按依赖顺序一组一组合并，最后做整体收尾。**

## 什么时候用

| 情况 | 怎么做 |
|---|---|
| checklist 有两个及以上并行组 | 用本文的流程 |
| 只有一个并行组 | 主 agent 自己按 x-dev SKILL.md 做完。想省主 agent 的上下文时，也可以派一个工人做完，这个工人同样遵守本文的「工人的规则」 |
| 环境里派不了子 agent | 主 agent 按 `xdev graph` 的批次一组一组自己做；每组做完照样另起一个会话验收，合并和收尾规则不变 |
| x-qdev | 不用本文 |

## 三个角色

| 角色 | 由谁担任 | 做什么 | 不做什么 |
|---|---|---|---|
| 主 agent | 调用 x-dev 的 agent | 派单、派验收、回写 checklist 状态、合并、改共享文件、整体收尾 | 开发阶段不替工人写这组的代码 |
| 工人 | 子 agent，一组一个 | 按派工单做完这组的行，交回执 | 不改派工单以外的文件，不写 checklist 状态列 |
| 验收 agent | 另一个子 agent，不能是做这组的工人；能换 harness 就换 | 对这组跑 x-verify-spec 和 x-verify-tech，交回执 | 只读，不修代码 |

## 主 agent 的步骤

1. **开工前**
   - `xdev validate <task>` 必须通过。
   - `xdev impact <task>`：报"没有变化"才派单。报出变化时，按 [需求变化同步](../../x-tech-design/references/change-sync.md) 把它列出的项同步完（或确认只是措辞变化），再运行 `xdev baseline`。
   - 用 `xdev graph <task>` 取得派工批次。
   - 记下任务开始前的主干 commit，后面算改动覆盖率用它当基线。
2. **派单**：每组从当前主干拉一个分支 `dev/<task>/<组>`，能用 worktree 就给它一个独立 worktree，然后写派工单（见下）派给工人。同一批的组同时派；下一批要等它依赖的组合并以后再派。派工记录里这组记为"已派出"。
3. **收回执、派验收**：工人交回后，主 agent 核对回执：报"已完成"的行回写成 `[ ] 🟡` 待验证；报"停下"的行保持 `[ ] ⏳`，派工记录写"阻塞：<原因>"。然后派验收 agent 对这组已完成的行跑 x-verify-spec（按组对账）和 x-verify-tech，派工记录记为"验收中"。
4. **验收不通过**：把验收回执交回**原来那个工人**，在它原来的会话里接着修，派工记录记为"修复中"。工人的会话已经结束时，用原派工单加上验收回执重新派一个工人。每组各自计轮数，最多 3 轮；3 轮还不过，这组的行标 `[ ] ↗️`，停下这一组升级给用户，其他组照常进行。各组的轮数记在派工记录里，不写 task 级的 `reports/.fix-counter`。
5. **合并**：验收通过的组记为"待合并"。按批次顺序一组一组合进主干，每合一组跑一次全量测试。
   - 全部通过：这组的行回写为 `[x] 🟢`，派工记录记为"已合并"。行只有合并进主干并通过全量测试后才写 🟢。
   - 合并冲突或测试不过：看失败的测试属于哪一组的行。能定位到一组就打回那一组；定位不了时，打回后合的那一组，并附上失败输出。被打回的组在最新主干上重做，算一轮。
6. **共享文件**：工人回执里"集成时处理"的项（spec 变更记录、索引、依赖锁文件等），由主 agent 在每组合并后统一改。
7. **checklist 状态与派工记录**：checklist 状态列只由主 agent 写。派工记录在 dev-report 的「派工记录」一节，每组一行：分支、工人、验收轮数、状态。状态只用这几种：等待依赖、已派出、验收中、修复中、待合并、已合并、阻塞、已升级。中断后照这张表就能接着做。
8. **工人报回的问题**，主 agent 从下面四种处理里选一种：
   - **要改派工单外的文件，这个文件不属于别的组**：把文件补进这一行的"涉及文件"和影响文件树，重跑 `xdev validate` 和 `xdev graph`，更新派工单后让工人继续。
   - **要改的文件正在被另一组改**：两组不能同时改一个文件。把这一行改成依赖那一组的相应行，重跑 `xdev validate` 和 `xdev graph`，等那一组合并后再派这一行。
   - **需求或设计的问题**：交来源负责方（x-explore-for-spec / x-tech-design），改完按第 9 步处理。
   - **和本 task 无关的问题**：登记成后续任务。
9. **中途 spec 变了**：运行 `xdev impact`，按 change-sync 同步：受影响的行重开为 `[ ] ⏳`，需要的新行补进 checklist，然后 `xdev validate`、`xdev baseline`。
   - 只停受影响的行所在的组，其他组继续。
   - 受影响的组还没合并：原工人在原分支按更新后的派工单继续。
   - 已经合并：从最新主干新开分支重新派，这组的验收轮数从 0 重新算。
10. **整体收尾**：所有组都合并后，主 agent 在主干上做 x-dev SKILL.md 的第 4、5 步：Web 任务的浏览器验收、本 task 全量测试和回归、按第 1 步记下的基线采集改动覆盖率、把各组的证据汇进唯一测试报告、给用户的回执。
11. **整体验收**：对整个 task 再跑一次 x-verify-spec 和 x-verify-tech。都通过后，按 checklist 头部的 `risk` 处理：Q2 / Q3 交 x-qa-gate；Q0 / Q1 由主 agent 把行升为 `[x] ✅` 并交付。
12. **整体验收或 x-qa-gate 发现问题**：整个 task 一份问题清单交 x-fix，由主 agent 执行 x-fix（这时已经过了开发阶段，不再分组派工），按 task 级 `reports/.fix-counter` 计轮数。

## 派工单模板

```text
派工单 · <task> · 组 <A>
- 分支：dev/<task>/A（基于 <commit>）
- 任务行：T1、T2（按行序做）
- 只许改的文件：<这些行"涉及文件"的并集>；可以新建这些行自己用的测试文件
- 证据目录：reports/<task>/<batch>/evidence/A/（只写这一组的原始输出，执行编号用 A-001、A-002…）
- 依据：<spec 路径>、<tech-design 路径>；要通过的用例：T1、T2 …
- 测试命令：<本组用例的命令>；交付前再跑：<回归命令>
- 不许碰：checklist、dev-report、统一测试报告正文、spec、tech-design、变更记录和索引
- 交付：按「工人回执」格式
```

## 工人的规则

工人按 x-dev SKILL.md 第 2、3 步的逐行开发规则做（先写测试、有效红灯、不 mock 掉被验证的机制、失败按根因修），再加上下面这些。

**x-dev SKILL.md 里这些事工人不做，由主 agent 做**：回写 checklist 状态列、运行 `xdev baseline`、写 dev-report、汇总统一测试报告、第 4 步收尾验证、第 5 步给用户的回执。工人把每行的状态和证据写在自己的回执里。

| 遇到的情况 | 工人怎么做 |
|---|---|
| 改派工单里列出的文件 | 正常改 |
| 要给自己这几行新建测试文件 | 可以建，回执里列出来 |
| 写测试的原始输出 | 只写派工单给的证据目录 |
| 要改派工单以外的文件（哪怕只改一行） | 不改。停下这一行，报回：要改哪个文件、为什么、打算怎么改 |
| 发现 spec 或 tech-design 有问题（写错、缺用例、和代码冲突） | 不自己补设计。停下受影响的行，报回 |
| 发现别的组范围内的 bug | 不修，记进回执的"报回问题" |
| 要改共享文件（spec 变更记录、索引、依赖锁文件） | 不碰，写进回执的"集成时处理" |
| 同一行失败多次，原因不清楚 | 不改目标、不降低断言，停下这一行报回 |
| 停下了一行，但同组的其他行不依赖它 | 继续做其他行 |
| 一行验证通过了 | 不改 checklist，在回执里报这一行"已完成"并给证据 |

## 工人回执

```text
组 A · 分支 dev/<task>/A@<commit>

| 行 | 状态 | 证据 |
|---|---|---|
| T1 | 已完成 | reports/<task>/<batch>/evidence/A/A-001.log |
| T2 | 停下 | 见报回问题 1 |

新建文件：tests/xxx.test.ts
报回问题：
1. T2：要改 src/shared/date.ts（不在派工单里），因为 ……，打算 ……
集成时处理：
- spec 变更记录加一行：……
```

回执里的状态只用"已完成"和"停下"两种。"停下"不是验证失败，不走 x-fix，由主 agent 按第 8 步处理。

## 验收 agent 回执

按 x-verify-spec 和 x-verify-tech 各自的回执格式，范围写清是"组 A 的 T1、T2，分支 dev/<task>/A@<commit>"。x-verify-spec 按组对账时只对这些行判断覆盖和状态。主 agent 把回执收进这个 task 的统一测试报告。
