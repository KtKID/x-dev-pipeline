# 多 agent 协作开发

一句话：**主 agent 按 `xdev graph` 的批次把并行组派给工人子 agent；每组交回后主 agent 自己在这组分支上跑测试和覆盖率核对，不过就打回原工人；通过的组按依赖顺序合并；全部合并后整体跑一遍 x-dev 的覆盖率、交付核对和审查。**

独立性放在最后一道：整体审查的 reviewer 由 x-qa-gate 另派，和做开发的工人不是同一个 agent。每组不再单独派验收 agent，免得同一份代码审两次。

## 什么时候用

| 情况 | 怎么做 |
|---|---|
| checklist 有两个及以上并行组 | 用本文的流程 |
| 只有一个并行组 | 主 agent 自己按 x-dev SKILL.md 做完。想省主 agent 的上下文时，也可以派一个工人做完，这个工人同样遵守本文的「工人的规则」 |
| 环境里派不了子 agent | 主 agent 按 `xdev graph` 的批次一组一组自己做；每组的核对、合并和收尾规则不变 |
| x-qdev | 不用本文 |

## 两个角色

| 角色 | 由谁担任 | 做什么 | 不做什么 |
|---|---|---|---|
| 主 agent | 调用 x-dev 的 agent | 派单、核对每组、回写 checklist、合并、改共享文件、整体收尾 | 开发阶段不替工人写这组的代码 |
| 工人 | 子 agent，一组一个 | 按派工单做完这组的行，自己跑覆盖率补齐，交回执 | 不改派工单以外的文件，不写 checklist |

## 主 agent 的步骤

1. **开工前**
   - `xdev validate <task>` 必须通过。
   - `xdev impact <task>`：报"没有变化"才派单。报出变化时，按 [需求变化同步](../../x-tech-design/references/change-sync.md) 同步完（或确认只是措辞变化），再运行 `xdev baseline`。
   - `xdev start <task>` 记下代码基线，然后把 checklist 提交进主干，这样每组的分支都带着同一个代码基线。
   - 用 `xdev graph <task>` 取得派工批次。
2. **派单**：每组从当前主干拉一个分支 `dev/<task>/<组>`，能用 worktree 就给它一个独立 worktree，写派工单（见下）派给工人。同一批的组同时派；下一批等它依赖的组合并以后再派。派工记录里这组记为"已派出"。
3. **收回执、核对这组**：工人报"已完成"的行回写成 `[ ] 🟡`；报"停下"的行保持 `[ ] ⏳`，派工记录写"阻塞：<原因>"。然后主 agent 在这组的分支上**自己**运行（不照抄工人的结论）：

   ```bash
   xdev coverage <task> --cmd "<全量测试命令>" --report <报告> --out <task>/evidence/<组>/
   ```

   要求测试命令通过、这组分支相对代码基线的改动行覆盖率 100%，并且工人回执里的每个用例都指向真实存在的测试函数。派工记录记为"核对中"。
4. **核对不通过**：把 `xdev coverage` 的输出（失败的测试、没覆盖的 `文件:行`）交回**原来那个工人**，在它原来的会话里接着修，派工记录记为"修复中"。工人会话已结束时，用原派工单加这份输出重新派一个工人。每组各自计轮数，最多 3 轮；3 轮还不过，这组的行标 `[ ] ↗️`，停下这一组升级给用户，其他组照常进行。各组轮数记在派工记录里，不写 task 级的 `reports/.fix-counter`。
5. **合并**：核对通过的组记为"待合并"。按批次顺序一组一组合进主干，每合一组跑一次全量测试。
   - 通过：这组的行回写为 `[x] 🟢`，工人回执里的用例行抄进「结果 / 用例对应」表，派工记录记为"已合并"。行只有合并进主干并通过全量测试后才写 🟢。
   - 合并冲突或测试不过：看失败的测试属于哪一组的行。能定位到一组就打回那一组；定位不了时打回后合的那一组，附上失败输出。被打回的组在最新主干上重做，算一轮。
6. **共享文件**：工人回执里"集成时处理"的项（spec 变更记录、索引、依赖锁文件等），由主 agent 在每组合并后统一改。
7. **派工记录**：写在 checklist「结果」节下的「派工记录」表，每组一行：分支、工人、轮数、状态。状态只用：等待依赖、已派出、核对中、修复中、待合并、已合并、阻塞、已升级。中断后照这张表就能接着做。
8. **工人报回的问题**，主 agent 从下面四种处理里选一种：
   - **要改派工单外的文件，这个文件不属于别的组**：把文件补进这一行的"涉及文件"和影响文件树，重跑 `xdev validate` 和 `xdev graph`，更新派工单后让工人继续。这一行所在的组已经合并时，从最新主干为这一行单独派一次。
   - **要改的文件属于另一组**：两组不能同时改一个文件，按硬规则这一行要和那一组同组。把这一行的并行组改成那一组，文件补进涉及文件，重跑 `xdev validate` 和 `xdev graph`。那一组还在做：把这一行追加进它的派工单，由那一组的工人接着做；那一组已经交回或合并：等它合并后，从最新主干为这一行单独派一次。并组后 `xdev validate` 报依赖有环（DEP_CYCLE）时，把环里的组合并成一组，交给其中还在做的那个工人；合不了（比如环里有已合并的组）就停下这几行，升级给用户。
   - **需求或设计的问题**：交来源负责方（x-explore-for-spec / x-tech-design），改完按第 9 步处理。
   - **和本 task 无关的问题**：登记成后续任务。
9. **中途 spec 变了**：运行 `xdev impact`，按 change-sync 同步：受影响的行重开为 `[ ] ⏳`，需要的新行补进 checklist，然后 `xdev validate`、`xdev baseline`。只停受影响的行所在的组，其他组继续。受影响的组还没合并：原工人在原分支按更新后的派工单继续；已经合并：从最新主干新开分支重新派，这组轮数从 0 重新算。
10. **整体收尾**：所有组都合并后，主 agent 在主干上做 x-dev SKILL.md 的第 4–8 步：全量覆盖率、Web 与界面验收、测试真实性检查（对整个 task 新增和改动的测试做一次）、`xdev check`。`xdev check` 通过后按 risk 走：Q0 直接把行升为 `[x] ✅` 并交付；Q1、Q2、Q3 都交 x-qa-gate。给用户的回执放在最后。
11. **整体审查发现问题**：整个 task 一份问题清单交 x-fix，由主 agent 执行 x-fix（已过开发阶段，不再分组派工），按 task 级 `reports/.fix-counter` 计轮数。

## 派工单模板

```text
派工单 · <task> · 组 <A>
- 分支：dev/<task>/A（基于 <commit>，checklist 里已有代码基线）
- 任务行：T1、T2（按行序做）
- 只许改的文件：<这些行"涉及文件"的并集>；可以新建这些行自己用的测试文件
- 证据目录：<task>/evidence/A/（只写这一组的原始输出）
- 依据：<spec 路径>、<tech-design 路径>；要通过的用例：T1、T2 …
- 测试与覆盖率：xdev coverage <task> --cmd "<全量测试命令>" --report <报告> --out <task>/evidence/A/，交回前要 100%
- 不许碰：checklist、spec、tech-design、变更记录和索引
- 交付：按「工人回执」格式
```

## 工人的规则

工人开工前先读自己这几行要用的依据：回指场景的正文、适用的 C、tech-design 里的 D 和用例主定义，确认涉及文件存在。然后按 x-dev SKILL.md 第 2、3 步的逐行开发规则做（先写测试、有效红灯、不 mock 掉被验证的机制、失败按根因修），做完按派工单跑覆盖率，没覆盖的行补测试直到 100%，再加上下面这些。

**这些事工人不做，由主 agent 做**：回写 checklist（状态列、结果节）、运行 `xdev start` / `xdev baseline` / `xdev check`、派测试真实性检查、Web 与界面验收、给用户的回执。工人写测试同样遵守 x-dev SKILL.md「测试是硬规则」。工人把每行的状态、用例对应和证据写在自己的回执里。

| 遇到的情况 | 工人怎么做 |
|---|---|
| 改派工单里列出的文件 | 正常改 |
| 要给自己这几行新建测试文件 | 可以建，回执里列出来 |
| 写测试的原始输出 | 只写派工单给的证据目录 |
| 要改派工单以外的文件（哪怕只改一行） | 不改。停下这一行，报回：要改哪个文件、为什么、打算怎么改 |
| 覆盖率没到 100%，缺的行在派工单以外的文件里 | 不改那个文件，报回 |
| 发现 spec 或 tech-design 有问题（写错、缺用例、和代码冲突） | 不自己补设计。停下受影响的行，报回 |
| 发现别的组范围内的 bug | 不修，记进回执的"报回问题" |
| 要改共享文件（spec 变更记录、索引、依赖锁文件） | 不碰，写进回执的"集成时处理" |
| 同一行失败多次，原因不清楚 | 不改目标、不降低断言，停下这一行报回 |
| 停下了一行，但同组的其他行不依赖它 | 继续做其他行 |
| 一行验证通过了 | 不改 checklist，在回执里报这一行"已完成"，列出它的用例对应 |

## 工人回执

```text
组 A · 分支 dev/<task>/A@<commit> · 覆盖率 ✅ 100%（记录 <task>/evidence/A/coverage.json）

| 行 | 状态 | 说明 |
|---|---|---|
| T1 | 已完成 | |
| T2 | 停下 | 见报回问题 1 |

用例对应：
| 用例 | 测试位置 | 层级 | 结果 |
|---|---|---|---|
| T1 | tests/test_borrow.py::test_borrow_ok | unit | 通过 |

新建文件：tests/test_borrow.py
报回问题：
1. T2：要改 src/shared/date.py（不在派工单里），因为 ……，打算 ……
集成时处理：
- spec 变更记录加一行：……
```

回执里的状态只用"已完成"和"停下"两种。"停下"不是验证失败，不走 x-fix，由主 agent 按第 8 步处理。
