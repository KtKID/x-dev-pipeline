# 当次代码改动测试报告

开发、修复与验收共用本约定。每个任务的一次交付代码基线维护一份 `test-report.md`，集中呈现用例明细、改动覆盖率、未覆盖位置和验收结论。用例预期回指需求/设计的主定义，实际结果来自本轮执行与观察。

## 产物与写入责任

默认放在项目根目录的 `reports/<task-name>/<batch-id>/`；`batch-id` 沿用项目已有运行编号，或使用时间加序号。任务同名时用所属 spec/模块限定目录。项目已有等价报告位置时沿用，并在任务记录中给出唯一入口。

```text
reports/<task-name>/<batch-id>/
├── test-report.md          # 本次改动的唯一测试阅读入口
└── evidence/
    ├── execution.log       # 按执行编号集中保存命令、元数据和原始输出
    └── coverage/           # 覆盖工具的原生数据文件
```

采用 [测试报告模板](../templates/test-report.md)。常规任务的 `dev-report.md`、qdev 的⑤仅保存简短结论、报告链接、交付状态和未决项索引。技术验收与 QA 返回增量回执，由主 agent 收录到同一报告；独立技术验收负责建立或更新该报告，受只读委派约束时返回待收录内容及附件位置。每个任务由主 agent 统一维护入口和报告正文。

同一交付基线下，开发、技术验收、复审的独立执行分配不同执行编号，共用报告和附件目录。代码、设计或相关输入变化后，进入下一轮交付验证时按新基线建立批次并重跑受影响检查；已有批次保留历史事实，可复用记录注明原批次、基线及适用依据。红灯、修复与最终验证各执行记录保留自己的代码/输入基线，覆盖率对应本次交付版本。调查结论与后续设计放所属文档位置，报告通过链接引用。

## 报告内容

开头说明任务、比较基线、交付版本、实际测试范围、通过/失败/跳过/未执行数及关键缺口。任务行数、需求场景数、用例数与框架执行数分别统计。

完整列出本轮范围内的专项、回归、人工检查和技术验收用例。以测试清单和实际执行明细交叉核对；参数化用例说明各组输入与结果，长回归列表按功能折叠。共同准备、预期和已有完整用例过程使用主定义链接，报告填写本轮实际差异与结果。同一用例复跑沿用 ID 与明细行，关联各执行编号及结果；交付结论采用当前交付基线的有效记录。

每条用例写清：

- **目的与依据**：日常语言名称、用例 ID、需求/设计主定义和测试位置。
- **准备与操作**：实际数据、初始状态、输入、边界参数及执行方式。
- **预期与实际**：可观察预期、实际观察、通过/失败/跳过/未执行/缺证据状态及原因。
- **改动关联与来源**：关联的改动文件/位置、映射依据、执行编号和附件定位。需求映射、代码审查推定与运行时逐例覆盖分别标识。

汇总输出仅支持汇总结论时，逐例观察明细列为待补资料。验收节保存实际回执、读过的来源、适用范围、基线、复用/本轮执行区别和未决项；技术约束通过用例 ID、代码位置和执行编号关联已有明细。

## 当次改动覆盖率

每次代码修改都采集并报告改动覆盖率，优先使用项目测试框架和已安装运行时工具，覆盖阈值沿用项目或用户约定。变更清单列全本次任务涉及的文件；测试文件、生成文件等按项目已有规则说明计入、排除及适用性依据。

1. **确定比较范围**：优先使用用户指定的比较基线；否则保存任务开始前的可读代码基线，并对照最终交付版本。记录提交、工作区差异及相关未跟踪文件内容，区分任务开始前已有改动与本次改动。附件保留可读取的本次 diff/快照或可恢复的版本引用，哈希与具体内容对应。
2. **对齐执行版本**：原始覆盖率对应最终被测代码和测试选择；记录工具、采集命令、范围、排除项及依据。转译代码通过 source map 或工具提供的映射定位回修改源码；映射缺失列为未核实。
3. **统计改动行**：以 diff 新版本侧的新增/修改行，与覆盖工具识别的可执行行取交集。逐文件列已覆盖/改动可执行行数及百分比；整体按行数求和后计算。新增文件纳入范围，重命名记录前后路径，删除内容列出移除行为与回归验证。纯文档、纯删除等零可执行改动标明“不适用：0 个改动可执行行”及依据。
4. **统计相关分支**：按工具可定位的、与改动行/条件相交的分支列已覆盖/总数、百分比和未命中出口；标明筛选口径。工具提供整文件分支数据时单列范围，改动分支范围无法定位的部分标未采集。
5. **列出缺口**：逐项给出未覆盖文件、具体源码行/分支、对应行为、风险及补测动作。受测文件缺失于覆盖数据、工具不可用、范围或 source map 缺失分别列为未采集/未核实，保持缺口可见。只覆盖部分文件时显示已采集部分及待采集文件，整体覆盖率标未核实。全文件覆盖率作为补充统计，报告主指标采用本次改动范围。

报告默认标“本批测试合计”。逐用例覆盖归属采用工具支持的逐例采集，或按明确用例分别运行并隔离原始数据；记录实际选中/执行/跳过数及初始化、清理计入的边界。用例关联来自设计或测试位置时按该依据展示。

覆盖率度量代码执行范围，功能结论结合预期结果检查。覆盖率缺口与违反既有阈值分别列明；采集缺失记为证据缺项，按相关验收项判未完成/未验证。零可执行改动的任务仍提供测试/检查报告与适用性依据。

## 原始证据集中留存

`evidence/execution.log` 按执行编号记录时间、阶段、命令或人工步骤、工作目录、代码/输入基线、退出码、实际执行/通过/失败/跳过数和原始输出。红灯原因或实际取证理由、替身边界、环境限制和浏览器观察同时留存。静默检查记录“标准输出/错误输出为空”及实际退出码。

覆盖率原始数据放 `evidence/coverage/`，保留工具原生名称与格式；批次内多次采集使用执行编号区分，报告标明对应范围及采用哪次数据。项目已有机器记录可以替代集中日志中的相同内容，统一在附件索引定位。同一输出共用来源，每次独立复跑各有执行记录。使用真实输出填报。

回放输入、截图、轨迹和 HTML 等专项材料按功能要求放附件；已有固定路径或敏感资料存放约定时保持原位置，在附件索引引用。修复报告保留根因和逐条处置，测试内容链接到统一报告的用例/执行记录。

## Web 浏览器验收

`x-dev` 和 `x-qdev` 的 Web 任务在实现后、交付前由 agent 亲自使用浏览器验证。打开运行本次改动的版本，操作受影响的关键流程并按验收条件核对实际结果。后端改动影响 Web 页面时也验证对应的页面操作。仅提供 Web API 的需求可在浏览器中发起请求并核对响应。

发现验收问题就修复，再用修复后的版本操作失败场景和受影响的流程。最终交付版本验收通过后，截取能展示本次变化的页面或操作结果。在执行记录中留存页面地址、操作步骤、实际结果与复验记录，截图存入附件并在测试报告中引用。浏览器验收或截图交付受阻时，记为未完成并说明具体原因。

## 复查责任与兼容

- **x-verify-spec**：读取唯一测试报告及逐例关联的附件，共同来源读取一次；核对需求映射、完整用例数量、基线、执行结果、改动覆盖率统计与缺口。返回对账回执。
- **x-verify-tech**：对照设计阅读代码与测试，实际运行相关检查；把本轮用例/执行增量和设计约束结论交由主 agent 收录同一报告，核对改动覆盖率的采集版本、范围和未覆盖位置。
- **x-qa-gate**：按既有风险路由审查测试发现错误实现的能力，引用同一报告及相关原始附件，返回审查回执。

历史任务按原交付约定和已有资料核对。本轮新增交付采用统一报告；历史 `dev-report`、qdev⑤与旧 verify 块仍作为已有来源读取。旧 `spec_version: 3` 的可执行 verify 块保留原消费位置，执行结果和原始证据汇入本次测试报告与附件。
