# 测试报告与证据复查

开发与验收共用本约定。常规任务的 `dev-report.md` 是用户阅读入口；qdev 在任务文档⑤提供同样内容。技术验收报告列出本轮实际检查。用例预期仍由需求和设计主定义提供，报告用日常语言说明实际执行过程。

## 用户阅读部分

开头说明本次验证了什么、通过/失败/跳过/未执行各多少、还缺什么。任务行数、场景数、测试执行数分别统计。

完整列出本次范围内的全部测试用例，包括专项、已有功能回归及人工检查。以测试清单和实际执行明细交叉核对完整性；参数化用例说明各组输入、操作和结果，框架展开数另列。长回归列表可以按功能折叠，保持逐例可读。已有历史记录缺少完整明细时明确列为待补资料。

每条至少包含：

- **测试什么**：日常语言名称；原用例 ID 和来源保留为定位信息。
- **怎样测试**：准备什么数据或状态，实际执行哪些操作、输入及边界参数；区分自动测试、浏览器人工操作和代码审查。
- **应该看到什么**：从主定义引用的可观察结果。
- **实际看到什么与结论**：真实观察和通过/失败/跳过/未执行/缺证据状态；失败、跳过及局限写清原因。
- **复查入口**：对应测试位置和执行记录；一份共同日志可供多条用例引用。

例如：“先提交一次密码，记录为1条；刷新页面后仍为1条；再提交密码变为2条。自动测试通过。”准备、操作、观察均依据实际代码和记录；历史汇总只支持汇总结论时写明观察明细待补。

## 覆盖率

项目已有覆盖率要求或用户要求统计时，用项目测试框架及运行时覆盖率工具实际采集。用户部分按文件列出行覆盖率、分支覆盖率、未覆盖位置及统计范围；写清全文件或本次变更范围、分子/分母、基线和排除依据。详细语句/函数计数与原始数据可放附件。覆盖率说明代码执行范围，功能结论结合预期结果检查。

整批运行报告标明“本批测试合计”。需要“每个用例→每个文件”时采用工具支持的逐例采集，或按明确用例筛选分别运行并隔离结果目录；记录实际选中/执行/跳过数，以及初始化和清理也被计入的边界。聚合报告只提供本批合计数据。

## AI 复查附件

沿用项目已有执行记录与附件格式，保存命令、工作目录、代码/输入基线、退出码、实际测试数量、关键输出及来源。红灯原因、替身边界、环境限制和浏览器观察同样保留。

静默成功的检查在执行记录中明确写“标准输出/错误输出为空”及实际退出码。单独空日志的信息有限，复查以对应执行元数据为依据；元数据也缺失时列为缺证据。占位文件待取得实际结果后填写；同一输出共用一份来源，复用记录注明复用，独立复跑保存各自执行来源。

复查责任：

- **x-verify-spec**：核对完整用例列表、需求映射与数量；实际打开每条关联的执行记录，共同日志读取一次，核对结果、失败/跳过项与基线。已有覆盖率报告同时核对逐文件数据、统计范围与报告数字。保持记录对账职责。
- **x-verify-tech**：对照设计阅读代码与测试，实际运行本轮相关检查；检查测试观察覆盖了待验证机制，按适用要求复查覆盖率来源和范围。
- **x-qa-gate**：依既有风险路由审查测试能否发现错误实现，并核对相关原始证据。

各环节回执说明实际读过的记录、核查范围、发现的缺口及复用/本轮执行的区别；读取与运行情况按事实报告。历史缺项按原任务约定与实际资料判定，本轮新增交付遵守上述完整清单要求。
