# 测试真实性检查

一句话：**覆盖率只能说明代码被跑到了，不能说明测试真的在测。** 所以测试写完、覆盖率到 100% 之后，主 agent 派一个轻量子 agent，只读本次新增或改动的测试，看有没有弄虚作假或偷懒。它不看需求写得对不对（那是审查的事），只回答一个问题：

> 如果生产代码被改错了，这些测试会不会变红？

会变红的才是真测试。

x-dev、x-qdev 都用。多 agent 协作时，全部合并后由主 agent 对整个 task 做一次，工人不做。

## 什么时候做

1. `xdev coverage` 通过（全量测试全绿、改动行覆盖率 100%）之后，`xdev check` 之前。
2. 改过测试以后，覆盖率记录和真实性记录都作废：先重跑 `xdev coverage`（新测试也得是绿的），再重新检查。这包括真实性检查发现问题后改的测试，也包括审查回流时 x-fix 改的测试。代码基线变了（需求变化同步后重新 `xdev start`）也要重新检查。`xdev check` 会发现记录过期。

## 派谁、给什么

- 用当前环境里最便宜、最快的模型（如 haiku），新开一个子 agent，不带主 agent 的对话历史，只跑一个 turn，只读，不改文件。
- 主 agent 一次给全输入：
  - 要检查的测试文件：和代码基线相比改过的、加上新建还没提交的测试文件。算不算测试文件按路径判断：路径里有 `tests/`、`test/`、`__tests__/`、`spec/`、`fixtures/`、`testdata/`，或文件名形如 `test_*`、`*_test.*`、`*.test.*`、`*.spec.*`、`conftest.py`，并且是代码文件。fixture 和 conftest 也要交给子 agent。拿不准就以脚本为准：不带 `--receipt` 运行 `xdev integrity`，有测试改动时它会报错并列出完整清单。
  - 这些测试的 diff：`git diff <代码基线> -- <测试文件>`。
  - 它们要测的生产代码：用例对应表里每个用例所在行的「涉及文件」。
  - 用例对应表，以及 tech-design 里这些用例的预期结果（qdev 是③）。
  - 本文件的「检查清单」和「回执格式」两节原文。
- 回执原样存为证据目录里的 `test-integrity.md`，然后运行 `xdev integrity <task> --receipt <证据目录>/test-integrity.md`。

## 检查清单

对每个测试函数，先找出它调用了项目里的哪个函数、类、接口或命令，再按下表逐项看。命中任何一项就是问题，问题类型只用表里的名字。

| 问题类型 | 是什么 | 典型样子 |
|---|---|---|
| 重写了生产逻辑 | 测试调用了项目代码，但期望值是照抄业务规则算出来的（哪怕用的是从生产代码 import 的常量），或者测试里另写了一份规则拿来对比 | `expected = days * 0.5` 或 `expected = days * DAILY_FINE` 照抄罚款公式；测试里自己写了一个 `calc_fine()` 再和生产结果比 |
| 没调用项目代码 | 测试根本没调用项目里的被测函数：测的是测试文件里自己定义的函数、复制进来的类，或一个和项目无关的替身（这种情况归这一类，不归“重写了生产逻辑”） | 把生产函数复制到测试文件里测；import 的是测试目录下的同名模块 |
| 绕过要测的流程 | 调了项目代码，但跳过了场景要验证的入口或步骤 | 场景是“借第 6 本被拒”，测试直接往数据库写 6 条借阅记录再查，没调借书入口；直接调内部私有函数，跳过了校验 |
| mock 掉了被测对象 | 被测函数本身，或 tech-design 要验证的 D 机制，被 mock 或打桩了 | `patch("loan.borrow.check_limit", return_value=False)` 之后测借书被拒 |
| 只断言调用不断言结果 | 只检查“被调用了”“没报错”“不是 None”，没检查场景要的结果 | `mock.assert_called_once()`；`assert result is not None`；整个测试没有断言 |
| 断言恒真 | 期望值来自被测代码自己，或者无论实现对错都成立 | `assert f(x) == f(x)`；期望值由同一次调用得出；断言 `len(xs) >= 0` |
| 吞掉失败 | 失败被藏起来了，测试永远绿 | `try: ... except: pass`；`skip` / `xfail`；`if result:` 包着断言；中途 `return` |
| 数据测不出对错 | 选的数据让错误的实现也能通过 | 上限是 5 本，测试只借 2 本；边界场景没测边界值；期望值恰好等于默认值 |

**不算问题**（不要报）：

- mock 网络、时钟、随机数、第三方服务，或者被测函数下面的存储层、数据库访问，只要被测的那个函数本身真实运行，断言的是它的结果。
- 用测试工具函数或 fixture 准备输入数据。
- 期望值是手写的常量（如 `assert fine == 1.5`），这正是推荐写法。
- 同一个场景拆成几个小测试分别断言。

拿不准时，在心里做一次“改坏试验”：把生产代码里相关的判断删掉，或者把返回值改错，看这个测试还会不会通过。会通过，就是问题。

## 回执格式

```text
测试真实性检查回执 · <task> · 结论：通过 / 不通过
已检查：<每个测试文件的路径，用顿号分隔>（共 N 个测试函数）

| 测试位置 | 问题类型 | 证据 | 怎么改 |
|---|---|---|---|
| tests/test_fine.py::test_fine_amount | 重写了生产逻辑 | tests/test_fine.py:12 `expected = days * 0.5` | 期望值写成手算的常量 1.5 |

穷尽声明：已检查范围内没有其他问题。
```

没有问题时，表格只留表头，结论写“通过”。“已检查”必须列出主 agent 给的每个测试文件，写完整路径，用顿号分隔，`xdev integrity` 会逐个精确核对。问题表格的第一列标题必须是“测试位置”。

## 主 agent 怎么处理

- **通过**：`xdev integrity` 记下回执和当时测试文件的版本，接着跑 `xdev check`。
- **不通过**：主 agent 按“怎么改”修测试。只改测试，不为了让测试好写去改生产代码；测试暴露出生产代码真有错，就按 x-dev 第 3 步修实现。修完重跑 `xdev coverage`，再派一个新的轻量子 agent 检查一遍，最多 3 轮；3 轮还不过就停下，告诉用户卡在哪。
- **认为某条报错了**：不改测试，在「问题与处置」写一行 `测试真实性 · <测试位置> · 不采纳：<理由>`。必须写在同一行，测试位置和回执表格里的一字不差（包括 `::函数名`）。回执里每条问题都有“不采纳”记录时，`xdev integrity` 也认为通过，理由留给审查判断（Q0 没有审查，所以要格外慎重）。
