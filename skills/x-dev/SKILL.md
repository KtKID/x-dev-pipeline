# x-dev — task 执行

## 输入与边界

作用域是**单个 task**：`docs/spec/<spec-name>/tasks/<task-name>/`，入口是 `dev-checklist.md`，按头部 `spec:` 与 `tech-design:` 跟读相关场景、已确认的 C 约束、D 机制和编号用例。一次只做指定 task，不扫描或编排同级 task。checklist 有两个及以上并行组时，按 [多 agent 协作开发](references/parallel-dev.md) 派给工人子 agent；被派为工人时，也按那份文件里工人的规则做。状态与写权见 [执行规则](references/execution-rules.md)。

交付只有一份文件：`dev-checklist.md`。开发结果写在它末尾的「结果」节，原始输出（测试日志、覆盖率记录、截图、人工验证记录）放同目录 `evidence/`。不另写 dev-report 和测试报告。声明 `spec_version: 3` 的旧契约包仍用 `templates/dev-report-template.md`。

本轮承接的 D 机制或用例主定义缺失、有等待用户拍板的取舍时，受影响行阻塞并交来源负责方补齐，不从实现猜设计。项目有 [架构偏好](../x-tech-design/templates/architecture-preferences.md) 文件（默认 `docs/architecture.md`）时，实现遵守它；做不到就停下问用户，不悄悄绕开。

checklist 的约定（由 x-req 生成）：

- **按并行组和依赖执行**：同组内行序即实现顺序；组之间按依赖先后，`xdev graph` 给出派工批次。只有一组时从 T1 开始逐行往下做。
- **场景回指定验收**：一行做完 = 它回指的每个场景的 THEN 及适用 C 约束的预期/禁止结果都有测试证明。任务列的“用例 T1”回指 tech-design，不要和任务行 T1 混淆。
- **风险列为 `高:` 的行**，用例里至少一条是真实链路（smoke、集成或 e2e），不能只有 unit。
- 改动落在「涉及文件」范围内，不"顺便"改别的。

下文的 `xdev` 指 `python3 <本 skill 目录>/scripts/xdev.py`。

## 执行

1. **开工**：一次读完 checklist、被回指的场景与 C、tech-design 的 D 和用例、涉及的实现与测试文件。依次运行：
   - `xdev validate <task>`：报错先修 checklist 或交回 x-req。
   - `xdev impact <task>`：报出需求变化时，按 [需求变化同步](../x-tech-design/references/change-sync.md) 核对它列出的 D、T、任务行是否已同步；没同步的行不开工，交回来源负责方；已同步或只是措辞变化，运行 `xdev baseline <task>`。
   - `xdev start <task>`：把当前 git HEAD 记为「代码基线」（已有就不动），建 `evidence/`。需要 git 仓库且至少有一个 commit；没有就先 `git init` 并提交现状。之后的覆盖率都和这个基线比。开工前已有的未提交代码改动会算进本次改动，它会提示出来。
2. **逐行开发**（多 agent 协作时状态列由主 agent 按工人回执回写，工人不改 checklist）：
   - 当前行改为 `[ ] ▶️`。
   - 按场景 THEN 与用例的预期/禁止结果写测试，先跑，确认失败是因为目标行为还没有（有效红灯）；构建、导入、环境或测试本身的错误不算，先排除。不得 mock 掉被验证的 D 机制。
   - 写实现让测试变绿，改动留在涉及文件内。不能为了通过改低断言或验收标准；需求或设计有问题交来源负责方，改完按需求变化同步处理受影响的行。
   - 不能自动化的，写清原因、步骤和实际看到的结果，存成 `evidence/manual-<用例>.md`，结果记“人工通过”。既有实现已满足的，跑一遍对应用例留证据，不伪造红灯。
   - 在「结果 / 用例对应」表登记这一行的每个用例：`用例 | 测试位置 | 层级 | 结果`，测试位置写到函数（如 `tests/test_loan.py::test_sixth_rejected`）。行改为 `[x] 🟢`。
3. **行失败时**：读完整输出，按根因一次修完所有关联位置。发现是测试写错就改测试，并在「问题与处置」记一行原因。同一行失败多次不改目标，回看场景定义，仍不清楚就停下问用户。失败中的行标 `[!] 🔴`，修好恢复。
4. **覆盖率**：全部行 🟢 后运行

   ```bash
   xdev coverage <task> --cmd "<全量测试命令，会生成覆盖率报告>" --report <报告路径>
   ```

   它会真的跑测试命令（日志存 `evidence/`），再读报告，算出“和代码基线相比改动过的代码行，有几行被测试跑到”。测试文件和文档不算。不到 100% 时它列出 `文件:行`，退出码 1：给这些行补测试（补的测试也要登记到用例对应表），再跑，直到 100%。报告里完全没有的改动文件也算没覆盖，通常是测试没加载它，或覆盖率范围没配到；没有覆盖率工具的语言（如 Shell）怎么处理见证据约定。确实跑不到的防御代码，用语言自带的排除标记（如 Python `# pragma: no cover`）并在「问题与处置」写一行 `文件路径:行 理由`（`xdev check` 按文件路径找这行），交给审查判断。各语言生成报告的命令见 [证据约定](references/test-reporting.md)。
5. **Web 与界面**：涉及 Web 的任务，agent 亲自在浏览器操作实际功能，有问题就修复复验，通过后截图；其他界面改动打开最终版本截图。截图放 `evidence/`，做法见 [证据约定](references/test-reporting.md#web-与界面验收)。代码因此改了就重跑第 4 步。
6. **交付核对**：运行 `xdev check <task>`。它逐项核对：编号和结构、需求变化已同步、每行 🟢、每个本轮场景都有通过的用例、每个用例都对应到真实存在的测试函数、高风险行有真实链路用例、测试命令通过且覆盖率 100%、覆盖率跑完后代码没再改。退出码 1 就按它列的问题修，修完从第 4 步重来。
7. **验收**：`xdev check` 通过后按头部 `risk` 走：Q0 由主 agent 把行升为 `[x] ✅`（`reports/.fix-counter` 存在时写回 0）；Q1/Q2/Q3 交 [x-qa-gate](../x-qa-gate/SKILL.md) 做一次独立审查。多 agent 协作时回执放到整体验收之后，见 [多 agent 协作开发](references/parallel-dev.md)。最后报告下一步（同 spec 的下一个 task，或全部完成）。

## 回执

最终回复先用大白话交代下面几件事，再附验证状态和 checklist 链接。假设用户没读过代码，用短句讲具体动作和结果，必要的术语就地解释。

- **完成了什么功能**：用户现在能做什么、在哪操作、会看到什么变化。
- **改了哪些文件**：附链接，按文件简述它负责什么；列出新增或改动的核心函数（保留真实函数名），一句话讲清每个做什么。纯配置、样式改动说明文件作用即可。
- **验收截图**：Web 和界面改动附最终截图，说明每张图对应的页面或操作结果；不能显示图片时给链接。受阻时说明原因和待补事项。

```
✅ x-dev 完成 · <task-name> · 行 N/N 🟢 · 场景 M/M 有用例 · 改动行覆盖率 100%（K 行）· xdev check 通过
```

有阻塞或失败残留时如实列出：行号、失败摘要、已尝试的动作、需要用户决定的问题。
