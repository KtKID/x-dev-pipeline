# x-dev — task 执行

## 输入与边界

x-dev 的作用域是**单个 task**：`docs/spec/<spec-name>/tasks/<task-name>/`，入口是它的 `dev-checklist.md`，按头部 `spec:` 与 `tech-design:` 指针跟读相关 feat、场景、已确认关键约束和编号测试用例的主定义。一个 spec 下可以有多个 task，x-dev 一次只执行指定 task，不扫描或编排同级 task。

旧 checklist 缺设计指针时查 spec 同目录的 `tech-design.md`；本轮承接的机制或用例主定义仍缺失/未确认时，受影响行阻塞并交来源负责方补齐，不从实现猜设计。既有 spec 未使用 C 或 feat/场景编号时沿用其已确认约束、场景 ID/章节定位，不强制迁移编号；没有新增适用关键约束的旧行仍按原场景和证据核对，不伪造 C。

checklist 的约定（由 x-req 生成）：

- **行序即实现顺序**，无依赖图；从 T1 开始逐行往下做。
- **场景回指定验收**：一行做完的判定标准是它回指的每个场景的 GIVEN/WHEN/THEN 及适用 C 约束的预期/禁止结果全部成立；任务列的“用例 T1”回指 tech-design，不能与任务行 T1 混淆。
- **风险列为 `高:` 的行**，验证必须包含真实链路（smoke 或以上），不允许只写 unit。
- 改动落在「涉及文件」范围内，不"顺便"改别的。

## 执行

高能力模型按批次执行：独立读取放同一批次；文件只在内容变化后重读；过程更新只报告新进展或阻塞。

1. **取证批次**：一次读完整 checklist、spec 中被回指的 feat 场景与 C 约束、tech-design 的 D 机制及编号用例、涉及的实现与测试文件，建立「场景/C → D/用例 → 代码/证据」的对应关系；发现缺定义、覆盖或确认先报告来源负责方，不从实现补验收标准；顺带确认涉及文件路径真实存在（x-req 留了 glob 的就在此批次定位）。按 [共用报告约定](references/test-reporting.md) 保存任务开始前的比较基线与既有工作区边界，确定唯一测试报告入口。
2. **逐行开发**（适合自动化的新行为先测试后实现）：
   - 把当前行状态改为 `[ ] ▶️`。
   - 按场景 THEN 与用例的预期/禁止结果写测试，先跑并证实失败来自目标行为缺失或违约（有效红灯）；构建、导入、环境或测试自身错误不是有效红灯，先排除后重跑。不得 mock 掉被验证的 D 机制；其他替身说明边界与局限，故障注入保留真实处理路径。
   - 有效红灯后写实现，让测试变绿，改动保持在涉及文件范围内。不能为了通过改低断言、排除项或验收标准；需求/设计有问题交来源负责方澄清，变更后重新对齐用例和证据。
   - 不可自动化时记录原因、可复现步骤与实际观察；既有实现已满足时先运行相应用例并保留通过证据，直接补缺失覆盖。集成验证行只验证结果；这些情况不伪造 TDD 或故意破坏实现造红灯。证据不足的行不能标绿。
   - 验证通过后行状态改为 `[x] 🟢`。统一测试报告记录实际取证理由、最终结果及执行编号，原始输出集中保存在附件；dev-report 同步简短结论与链接。
3. **行失败时**：读完整输出，按根因一次修完全部关联位置；发现是测试写错就改测试并在 dev-report 未决节记一行原因。同一行失败多次不改目标——回看场景定义，仍不清楚就停下来问用户。失败中的行标 `[!] 🔴`，修复后恢复。
4. **收尾验证**：全部行 🟢 后，涉及 Web 的任务由 agent 亲自在浏览器中操作实际功能，发现问题就修复并复验，通过后截取最终效果。按[浏览器验收约定](references/test-reporting.md#web-浏览器验收)记录结果和截图。然后跑一次本 task 全量测试 + 一次既有测试回归，按共用约定采集当次改动行及相关分支覆盖率。用例明细、未覆盖位置、采集缺口与结论集中写入测试报告，dev-report 同步交付摘要。
5. **交付**：确认 checklist 无 🔴 残留，按[回执](#回执)向用户说明完成的功能和改动。Web 任务须通过浏览器验收并在回执附上最终效果截图，两项齐备才标记完成。报告下一步（同 spec 的下一个 task，或全部完成）。

## dev-report

`docs/spec/<spec-name>/tasks/<task-name>/dev-report.md` 按 `templates/dev-report.md` 保存交付摘要、状态、未决项索引和唯一测试报告链接。完整用例明细、当次代码改动覆盖率、未覆盖位置及后续验收回执统一写入 [测试报告](templates/test-report.md)，存放与原始附件遵循 [共用报告约定](references/test-reporting.md)。

## 自检（交付前）

- checklist 每个非 `None` 场景回指都有对应测试且行状态 🟢？
- 每条适用 C 及分配用例都有实际结果与证据，未把正常路径全绿当成全部约束覆盖？有效红灯/不采用 TDD 的理由可核查，未 mock 掉被验证机制？
- 高风险行有真实链路验证？
- 全部改动都在「涉及文件」范围内？
- 既有测试回归通过？
- Web 任务已在浏览器操作并通过验收，回执已附最终效果截图？
- 唯一测试报告包含完整用例明细、当次改动行/相关分支覆盖率和具体未覆盖位置？未采集项与零可执行改动的适用性如实列明？原始证据集中在附件，静默检查有执行记录及退出码？
- 每个 🔴 行都在 dev-report 未决节有一行摘要？

## 回执

在最终回复里先用大白话交代以下内容，再附验证状态和报告链接。假设用户没读过代码，也不熟悉技术名词。用短句讲具体动作和结果，必要的术语就地解释。

- **完成了什么功能**。说清用户现在能做什么、在哪操作或会看到什么变化。
- **改了哪些脚本或代码文件**。附文件链接，按文件简述它负责什么。列出本次新增或改动的核心函数，保留实际函数名，用一句话讲清每个函数做什么。纯配置、样式等改动说明文件作用即可。
- **验收截图**。Web 任务附上浏览器验收通过后的截图。其他界面调整附上实际运行后的截图。在最终回复中展示截图，载体无法显示图片时提供可打开的截图链接，并说明每张图对应的页面或操作结果。截图按[共用报告约定](references/test-reporting.md#原始证据集中留存)存入测试报告附件。浏览器验收受阻或截图暂时无法取得时，交代原因和待补事项。

```
✅ x-dev 完成 · <task-name> · 行 N/N 🟢 · 场景覆盖 M/M · 高风险行 K（已验证）· 回归通过
```

有阻塞或失败残留时如实列出：行号、失败摘要、已尝试的动作、需要用户决定的问题。
