# 模式 2：CR 报告修复

> 当用户提供了仓库级或 task 内 CR 报告，或明确提到"按 CR 报告修复"时执行。
> 严格按以下步骤执行，不可跳步。

## 步骤 1：定位报告

报告查找优先级：
1. 用户在指令中显式指定路径 → 直接使用
2. 当前目录属于 `docs/spec/<spec>/tasks/<task>/` 时，读取该 task 的 `reports/cr/` 下最新报告
3. 当前仓库 `reports/cr/` 下最新的 `cr-report-*.md`
4. 兼容历史 `dev-pipeline/tasks/<task>/reports/cr/` 和当前工作目录中的旧报告

**无报告时**：立即停止，输出：
```
❌ 未找到 CR 报告，请先运行 x-cr 生成报告。
```

报告 schema：

- `> Schema: x-cr-v2`：要求包含“不变量覆盖”“审查结论”“问题详情”，按 Bn/INV-ID 解析。
- 历史报告：包含“审查结论”和“问题详情”，按旧表格兼容解析，并把缺少 INV-ID 记录为 `legacy-unmapped`。

x-cr-v2 报告先运行：

```bash
python3 skills/x-cr/scripts/validate_report.py <CR_REPORT_PATH>
```

校验失败时停止，返回校验器列出的结构错误。历史报告继续走兼容解析。

**两种 schema 都不满足时**：立即停止，输出：
```
❌ 报告结构不符合预期，无法解析（x-cr-v2 需要"不变量覆盖"、"审查结论"和"问题详情"；历史报告需要"审查结论"和"问题详情"）。
```

---

## 步骤 2：解析问题清单

1. 扫描「审查结论」各 P 级表格，收集状态为 ❌ 或 ⚠️ 的问题行
2. x-cr-v2：验证每个 Bn 唯一且恰好对应一个 `### Bn:`；历史报告按文件位置和描述关联既有 Bn
3. 提取严重程度、INV-ID、文件:行号、置信度、根因分类和问题描述；历史缺失 INV-ID 时填 `legacy-unmapped`
4. x-cr-v2：从「不变量覆盖」读取对应规则、来源、触达路径、最小反例和结论
5. 建立 Bn、INV-ID 和问题详情映射，并在计划中标记 legacy 项

**已含 `✅已修复` / `➖无需修复` / `⏭已跳过` 标记的条目**：跳过（已被之前的 x-fix 处理过）。

---

## 步骤 3：确定处理范围

- **P0 / P1**：处理
- **P2 可执行缺口**：报告给出明确测试、日志、文档或代码动作时处理
- **P2 待确认 / 来源冲突**：暂停该条，向用户列出需确认的权威规则
- **历史 P1.5 / P3**：P1.5 按 P1 处理，P3 保持跳过

---

## 步骤 4：汇报计划

修复前向用户汇报：

```
📋 修复计划

将处理：
- B1 (P0) xxx.ts:32 — 条件判断导致错误分支执行
- B2 (P1) xxx.ts:80 — Promise 错误未被捕获

将跳过（P3）：
- B4 (P3) zzz.ts:90 — 建议使用更合理的抽象

共 N 条需处理，M 条跳过。
```

如用户希望调整范围，先按用户指示调整，再继续。

---

## 步骤 5：逐条处理（串行）

### a) 读取上下文代码

读取问题所在文件，定位到报告中标注的行号，读取前后 10~20 行上下文。

**行号偏移处理**：
- 行号处内容与报告描述不匹配 → 通过代码特征（函数名、关键词）重新定位
- 重新定位失败 → 暂停该条，询问用户

**文件不存在**：记录 `➖无需修复`，备注"文件不存在，可能已重构或删除"，继续下一条。

### b) 判断处置情形

| 情形 | 含义 | 操作 |
|------|------|------|
| A | 确认是问题，按报告建议修复 | 执行代码修改 |
| B | 确认是问题，有更优方案 | 执行修改，备注中说明原因 |
| C | 误报，实际不需要修复 | 不修改代码，记录 `➖无需修复` |
| D | 影响较大或无法确定，需用户确认 | 暂停，向用户描述情况并征询意见 |

**多条问题互相影响**：修复 Bn 时已连带解决 Bm → 处理 Bm 时记录 `✅已修复`，备注"已被 Bn 修复消除"，不重复修改。

### c) 执行代码修改（情形 A/B）

- 精准 Edit，只改动必要的代码
- 不引入无关格式调整或重构

### d) 更新报告

每条处理完后立即更新报告：

1. 按 Bn ID 在「审查结论」表格中替换状态标记：
   - ❌ → `✅已修复` 或 `➖无需修复`
   - ⚠️ → `✅已修复` 或 `➖无需修复`

2. 在对应 `### Bn:` 条目末尾追加：

   ```markdown
   **处置结果**：✅已修复 / ➖无需修复 / ⏭已跳过
   **处置说明**：[简述处置原因或修复方案]
   ```

3. 在「不变量覆盖」中保留 INV-ID 和原始结论，修复结果通过“修复备注”记录
4. 同步在当前 task 的 `reports/fix/` 或仓库级 `reports/fix/` 记录本次修复过程

---

## 步骤 6：追加修复备注

在报告文件末尾追加：

```markdown
---
## 修复备注
> 修复执行时间：YYYY-MM-DD HH:mm

| ID | INV-ID | 严重程度 | 文件 | 处置结果 | 修复方式 | 反例/验证 | 备注 |
|----|--------|----------|------|----------|----------|-----------|------|
| B1 | INV-SPEC-01 | P0 | `xxx.ts:32` | ✅已修复 | 同方案 | `test_xxx` | |
| B2 | INV-CAND-01 | P1 | `xxx.ts:80` | ✅已修复 | 扩大错误捕获范围 | `test_error_path` | |
| B3 | INV-CAND-02 | P2 | `yyy.ts:15` | ➖无需修复 | - | 上游 guard 证据 | 误报 |

### 汇总
| 处置类型 | 数量 |
|----------|------|
| ✅ 已修复 | X |
| ➖ 无需修复（误报） | X |
| ⏭ 已跳过（P3） | X |
```

---

## 边界情况

| 情况 | 处置方式 |
|------|----------|
| 无 CR 报告 | 停止，提示先运行 x-cr |
| 报告格式异常 | 停止，提示结构不符合预期 |
| 文件不存在 | 记录 `➖无需修复`，备注"文件不存在" |
| 行号偏移但能重新定位 | 自动定位后继续处理 |
| 行号偏移且无法定位 | 暂停该条，询问用户 |
| 多条问题互相影响 | 修复时一并处理，后续条目记录已被消除 |
| P3 条目 | 默认跳过，记录 `⏭已跳过` |
| P2 来源冲突或待确认 | 暂停该条并请求权威规则确认 |
| Bn 重复或缺少详情 | 停止，提示报告 ID 映射异常 |
| x-cr-v2 的 INV-ID 缺少覆盖记录 | 暂停该条，提示不变量证据不完整 |
| 历史报告缺少 INV-ID | 使用 `legacy-unmapped` 继续处理，并在修复备注保留兼容标记 |
| 已有修复标记 | 跳过该条，不重复处理 |

---

## 步骤 7：提醒提交

修复完成后，提示用户：

```
✅ 修复完成，可提交：

git add .
git commit -m "fix: [一句话描述修复内容]"
```

如果本次涉及多个不相关改动，建议按实际修改分开 commit。
