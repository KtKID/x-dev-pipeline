# x-fix · 验收回流模式

> x-verify-spec 验收不通过时进入本模式：功能检查回执里有 P0/P1，或 `xdev check` 列出要改代码或测试的问题。

## 输入识别

- 功能检查回执（证据目录 `feature-check.md`）里的 P0、P1，编号沿用回执的 `issue-<n>`。
- `xdev check` 列出的问题中要改代码或测试的那些，主 agent 按顺序编号 V1、V2…。
- 旧契约包的 `verify-report-*.md` 路径。

两类可以同一轮一起修。哪些问题交 x-fix、哪些不交，以 [x-verify-spec「问题去向」](../../x-verify-spec/SKILL.md#问题去向) 为准。

## 通用流程

1. 读 fix-counter，counter >= 3 → 生成 fix-blocked-report.md，停。
2. 本轮至少有一条要修的问题时，counter +1，写回 .fix-counter（按轮计：本次批量修整体算 1 轮）；一条都没有就不递增，直接退回主 agent。
3. 读**完整问题清单**：P0 全修；P1 逐条修复，或认为报错了就在「问题与处置」写一行 `功能检查 · issue-N · 不采纳：<理由>`（`xdev check` 认这个写法）；P2 不在清单里。
4. 一次修完本轮全部应修项；**每修一个 P0 留一条可复跑反例**（测试断言或 verify 脚本步骤）。
5. 修复触及配置、CLI、公开 API、协议/schema 或落盘布局时，列出修复前已接受的最小输入样本；新增配置字段使用兼容默认值，或按 spec 提供显式迁移验收。
6. 自跑每条的聚焦反例，再跑 `xdev coverage`（修复前原始样本原样参与的全量测试与既有回归，改动行覆盖率仍 100%）；旧契约包为完整入口 verify。不跑功能检查和 `xdev check`，由主 agent 做。扩展后的 fixture 只作附加覆盖。
7. 新增的反例测试登记进用例对应表；处置逐条写进 checklist「问题与处置」（qdev 为⑤的同名节），不另建 fix 报告文件。
8. 控制权交回主 agent：主 agent 按 [功能检查](../../x-verify-spec/references/feature-check.md)「什么时候做」第 3 条重做功能检查（把上一份回执和修复 diff 一起给子 agent），再跑 `xdev check`；旧契约包复跑 `xdev verify`。
9. 修复过程中 dev-checklist 状态单元格保持原样；主 agent 验收通过后升钩。

## 按问题类型处理

- **漏了要的 / 做了没要的**：补上场景要的行为，或删掉多做的部分。涉及公开 API 签名变化时在处置里标出来。
- **测试类问题**（重写了生产逻辑、没调用项目代码、绕过要测的流程、mock 掉了被测对象、只断言调用、断言恒真、吞掉失败、数据测不出对错、没测到场景要的结果、人工记录不全）：默认**只改测试**，不为了让测试好写去改生产代码。测试改对以后暴露出生产代码真有错，一并修，并在处置里如实写明。
- **V 项**（`xdev check` 的问题）：只修让检查不过的代码：测试失败、编译错误、没覆盖的行（补测试）、缺真实链路用例（补 smoke / 集成测试）。V 项不能豁免，覆盖率和测试必须真的达标。收到悬空引用、范围遗漏、SPEC_CHANGED 这些文档或分配问题，不改，在回执里退回主 agent，由主 agent 交 x-req / x-tech-design。
- 旧契约包复跑本轮 fail 过的 verify 块，最终通关前完整跑一遍全清单。
- **注意**：不要为了通过去改用例对应表的结果、删用例、降低断言或加没有理由的覆盖率排除标记，那会绕过验收。
