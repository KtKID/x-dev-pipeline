# x-spec

把沟通完的需求写成一份纯功能性的 spec，描述用户能做什么、能看到什么，以及功能正确运行所需的边界处理。

## 核心原则

1. **如无必要，勿增实体。** 功能范围以用户明确要求和已确认结论为准；补充内容限于这些功能正确运行所必需的处理。
2. **只写做什么，不写怎么做。** 描述用户能感知的功能和结果，不写技术实现。
3. **用功能语言，不用技术词汇。** 写“保存”“查询”“加快”“提醒”，不写“数据库”“API”“缓存”“消息队列”。用户能看懂每一行。这条约束适用于概述、关键约束、场景、必要性说明和待确认清单；技术实现交给 x-tech-design。
4. **feat 是用户可感知的功能点。** 一个 feat 对应一个用户能说出名字的功能（如“登录”“搜索”“导出”）；同一功能的边界与失败处理放在该 feat 内。
5. **边界检查是必做项。** 对本次功能实际可达的输入、状态、操作时序和依赖失败逐项判断，覆盖会影响结果正确性的路径；场景数量由独立预期结果决定。

## 产物

一份 `docs/spec/<spec-name>/spec.md`。结构为：标题 + 概述 + 用户已确认的关键约束 + feat 列表；未确认提议留在待确认清单。完整读取 `templates/spec.md` 后填充，删除占位符和空示例。

## 工作流

### 1. 梳理需求

从刚结束的对话里提取用户明确要的功能、已确认结论，以及本次适用的既有行为约定，直接编写已明确部分的 spec 草案。每个 feat 都能回指需求来源。

补充一个行为前，判断它与已确认功能的关系：

- **必要的正确性处理**：在当前范围内能实际触发，缺少时会使已要求的结果出错、数据受损、状态矛盾或失败被误报为成功。写清触发条件和具体后果，归入原 feat。
- **新增产品能力或规则**：新增入口、角色、业务状态、配置项、额度或独立的恢复能力等，需要用户明确确认后进入功能正文。建议的合理性只用于说明价值，范围依据来自用户确认。

既有约定须能定位到文档、代码或已确认对话，适用范围与本次功能相符，并以本轮用户明确要求为准。确需用户决定的行为、阈值或业务取舍放入待确认清单，写清关联功能、具体问题、影响及建议；相关结果标为待确认，继续完成其余明确内容。可选增强仅在用户要求讨论扩展时提出。

### 2. 拆分 feat

按用户可感知的功能点拆分。编号规则：

- 新 spec 从 `feat01` 开始，两位序号，按文档顺序连续递增（feat01、feat02、feat03...）；增量修改沿用已有编号，新功能接续编号。
- 同一 spec 内序号不重复。
- 每个 feat 标题写功能名称，用功能性描述（如 `feat01: 用户用手机号登录`，不写 `feat01: AuthService`）。

一个 feat 是一个完整的功能点，不要拆得过细。判断标准：用户会把它当成"一个功能"来说，就归一个 feat。

### 3. 写场景

每个 feat 先写正常流程，再检查与本功能有关的边界和失败路径：

- **正常流程**：用户要求的操作产生什么结果。
- **适用边界**：从真实输入、已有状态和可达时序中找出会改变预期结果的条件，如空数据、有效范围端点、重复操作；适用项必须覆盖。
- **实际失败路径**：本功能涉及的读取、保存、下载等操作失败时，用户如何识别失败，已有数据和操作状态应保持什么结果。

检查范围以需求和现状为依据。同一预期结果的等价输入可合并为一个场景；不同预期结果分别保留。某类边界或失败确实与本功能无关时，在 feat 说明中简记检查结论与依据，按实际适用项编写场景。

**每个场景加一行必要性**：`必要性：<用户要求 / 既有约定 / 正确性补充及具体依据>；缺少时<具体功能缺失或错误后果>。` 正常流程可直接回指用户要求；补充边界必须说明实际触发条件和错误后果。理由保持一句话，以可核查依据和具体后果支撑场景；只有“体验更好”“以后可能用到”等收益的内容归为可选增强。理由同时满足范围依据，才构成本次验收要求。

格式：

```
## feat01: <功能名称>

<一句话说明这个功能给用户做什么>

场景1: <正常流程名>
必要性：<用户要求及来源>；缺少时<用户要求的哪项结果无法达成>。
- GIVEN <前置条件>
- WHEN <用户操作>
- THEN <可观察结果>

场景2: <实际适用的边界或失败路径>
必要性：<既有约定或实际可达的边界依据>；缺少时<具体错误后果>。
- GIVEN <前置条件>
- WHEN <用户操作>
- THEN <可观察结果>
```

**GWT 写法：**

- **GIVEN**：用户视角的前置条件或初始状态。例："用户已登录""购物车里有3件商品"。
- **WHEN**：用户的操作。例："点击结算""输入手机号后点击获取验证码"。
- **THEN**：用户能看到、能感知的结果。例："显示订单确认页""提示手机号格式不正确"。

**禁止出现**：技术词汇和技术实现细节。不写“调用 POST /api/order”“写入订单表”“返回 200 状态码”“缓存失效”。GWT 和必要性说明都只写用户能理解的功能、前提、操作、结果及错误后果；技术实现细节放入后续技术设计。

### 4. 提取关键约束

从用户已确认内容中提取“必定不能犯的错”，作为后续反例测试的依据。补充约束提议须对应本次功能可实际触发的错误及具体后果；数量以实际需要为准。边界处理的业务取舍尚待决定时，集中列入待确认清单。

- `spec.md` 的“关键约束（用户已确认）”是约束唯一正文来源。保留用户原意，写清必要的适用范围、可观察判据与禁止结果；用户原本给出的具体测试场景保留在相应 feat 下，约束只回指，不重复维护场景正文。
- 已确认条目用稳定编号 `C1`、`C2` 等；沿用既有约束编号，不重排或复用已删除编号。用 `featNN 场景M` 关联适用行为，已有 Scenario ID 的文档沿用原 ID，不为了加约束改编号。
- 用户已明确给出的约束可直接收录并注明来源；agent 新提议和新增的范围/判据先留在待确认清单，不能混入已确认章节。只确认部分时仅收录该部分，剩余项仍待确认；没有确认项时如实注明，不能把用户沉默写成“无约束”。
- 用户表述有歧义、不可观察或可能不可实现时，列出具体问题、建议澄清的范围/判据及影响，等待确认，不能自行削弱“绝不能”的含义。确认后回写权威条目，后续设计与任务只引用 ID。

### 5. 自检并报告待确认项

写完后逐条检查：

- 每个 feat 是否有用户明确要求或已确认结论作为范围依据？
- 每个补充场景是否落在原功能范围内，有实际触发条件和具体错误后果？新增产品能力或规则是否已有用户确认？
- 正常流程是否完整，实际可达的边界和失败路径是否逐项检查，适用项是否都有明确预期？
- 每个场景是否有一句可核查的必要性，等价场景是否已合并？
- 概述、关键约束、GWT、必要性说明和待确认清单中是否混入技术词汇或实现细节？发现后改成功能性描述。
- GWT 是否使用功能语言，THEN 是否给出可观察、可判定的结果？
- feat 编号是否从 01 连续递增、无重复（增量沿用已有编号）？
- 每条关键约束是否有真实用户依据、必要范围和可观察判据，C 编号稳定且关联场景有效？提议是否仍明确待确认？

最后报告实际待确认项，逐条写清关联 feat/场景、待决定行为、具体影响及建议，便于用户一次性 review；已明确内容直接交付。待确认项为空时如实说明。示例：

> 待确认：
> - feat01 场景1：用户前后分别提出“导出当前页”和“导出全部筛选结果”，两者产生的记录数不同，请确认本次导出范围。

## 确认之后

待确认清单及关键约束的提议逐条拍板，记录用户实际确认结论、来源和对应内容基线，spec 定稿后，主 agent 继续使用 x-tech-design：读取已确认的 spec，在 spec 同目录编写 `tech-design.md` 技术设计（模块、协议、数据流、规范落实），用大白话向用户讲清方案并组织确认。需求与技术设计由同一主 agent 连续完成。一个 spec 通常包含多个 feat，必须先有经用户确认的技术设计，才能进入 x-req 拆任务；给既有 spec 新增 feat 时，同样先补设计差异，再拆任务。

## 完整示例

用户要求“把当前筛选的图书列表导出为 CSV，包含当前展示的列”。现有下载约定已明确：空列表提示“暂无可导出数据”，下载失败时显示失败提示并保留筛选条件。正文据此写一个 feat，并补充特殊内容的正确性边界：

```markdown
# 导出当前图书列表

让用户把当前筛选的图书列表保存为 CSV 文件，内容与当前列表一致。

## 关键约束（用户已确认）

当前尚未收到用户单独确认的关键约束条目；功能场景依据上述用户要求和已有下载约定编写。

## feat01: 导出当前筛选列表

用户可以把当前筛选结果保存为 CSV 文件。

场景1: 正常导出
必要性：用户要求导出当前筛选结果及展示列；缺少时用户无法获得所需文件。
- GIVEN 当前筛选列表有图书
- WHEN 用户点击导出
- THEN 下载的 CSV 包含当前筛选结果和当前展示的列，内容与列表一致

场景2: 列表为空
必要性：沿用现有空列表下载约定；缺少时空结果的处理与现有操作约定冲突。
- GIVEN 当前筛选列表为空
- WHEN 用户点击导出
- THEN 提示“暂无可导出数据”

场景3: 内容包含逗号或换行
必要性：正确性补充，图书内容可包含逗号或换行；缺少时导出内容可能错列或截断。
- GIVEN 当前列表的某些单元格包含逗号或换行
- WHEN 用户导出并打开 CSV
- THEN 单元格内容完整，行列对应关系与原列表一致

场景4: 下载失败
必要性：沿用现有下载失败约定；缺少时用户可能误以为导出成功或丢失筛选状态。
- GIVEN 当前筛选列表有图书，下载操作失败
- WHEN 用户查看导出结果
- THEN 显示失败提示，当前筛选条件保持原样
```

场景3服务于“导出内容正确”这一既有目标。新增发布入口、自动重试、导出历史等能力各自需要用户明确要求或确认。
