# x-spec

用统一格式记录用户本次要完成的需求。需求分析依据用户当次目标确定范围；x-spec 负责忠实整理功能、约束和验收场景，MVP 验证、局部改动和正式交付共用这套格式。

## 核心原则

1. **剃刀法则：如无必要，勿增实体。** 功能、规则、场景和待确认问题都以达成本次目标所必需为准，够用即止。范围和完成程度以用户最新明确要求及仍适用的已确认结论为准。
2. **只写做什么，不写怎么做。** 描述用户能感知的功能和结果，不写技术实现。
3. **用功能语言，不用技术词汇。** 写“保存”“查询”“加快”“提醒”，不写“数据库”“API”“缓存”“消息队列”。用户能看懂每一行。这条约束适用于概述、关键约束、场景、必要性说明和待确认清单；技术实现交给 x-tech-design。
4. **feat 是用户可感知的功能点。** 一个 feat 对应一个用户能说出名字的功能（如“登录”“搜索”“导出”）；同一功能的边界与失败处理放在该 feat 内。
5. **边界深度随本次目标确定。** 保留用户明确要求和适用的既有约定；补充检查聚焦会直接妨碍本次目标达成的条件。MVP 验证重点覆盖会让验证结论失真的边界与失败路径，达到约定证据和完成条件即收敛。
6. **单份 spec 最多 3 个 feat，场景总数最多 10 个。** 总数按该 spec 全部 feat 下的场景合计；这是审阅容量上限，按实际需要填写。任一上限超出时拆分 spec，每份分别满足两项限制。

## 产物

每份需求写入 `docs/spec/<spec-name>/spec.md`。结构为：标题 + 概述 + 本次目标与完成条件 + 用户已确认的关键约束 + feat 列表；影响本次交付的待决问题留在待确认清单。完整读取 `templates/spec.md` 后填充，删除占位符和空示例。

## 工作流

### 1. 按本次目标梳理需求

从当前对话提取用户要达成的结果、本次范围、所需证据和完成条件。用户要求 MVP 验证时，写清要验证的假设、最小功能及判断假设是否成立的证据；其他任务按其实际目标记录。已有结论直接采用，影响本次结果的实质歧义集中澄清。

据此提取用户明确要的功能、已确认结论及本次适用的既有行为约定，直接编写已明确部分的草案。每个 feat 都能回指需求来源和本次目标。用户后来调整目标时，先同步 spec 范围与完成条件，再让后续设计和任务按新基线承接。

补充一个行为前，判断它与已确认功能的关系：

- **本次目标必需的处理**：当前范围内有实际触发依据，且会直接使已要求的结果出错、违反已确认约束或让验证结论失真。补充场景的具体预期须能由用户要求或适用既有约定直接确定，再归入原 feat；存在多种产品行为取舍时，只记录阻碍本次目标的待决问题，由用户确定行为。
- **新增产品能力或规则**：新增入口、角色、业务状态、配置项、额度或独立的恢复能力等，需要用户明确确认后进入功能正文。建议的合理性只用于说明价值，范围依据来自用户确认。

既有约定须能定位到文档、代码或已确认对话，适用范围与本次功能相符，并以本轮用户明确要求为准。确需用户决定的行为、阈值或业务取舍放入待确认清单，写清关联功能、具体问题、影响及建议；相关结果标为待确认，继续完成其余明确内容。可选增强仅在用户要求讨论扩展时提出。

### 2. 拆分 feat 与 spec

按用户可感知的功能点拆分。编号规则：

- 新 spec 从 `feat01` 开始，两位序号，按文档顺序连续递增（最多到 `feat03`）；增量修改沿用已有编号，新功能接续编号，数量按实际条目统计。
- 同一 spec 内序号不重复。
- 每个 feat 标题写功能名称，用功能性描述（如 `feat01: 用户用手机号登录`，不写 `feat01: AuthService`）。

一个 feat 是一个完整的功能点，不要拆得过细。判断标准：用户会把它当成"一个功能"来说，就归一个 feat。

写场景后复核容量：单份超过 3 个 feat 或场景总数超过 10 个，按可单独验收的目标或行为阶段拆成多份 spec，分别放入独立目录。单个 feat 超过 10 个场景时，也按可分别验收的行为段拆分。保留全部已确认需求及独立预期结果，仅合并等价输入；每份简记关联 spec、必要先后关系和本次执行范围。已有设计或任务回指时，同步对应关系并保留原编号的定位，拆分后的每份仍遵守容量上限。

### 3. 写场景

每个 feat 先写达成本次目标的正常流程，再依据本次范围和完成条件筛选必要的边界与失败路径：

- **正常流程**：用户要求的操作产生什么结果。
- **必要边界**：从实际输入和状态中选择会改变本次验收结论的条件；MVP 聚焦验证所用环境与数据，其他环境的支持按用户后续目标决定。
- **必要失败路径**：覆盖会违反已确认约束、破坏本次目标或把失败误判成验证成功的情况；具体处理行为按第 1 步的范围依据确定。

每个场景描述一条可独立验收的“前提—操作—结果”路径，同一路径可有多项共同成立的结果。等价输入可合并；不同前提或操作形成的独立路径分别计数，包括写在同一标题下的不同分支。场景按实际需要选择，正文只保留本次验收所需内容；全部场景足以判定本次目标与已确认约束时结束补充。超过容量上限按第 2 步拆分 spec。

**先核对来源，再写一行必要性**：`必要性：<用户要求或适用既有约定及来源>；缺少时<对本次目标或验证结论的具体影响>。` 补充边界同时说明实际触发依据，具体预期按第 1 步核对；风险理由与行为授权分别判断。只有“体验更好”“以后可能用到”等收益的内容归为可选增强，仅在用户要求讨论扩展时提出。

格式：

```
## feat01: <功能名称>

<一句话说明这个功能给用户做什么>

场景1: <正常流程名>
必要性：<用户要求及来源>；缺少时<用户要求的哪项结果无法达成>。
- GIVEN <前置条件>
- WHEN <用户操作>
- THEN <可观察结果>

场景2: <实际适用的边界或失败路径>
必要性：<用户要求或既有约定，实际触发依据>；缺少时<对本次目标的具体影响>。
- GIVEN <前置条件>
- WHEN <用户操作>
- THEN <可观察结果>
```

**GWT 写法：**

- **GIVEN**：用户视角的前置条件或初始状态。例："用户已登录""购物车里有3件商品"。
- **WHEN**：用户的操作。例："点击结算""输入手机号后点击获取验证码"。
- **THEN**：用户能看到、能感知的结果。例："显示订单确认页""提示手机号格式不正确"。

**禁止出现**：技术词汇和技术实现细节。不写“调用 POST /api/order”“写入订单表”“返回 200 状态码”“缓存失效”。GWT 和必要性说明都只写用户能理解的功能、前提、操作、结果及错误后果；技术实现细节放入后续技术设计。

### 4. 提取关键约束

从用户已确认内容中提取“必定不能犯的错”，作为后续反例测试的依据。待确认清单只收录阻碍本次目标达成或验收判定的实际歧义、冲突与行为取舍，每项说明具体影响。已明确内容直接交付，清单允许为空。

- `spec.md` 的“关键约束（用户已确认）”是约束唯一正文来源。保留用户原意，写清必要的适用范围、可观察判据与禁止结果；用户原本给出的具体测试场景保留在相应 feat 下，约束只回指，不重复维护场景正文。
- 已确认条目用稳定编号 `C1`、`C2` 等；沿用既有约束编号，不重排或复用已删除编号。用 `featNN 场景M` 关联适用行为，已有 Scenario ID 的文档沿用原 ID，不为了加约束改编号。
- 用户已明确给出的约束可直接收录并注明来源；确需用户决定的范围/判据留在待确认清单，确认后进入已确认章节。只确认部分时仅收录该部分，剩余实际待决项仍待确认；确认项为空时如实注明实际状态。
- 用户表述有歧义、不可观察或可能不可实现时，列出具体问题、建议澄清的范围/判据及影响，等待确认，不能自行削弱“绝不能”的含义。确认后回写权威条目，后续设计与任务只引用 ID。

### 5. 自检并报告待确认项

写完后逐条检查：

- 本次目标、范围、所需证据和完成条件是否忠实于用户当前要求？MVP 的验收是否聚焦约定假设及证据？
- 每个 feat 是否有用户明确要求或已确认结论作为范围依据？剃刀检查后保留的内容是否都服务于本次目标？
- 每个补充场景是否有实际触发依据、对本次目标的具体影响以及可追溯的预期行为来源？存在多种产品取舍时是否交由用户决定？
- 正常流程和必要边界是否足以判定本次目标，明确约束是否保留？待确认清单是否只含本次实际待决问题？
- 每份 spec 是否最多 3 个 feat、全部场景合计最多 10 个？独立验收路径是否分别计数，超限是否已完成拆分并保持有效回指？
- 每个场景是否有一句可核查的必要性，等价场景是否已合并？
- 概述、关键约束、GWT、必要性说明和待确认清单中是否混入技术词汇或实现细节？发现后改成功能性描述。
- GWT 是否使用功能语言，THEN 是否给出可观察、可判定的结果？
- feat 编号是否从 01 连续递增、无重复（增量沿用已有编号）？
- 每条关键约束是否有真实用户依据、必要范围和可观察判据，C 编号稳定且关联场景有效？提议是否仍明确待确认？

最后报告实际待确认项，逐条写清关联 feat/场景、待决定行为、具体影响及建议，便于用户一次性 review；已明确内容直接交付。待确认项为空时如实说明。示例：

> 待确认：
> - feat01 场景1：用户前后分别提出“导出当前页”和“导出全部筛选结果”，两者产生的记录数不同，请确认本次导出范围。

## 确认之后

记录用户实际确认结论、来源和对应内容基线。后续工作以用户本轮授权的阶段为准：需要进入技术设计时，主 agent 继续使用 x-tech-design，在 spec 同目录编写 `tech-design.md` 并组织确认；需要拆任务时，再由 x-req 承接已确认的需求和技术设计。各环节沿用本次目标、范围及完成条件，MVP 任务以取得约定验证证据为完成依据。给既有 spec 新增内容时，先复核容量，再同步设计差异与任务；拆出的多份 spec 各自按本轮执行范围推进。

## 完整示例

用户要求“把当前筛选的图书列表导出为 CSV，包含当前展示的列”。现有下载约定已明确：空列表提示“暂无可导出数据”，下载失败时显示失败提示并保留筛选条件。正文据此写一个 feat，并补充特殊内容的正确性边界：

```markdown
# 导出当前图书列表

让用户把当前筛选的图书列表保存为 CSV 文件，内容与当前列表一致。

## 本次目标与完成条件

- 本次目标与范围：交付当前筛选结果及展示列的 CSV 导出。
- 验证证据：核对导出内容与列表一致，并检查下列边界及失败结果。
- 完成条件：本 spec 的 4 个场景满足预期，已有下载约定得到保留。

## 关键约束（用户已确认）

当前尚未收到用户单独确认的关键约束条目；功能场景依据上述用户要求和已有下载约定编写。

## feat01: 导出当前筛选列表

用户可以把当前筛选结果保存为 CSV 文件。

场景1: 正常导出
必要性：用户要求导出当前筛选结果及展示列；缺少时用户无法获得所需文件。
- GIVEN 当前筛选列表有图书
- WHEN 用户点击导出
- THEN 下载的 CSV 包含当前筛选结果和当前展示的列，内容与列表一致

场景2: 列表为空
必要性：沿用现有空列表下载约定；缺少时空结果的处理与现有操作约定冲突。
- GIVEN 当前筛选列表为空
- WHEN 用户点击导出
- THEN 提示“暂无可导出数据”

场景3: 内容包含逗号或换行
必要性：用户要求导出内容与列表一致，图书内容可包含逗号或换行；缺少时导出内容可能错列或截断。
- GIVEN 当前列表的某些单元格包含逗号或换行
- WHEN 用户导出并打开 CSV
- THEN 单元格内容完整，行列对应关系与原列表一致

场景4: 下载失败
必要性：沿用现有下载失败约定；缺少时用户可能误以为导出成功或丢失筛选状态。
- GIVEN 当前筛选列表有图书，下载操作失败
- WHEN 用户查看导出结果
- THEN 显示失败提示，当前筛选条件保持原样
```

场景3服务于“导出内容正确”这一既有目标。新增发布入口、自动重试、导出历史等能力各自需要用户明确要求或确认。
