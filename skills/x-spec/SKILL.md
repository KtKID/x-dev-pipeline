# x-spec

用统一格式记录已明确的功能、约束和验收场景。MVP 验证、局部改动和正式交付共用这套格式。

## 核心原则

1. **剃刀法则：如无必要，勿增实体。** 功能、规则和场景都以达成本次目标所必需为准。范围和完成程度以用户最新明确要求及仍适用的已确认结论为准。
2. **只写做什么，不写怎么做。** 描述用户能感知的功能和结果，不写技术实现。
3. **用功能语言，不用技术词汇。** 写“保存”“查询”“加快”“提醒”，不写“数据库”“API”“缓存”“消息队列”。这条约束适用于概述、关键约束、场景和必要性说明。技术实现交给 x-tech-design。
4. **feat 是用户可感知的功能点。** 一个 feat 对应一个用户能说出名字的功能（如“登录”“搜索”“导出”）；同一功能的边界与失败处理放在该 feat 内。
5. **边界深度随本次目标确定。** 保留用户明确要求和适用的既有约定；补充检查聚焦会直接妨碍本次目标达成的条件。MVP 验证重点覆盖会让验证结论失真的边界与失败路径，达到约定证据和完成条件即收敛。
6. **每次新增或修改最多 3 个 feat，场景合计最多 10 个。** 这是单次审阅容量上限，只计本次新增和修改的 feat 及其场景；同一模块 spec 长期累积的既有 feat 不计入。本次超出上限时分多次完成，每次分别满足两项限制。

## 产物

一个模块功能一份 spec，写入 `docs/spec/<模块名>/spec.md` 并长期更新：模块名用英文小写加横线，不带版本号；同一模块已有 spec 时更新它，不另建。spec 包括标题、模块头部四行（模块、管哪些代码、状态、最近更新）、概述、本次目标与完成条件、用户已确认的关键约束、feat 列表和底部变更记录。完整读取 [模板](templates/spec.md) 后填充，删除占位符和空示例。

## 工作流

### 1. 核对已明确的输入

以用户的明确要求、探索结论和本次适用的既有行为约定为输入。核对本次目标与范围、所需证据和完成条件，以及已分好的 feat 和各自的行为。MVP 写清假设、最小功能与判断假设是否成立的证据。既有约定须能定位到文档、代码或已确认对话，并以用户本轮明确要求为准。

功能分组和验收条件已经明确时直接整理。仍需拆 feat，或发现行为、约束、验收条件有实质取舍时，交给 [x-explore-for-spec](../x-explore-for-spec/SKILL.md)，本次范围内的问题解决后再落盘。更新已有 spec 时，同样处理本轮涉及的旧待决条目，将确认结论纳入相应 feat 或约束章节，移除已解决的旧条目及空标题。

每个 feat 回指需求来源和本次目标。补充场景须有实际触发依据，且缺少时会直接影响目标、约束或验证结论。具体预期来自用户要求或适用既有约定。新增入口、角色、状态、额度等功能取舍由探索阶段取得明确确认后进入正文。

### 2. 编排已分好的 feat

沿用输入中的功能分组。编号规则：

- 新 spec 从 `feat01` 开始，两位序号，按文档顺序连续递增（最多到 `feat03`）；增量修改沿用已有编号，新功能接续编号，数量按实际条目统计。
- 同一 spec 内序号不重复。
- 每个 feat 标题写功能名称，用功能性描述（如 `feat01: 用户用手机号登录`，不写 `feat01: AuthService`）。

复核每份 spec 的容量。将探索阶段已按可独立验收目标或行为阶段分组的内容分别写入对应目录，按需记录关联 spec、先后关系和本次执行范围。发现单份超限且缺少明确的拆分依据时，回到探索阶段确定分组。已有设计或任务回指时，保持原编号可定位。

### 3. 写场景

每个 feat 先写达成本次目标的正常流程，再依据本次范围和完成条件筛选必要的边界与失败路径：

- **正常流程**：用户要求的操作产生什么结果。
- **必要边界**：从实际输入和状态中选择会改变本次验收结论的条件；MVP 聚焦验证所用环境与数据，其他环境的支持按用户后续目标决定。
- **必要失败路径**：覆盖会违反已确认约束、破坏本次目标或把失败误判成验证成功的情况；具体处理行为按第 1 步的范围依据确定。

每个场景描述一条可独立验收的“前提—操作—结果”路径，同一路径可有多项共同成立的结果。等价输入可合并；不同前提或操作形成的独立路径分别计数，包括写在同一标题下的不同分支。场景按实际需要选择，正文只保留本次验收所需内容；全部场景足以判定本次目标与已确认约束时结束补充。超过容量上限按第 2 步拆分 spec。

**先核对来源，再写一行必要性**：`必要性：<用户要求或适用既有约定及来源>；缺少时<对本次目标或验证结论的具体影响>。` 补充边界同时说明实际触发依据，具体预期按第 1 步核对；风险理由与行为授权分别判断。只有“体验更好”“以后可能用到”等收益的内容归为可选增强，仅在用户要求讨论扩展时提出。

格式：

```
## feat01: <功能名称>

<一句话说明这个功能给用户做什么>

场景1: <正常流程名>
必要性：<用户要求及来源>；缺少时<用户要求的哪项结果无法达成>。
- GIVEN <前置条件>
- WHEN <用户操作>
- THEN <可观察结果>

场景2: <实际适用的边界或失败路径>
必要性：<用户要求或既有约定，实际触发依据>；缺少时<对本次目标的具体影响>。
- GIVEN <前置条件>
- WHEN <用户操作>
- THEN <可观察结果>
```

**GWT 写法：**

- **GIVEN**：用户视角的前置条件或初始状态。例："用户已登录""购物车里有3件商品"。
- **WHEN**：用户的操作。例："点击结算""输入手机号后点击获取验证码"。
- **THEN**：用户能看到、能感知的结果。例："显示订单确认页""提示手机号格式不正确"。

**禁止出现**：技术词汇和技术实现细节。不写“调用 POST /api/order”“写入订单表”“返回 200 状态码”“缓存失效”。GWT 和必要性说明都只写用户能理解的功能、前提、操作、结果及错误后果；技术实现细节放入后续技术设计。

### 4. 提取关键约束

从用户已确认内容中提取“必定不能犯的错”，作为后续反例测试的依据。

- `spec.md` 的“关键约束（用户已确认）”是约束唯一正文来源。保留用户原意，写清必要的适用范围、可观察判据与禁止结果；用户原本给出的具体测试场景保留在相应 feat 下，约束只回指，不重复维护场景正文。
- 已确认条目用稳定编号 `C1`、`C2` 等；沿用既有约束编号，不重排或复用已删除编号。用 `featNN 场景M` 关联适用行为，已有 Scenario ID 的文档沿用原 ID，不为了加约束改编号。
- 用户明确给出的约束直接收录并注明来源。范围、判据或原意有实质歧义时，先回到探索阶段确认。确认项为空时如实注明实际状态。后续设计与任务只引用 ID。

落盘前按模板核对功能语言、编号、容量、场景必要性、可观察结果和约束回指。交付时链接写入的 spec，说明对应确认依据。

## 确认之后

记录用户实际确认结论、来源和对应内容基线。后续工作以用户本轮授权的阶段为准：需要进入技术设计时，主 agent 继续使用 x-tech-design，在 spec 同目录编写 `tech-design.md` 并组织确认；需要拆任务时，再由 x-req 承接已确认的需求和技术设计。各环节沿用本次目标、范围及完成条件，MVP 任务以取得约定验证证据为完成依据。给既有 spec 新增内容时，先复核容量，再同步设计差异与任务；拆出的多份 spec 各自按本轮执行范围推进。

## 完整示例

用户要求“把当前筛选的图书列表导出为 CSV，包含当前展示的列”。现有下载约定已明确：空列表提示“暂无可导出数据”，下载失败时显示失败提示并保留筛选条件。正文据此写一个 feat，并补充特殊内容的正确性边界：

```markdown
# 导出当前图书列表

让用户把当前筛选的图书列表保存为 CSV 文件，内容与当前列表一致。

## 本次目标与完成条件

- 本次目标与范围：交付当前筛选结果及展示列的 CSV 导出。
- 验证证据：核对导出内容与列表一致，并检查下列边界及失败结果。
- 完成条件：本 spec 的 4 个场景满足预期，已有下载约定得到保留。

## 关键约束（用户已确认）

当前尚未收到用户单独确认的关键约束条目；功能场景依据上述用户要求和已有下载约定编写。

## feat01: 导出当前筛选列表

用户可以把当前筛选结果保存为 CSV 文件。

场景1: 正常导出
必要性：用户要求导出当前筛选结果及展示列；缺少时用户无法获得所需文件。
- GIVEN 当前筛选列表有图书
- WHEN 用户点击导出
- THEN 下载的 CSV 包含当前筛选结果和当前展示的列，内容与列表一致

场景2: 列表为空
必要性：沿用现有空列表下载约定；缺少时空结果的处理与现有操作约定冲突。
- GIVEN 当前筛选列表为空
- WHEN 用户点击导出
- THEN 提示“暂无可导出数据”

场景3: 内容包含逗号或换行
必要性：用户要求导出内容与列表一致，图书内容可包含逗号或换行；缺少时导出内容可能错列或截断。
- GIVEN 当前列表的某些单元格包含逗号或换行
- WHEN 用户导出并打开 CSV
- THEN 单元格内容完整，行列对应关系与原列表一致

场景4: 下载失败
必要性：沿用现有下载失败约定；缺少时用户可能误以为导出成功或丢失筛选状态。
- GIVEN 当前筛选列表有图书，下载操作失败
- WHEN 用户查看导出结果
- THEN 显示失败提示，当前筛选条件保持原样
```

场景3服务于“导出内容正确”这一既有目标。新增发布入口、自动重试、导出历史等能力各自需要用户明确要求或确认。
