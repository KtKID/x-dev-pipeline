# 需求变化同步：spec 改了，下游改哪些

x-ask-spec、x-tech-design、x-req、x-dev、x-qdev 遇到需求变化时都按本文处理。

## 一句话规则

**spec 里的场景或 C 变了，就顺着编号往下找引用它的 D、T、任务行和测试，按下表处理。没有被引用的一律不动，不顺手改。**

## 编号链

```text
场景 / C ──▶ D（tech-design 的技术约束）──▶ T（tech-design 的用例）──▶ 任务行（checklist 的 # 列）──▶ 测试文件
```

- 引用场景或 C 的 D：D 规则表"回指场景 / C"列里写了它。
- 引用场景或 C 的 T：用例表里关联了它。
- 引用某条 D 的 T：用例表里写了这个 D 编号。
- 承接 T 或 D 的任务行：checklist "任务"列里写了这个 T 或 D 编号，或者"场景回指"列里写了这个场景。
- 任务行的测试文件：该行"涉及文件"里的测试文件。

qdev 没有单独的 tech-design 时，链条是：场景 / C → task ②里的局部 D → ③里的用例 → 测试文件，规则相同。

## 怎么处理

| spec 怎么变 | T | D | 任务行 | 测试文件 |
|---|---|---|---|---|
| **改了场景**（前提、操作或结果变了） | 引用它的 T：**改**预期或操作 | 引用它的 D：逐条问"新行为下这条约束还成立吗"，成立就不动，不成立就**改** | 改了 T 或 D 的任务行：**重开** | 要改的 T 所在的测试文件：**改** |
| **改了 C** | 引用这条 C 的 T：**改** | 同上 | 同上 | 同上 |
| **新增场景** | **新增**至少一条 T | 只有这条场景带来新的技术约束（要多存数据、有先后顺序、失败后状态要保证）时才**新增** D | 放进承接同一 feat 的已有任务行并**重开**；没有这样的行才新增任务行 | 该行的测试文件：**改** |
| **删除场景** | 只为它存在的 T：**退役**（保留编号，写原因）；再**新增**一条 T 验证移除后的行为 | 只为它存在的 D：**退役** | 承接它的任务行：**重开** | 该行的测试文件：**改** |
| **只改措辞，行为不变** | 不动 | 不动 | 不动 | 不动 |
| **修 bug，spec 已写明正确行为**（spec 不变） | **新增**一条 T 覆盖出 bug 的输入 | 不动 | 承接这条场景的任务行：**重开** | 该行的测试文件：**改** |

D 被改了还要再往下走一步：

- 引用这条 D 的其他 T：逐条看预期变没变，变了才**改**。
- 引用这条 D 的**所有**任务行都**重开**，因为它们共用的实现可能被改。
- 这些行里内容不用改的测试文件：**重跑**。

动作的意思：

| 动作 | 意思 |
|---|---|
| 改 | 内容要改：约束、预期、操作或断言 |
| 新增 | 加一条新的 |
| 退役 | 不再有效，保留编号并写原因 |
| 重开 | 任务行状态退回 `[ ] ⏳`，原有证据作废，要重新取证 |
| 重跑 | 内容不变，但要重新运行并更新证据 |

## 谁来做

1. **x-ask-spec**：改完 spec 后，按上表列出影响清单，随 spec 增量交给下游。格式：`| 编号 | 动作 | 原因 |`。
2. **x-tech-design**：按清单改 D 和 T，退役项保留编号。
3. **x-req**：按清单重开或新增任务行，更新影响文件树。
4. **x-dev**：开工前比较 checklist 头部记录的 spec / tech-design 基线和当前内容。不一致时，按本规则检查同步是否做完；没做完的行不开工，交回来源负责方。
5. **x-qdev**：一个人走完上面四步，结果记在 task 的①②③；用了外部 tech-design 时，D 和 T 改在 tech-design 里。

开发中发现要改 spec，先改 spec 并给用户确认，再按本规则往下同步。不能先改代码再回头补文档。
