# 技术设计中的开发规范

本文件维护 x-tech-design 使用的用户开发规范。设计时结合项目权威规范逐条检查；项目已有同一规则时引用其来源，不再复制正文。为下列每个规则编号及项目附加规则记录适用性、原因、设计条目、落实位置与验证依据；不适用也要说明原因。

| 编号 | 规则与边界 | 设计落实及验证依据 |
|---|---|---|
| R1 模块边界 | 职责单一，目录边界清晰；依赖单向、无循环；不得跨模块访问内部文件/符号 | 明确职责、目录、公开接口和允许依赖。已有导入/依赖静态检查可检验循环及越界；未有检查时列出可执行检查计划与当前导入/调用审查证据，不能空写“遵循最佳实践” |
| R2 协议优先 | 前后端面向协议。TS 的边界数据以 Zod schema 定义和运行时校验，并从 schema 推导类型；Python 用 Pydantic 模型定义和校验边界。禁止平行手写同义协议、DTO、校验副本，不禁止作者编写 schema/Pydantic 模型或普通内部类型 | 指定权威 schema 路径、消费者、校验位置及失败处理；检查类型推导、引用关系和重复定义，安排边界有效/无效输入测试。已有不同方案时记录差距、兼容影响及待确认方案，不直接进行全仓替换 |
| R3 跨语言协议 | 同一协议指定一个权威定义和所有者；其他语言表示由其生成或受控同步，不各自手写维护同义协议 | 指定权威源、生成/同步方向、执行入口和漂移检查，说明版本兼容及失败时处理。生成的 Zod/Pydantic 表示和产物不成为第二权威源；纯单语言说明本条不适用 |
| R4 数据唯一来源 | 每类数据有明确唯一来源及所有者，区分值的权威存储与协议定义来源。可推导值不默认重复持久化；确需缓存、索引或快照须有明确理由 | 指定数据类别及必要字段的来源、写入方、读取方；派生值写明计算输入。副本写明更新、失效、重建和一致性策略，必要时安排过期/并发/恢复测试；检查实际读写路径，不能只列一张字段表 |
| R5 概念命名 | 同一概念的名称和定义统一，避免同义变量/字段各自维护造成漂移；不机械禁止局部别名 | 引用权威定义，检查协议、模块和存储命名。外部历史命名或局部别名确有用途时说明边界映射，避免引出第二份独立维护的概念；概念是否一致需语义审查，不能只靠字符串搜索 |
| R6 具名配置 | 业务阈值、时间、重试等用具名配置或常量，默认值和单位清楚，不散落魔法数 | 指定名称、语义、单位、默认值、权威位置及覆盖方式；默认值的业务含义不明时返回需求澄清。静态检查/代码审查定位重复字面值与配置读写，边界测试验证使用效果；不把普通索引等所有数字都当业务配置 |
| R7 数据流与状态 | 主要功能从入口、校验、处理、状态变化/持久化到返回完整可追踪；按需要处理异步、幂等、并发和失败恢复 | 回指场景并定位处理边界、状态所有者与提交点；适用时明确重复请求、竞态、部分失败、重试/恢复策略并计划对应测试；不适用需结合该流程说明原因 |

设计阶段可以给出检查入口、测试类型与预期结果；尚无实现时标注“待实现验证”。已经执行的检查记录命令/范围和结果，代码阅读记录文件/符号及结论；不能把计划写成已通过。静态检查不能替代职责合理性、协议权威性或数据归属的语义审查。
