# x-tech-design

把本轮 feat 的需求转成开发模型可以执行和验收的边界。功能行为以 `spec.md` 为准，`tech-design.md` 维护技术约束和编号用例。开发模型在约束内决定内部算法、私有类型、函数和文件拆法。

## 输入与产物

读取已落盘的 spec、本轮 feat 范围及对应确认记录。用户指定部分 feat 时，以该范围为准。spec、确认依据或必需约束有缺项时，补齐后再写草案。产品行为有待决取舍时，交回 [x-explore-for-spec](../x-explore-for-spec/SKILL.md) 确认。

在 spec 同目录写 `tech-design.md`，记录本轮 feat、spec 版本及确认依据，草案标为 **待用户确认**。已有设计时，先读现有内容和工作区改动，按本轮范围更新，沿用既有编号与锚点。

## 工作流

### 1. 核对 feat 与验收结果

从每个 feat 的主路径读起，列出本轮场景及适用 C 约束。保留已有场景 ID，或以 `featNN 场景M` 回指。先明确成功结果和必要的边界、失败结果，再调查会影响这些结果的代码。

### 2. 定位涉及的入口和模块

沿本轮 feat 的入口读取直接受影响的模块、公开契约及数据读写。用实际目录、公开接口、权威数据来源等划定改动范围，跨模块时写清职责和允许的依赖。已有设计、代码和协议可直接引用。新增或替换涉及的公开契约时，说明必要性与兼容影响。

读取项目适用规范和 [开发规范](references/development-rules.md)，在设计中记录会影响本轮实现边界的规则及验证位置。

### 3. 写清边界与验收

按 [模板](templates/tech-design.md) 记录范围、必要约束和测试。相同规则写一处，场景和适用入口回指该处。

- **技术约束。** 写清必须遵守的公开契约、数据归属、关键先后或失败后的状态，并标明依据。需要用户确认的边界取舍，简述理由和影响。允许多种做法的地方，只写它们共同要满足的条件。必要时用 Mermaid 表达跨模块时序，用公式或短伪代码澄清规则的结果，用带中文注释的类型或字段差异描述变更的公开契约。
- **验收用例。** 每个 feat 的主路径必须由至少一条标记为 **Smoke** 的用例覆盖，使用真实入口和最小数据，以可观察结果判定。多个 feat 可共用一条 Smoke，分别写清各自的通过条件。其余已确认场景和适用约束均有编号用例，可共用。记录测试目的、准备数据、操作、预期及适用的禁止结果。若必须先完成某步才可回包，用例应能在该步骤停住时检查有无提前回包。
- **验证状态。** 设计阶段写明怎么验证和预期结果，区分已检查与待实现验证。Smoke 随用例交给 x-req 分配，开发交付前执行并记录结果。实际执行证据按 [共用报告约定](../x-dev/references/test-reporting.md) 链接统一测试报告。

### 4. 检查并交付草案

1. **范围。** 每条设计都能回指本轮 feat 或其直接影响的模块。
2. **边界。** 必须满足的约束有依据、适用入口和可验证结果。内部实现由开发模型选择。
3. **验收。** 每个 feat 的主路径有 Smoke，本轮场景和适用约束都能找到带判据的编号用例。

交付草案链接、需确认的边界取舍和实际阻塞。删除模板提示，按用户实际确认结果更新状态。

## 确认与 x-req 对接

交接时提供 spec 与技术设计的路径及基线、确认依据、本轮场景和 C 约束对应的 D 规则与 T 用例，以及 Smoke 编号。已有设计沿用其编号或章节定位。关键边界未确认、场景缺用例或 Smoke 缺失时，补齐后再拆解。设计阶段以交付并确认草案为终点。

后续需求变化先确认受影响的 spec 条目，再更新对应设计和用例。开发模型需要越过已确认边界时，先提交受影响的设计变更。
