# x-tech-design

把已确认的功能需求转成可供用户审查、后续任务拆解引用的技术设计。功能行为以 `spec.md` 为唯一事实源，技术决策与编号测试用例的主定义以独立的 `tech-design.md` 维护；关键约束正文留在 spec，后续任务和报告只回指约束/用例 ID。

主 agent 在 spec 确认后继续使用本技能编写技术设计，并向用户讲解和组织确认。x-spec 与 x-tech-design 的独立性指技能职责和产物划分，两个阶段由同一主 agent 连续完成。

以人类可判断正确性为目标：主文先呈现关键决策，再用数据流、规则图表和可推演的具体例子解释方案；完整协议、测试用例及覆盖矩阵放附录。文字解释理由与代价，图表展示关系和条件，例子给出确定的预期结果。必要术语首次解释，精确定义或权威引用继续保留，主文与附录保持一致。

主文按技术问题和机制组织，例如数据归属、后台调度、状态转换、区间计算；一个机制可以支撑多个功能。Spec 负责功能行为和场景，技术设计负责实现这些行为的结构、规则与取舍，feat/场景的对应关系集中在追溯附录。

## 输入与产物

| 输入 | 要求 |
|---|---|
| 项目根目录 | 可访问的明确路径；代码、规范和设计中的仓库路径相对此目录 |
| spec 路径 | 已落盘的功能 spec；通常为 `docs/spec/<spec-name>/spec.md` |
| spec 确认状态 | 用户确认的结论、来源及对应版本/内容基线；文件存在或完成编写不等于用户已确认 |
| 约束 | 用户明确的范围、技术限制、开发规范及尚未解决的问题；没有额外约束也要注明 |
| 现有设计 | 相关架构/协议/数据归属文档路径及确认状态；若无，注明并从代码调查现状 |

产物固定为输入 spec 的同目录 `tech-design.md`，通常是 `docs/spec/<spec-name>/tech-design.md`。记录 spec 路径、版本/内容基线、确认依据、设计状态与本轮范围。默认状态为 **待用户确认**，不能把完成编写或通过自检当作批准。

若 `tech-design.md` 已存在，先读取其内容、状态和用户已有修改，基于原文做本轮设计差异；保留无关内容，不盲目覆盖已确认决策或其他人的编辑。项目采用不同 spec 路径时仍取该输入文件的父目录，不另建平行功能文档。

## 工作流

### 1. 核对输入与功能边界

完整读取 spec，核对确认依据是否覆盖当前落盘内容与范围。缺少项目根目录、spec 文件、确认依据或必要约束，以及 spec 仍待确认时，停止设计编写，报告缺项和阻塞原因；以实际可核查的确认记录为准，不编造用户批准。

读取项目适用的 `AGENTS.md`、相关 `.agents/skills` 和开发规范。设计前读取 [开发规范](references/development-rules.md)，结合项目已有规范逐条判定适用性；引用已有权威规范，不复制维护多份。冲突会影响设计时列出来源与影响，返回澄清。

场景用 `featNN 场景M` 回指（如 `feat02 场景3`），已有 Scenario ID 时沿用；关键约束用 spec 的 C 编号回指，不复制概述或 GIVEN/WHEN/THEN。发现功能行为、边界或数据含义存在歧义，向用户报告具体回指、分歧和影响，交回需求澄清；不得用技术假设补完产品行为。可继续调查不受影响的现状，受影响设计标为阻塞，不能宣称整体可交接。

C、D、用例 T 是追溯元数据示例，各自在约束、设计、用例范围内唯一；已有 ID、章节定位及链接锚点沿用，不为了重组正文改号。正文以技术问题和描述性中文名称组织，稳定 ID 放元数据或追溯附录，供 req/dev/verify 定位。旧 spec 没有 C 章节时从已确认场景和现有约束提取依据，不新造用户决定；新增约束先交 x-spec 确认。

### 2. 调查现有架构

围绕 spec 范围读取现有目录、模块公开入口、依赖、协议/schema、数据读写、配置与测试。区分“代码当前如此”“用户已确认”“本轮建议”，为现状和复用结论给出可定位的文件/符号证据，不把建议写成既成事实。

优先复用现有模块、技术栈与权威协议。新增模块、引入技术或替换现有方案时，说明现有方案为何不足，以及依赖、调用方、数据迁移、兼容性与维护成本的影响；只写本需求涉及的影响，不借机重构全仓。

### 3. 编写技术设计

读取 [评审模板](templates/tech-design.md)，按“关键决策 → 整体结构 → 关键机制与推演 → 验证状态 → 附录”组织。根据本轮技术问题选择章节，共用机制只解释一处；需求正文、feat 目录和 GIVEN/WHEN/THEN 保留在 spec。已有不变设计引用原出处，简单改动合并适用小节，仅展开受影响部分。

#### 主文：帮助人作判断

1. **关键决策前置**：简短元数据之后立即列出需要判断的选择、推荐、理由、主要代价及兼容/迁移影响、确认状态，并链接相应机制。开头以一屏可扫读为目标；影响范围和重大风险在此可见。普通局部实现选择交给开发者，调查明细和完整基线记录放附录。
2. **整体结构与数据归属**：用数据流图及简短所有权表展示入口、校验、处理、状态/持久化到返回的主路径，标出权威存储、写入方和派生结果。图中对应实际或计划模块，目录与公开入口在表中定位；代码依赖另标单向关系。单步改动可用短表或文字。沿用与新增、关键失败路径在这一层清楚可见。
3. **关键机制与规则**：按实际技术问题分节，例如“整理许可与取消”“时间区间如何累计”。主文保留影响正确性的条件、优先级、提交边界和不变量，以及改变结果的关键阈值；字段全集、序列化约定和接口明细放附录。条件交织或顺序敏感的规则采用下面适合的表达，配少量文字解释依据与取舍。

| 技术问题 | 表达方式 | 人类应能检查的内容 |
|---|---|---|
| 调用顺序、异步提交、失败回退 | Mermaid 时序图 | 先后关系、校验/提交点、失败后保留的状态 |
| 暂停、恢复、取消等状态变化 | 状态图或“当前状态＋事件/条件 → 动作＋下一状态”表 | 历史状态差异、迟到事件、恢复条件 |
| 多条件分类、冲突消解 | 决策表 | 条件组合、优先级、默认结果；按需列边界/非法组合 |
| 计算、合并、去重等算法 | 简短伪代码或公式＋输入输出表/时间图 | 计算步骤、边界、单位及不变量 |

4. **具体推演就近呈现**：每个复杂机制给出足以手工判断的具体输入、初始状态/事件顺序和确定的预期输出；选取正常路径以及会改变结论的边界或失败例。计算例写出数值和单位，状态例写出状态前后与持久化结果。例子回答“按这套规则会得到什么”，引用对应测试用例；输入夹具只维护一份，主文用最小必要投影展示。简单改动用一个直接例子即可，图表与例子的数量随实际问题调整。
5. **验证状态与待决问题**：简述已阅读/已执行的证据、仍待验证的关键风险、阻塞及其影响，并链接附录。“场景已安排用例”“用例已执行”“结果符合预期”分别报告。关键决策的确认入口保留在文档开头。

推演写法示意：已确认需求要求同一操作重试保持单条消息时，可写“初始 0 条，操作标识 op-42；首次提交后回执丢失，再以 op-42 重试 → 最终 1 条，返回首次消息 ID”。图表解释去重的提交边界，附录用例通过真实入口注入回执丢失并检查记录与返回值。具体机制来自项目设计，示意例只用于说明表达粒度。

#### 附录：精确定义与完整验证安排

**协议、结构与配置。** 保存本轮新增/变化结构的精确定义或权威引用：重要字段的可空性、单位、标识、关系和不变量，数据所有者与权威存储，派生值/缓存的更新、失效和重建策略。接口写生产者/消费者、输入输出、校验与错误行为；跨语言写生成/同步方向及漂移检查。具名配置写单位、默认值依据、权威位置和实际使用位置。新结构注明设计示意和计划实现位置，落地后引用正式 schema；未变定义沿用原出处。

**测试用例与矩阵。** 完整用例主定义放附录，按技术机制或验证目标分组，以描述性中文名称组织；Spec 场景作为覆盖索引，每个场景至少由一条编号用例承接全部预期及适用禁止结果。用例写清准确场景/约束来源、为什么测、数据与准备、执行流程、预期/禁止结果及观察点、验证方式与证据、局限。纯技术约束用例注明设计/规范来源与适用范围，作为补充验证；需求与 GWT 用链接回指。

“为什么测”说明这组输入、条件和步骤能暴露的具体错误及后果。流程写到可执行：准备数据/环境 → 调用入口 → 真实处理及故障注入 → 观察/断言 → 清理/复位。适合代码验证的用例给出虚拟数据必要字段、初始状态和构造方式，定位入口路径/符号、真实处理路径及结果读取位置；待实现入口标计划位置。被验证的存储、去重等机制保留真实执行，外部依赖替身注明边界和局限；人工/审查用例给出操作路径与判据。独立边界和故障用单独用例或可分别断言的数据行呈现，每行有输入、预期和观察点。

共享用例只定义一次，各来源场景分别关联其预期/禁止结果及实际观察点。一个场景可拆多条用例，多个场景可共享用例；本轮全部场景逐项登记，完整列出承接用例与缺口，供 req 检查。主文推演与正式用例使用同一规则和预期，合成推演标为预期示例，执行结果按实际证据记录。

**调查与追溯。** 汇集现状代码证据、spec/设计基线及确认记录、设计/用例定位、逐场景覆盖和规范索引。设计与用例分配稳定 ID（如 D01、用例 T1），沿用已有编号；“用例 T1”与 checklist 任务行 T1 分别定位。登记中文名称、唯一主定义链接、准确场景及适用 C/设计来源、结果/证据位置；共用规范 R1–R7 及项目规则逐条记录适用性、原因和落实/验证位置。重组时保留既有锚点或提供有效定位。

### 4. 检查并交付草案

- 从主文能否直接判断关键选择及代价、数据归属、复杂规则与预期结果？决策是否位于开头，重大风险与待确认项是否可见？
- 章节是否围绕技术问题与共用机制，Spec 的功能/场景仅在附录建立对应？需求正文保持在 spec，完整协议与测试矩阵位于附录，未变设计有原出处。
- 复杂规则是否有合适的图表及具体输入输出例子？状态变化、优先级和关键边界可逐项检查，数值/单位可手算；主文规则、样例与附录定义/测试预期一致，详细用例可从主文链接找到。
- 从 spec 本轮范围逐个列出全部场景，每个场景都有编号用例及其全部预期/适用禁止结果的观察点；每条用例的场景来源或纯技术约束来源、测试理由、数据准备与执行流程均可定位，缺项列为交接阻塞。
- 每条已确认关键约束都有机制和完整用例依据；共享测试只有一份主定义，各场景分别关联实际断言/观察点。代码验证用例的数据构造、调用入口、被测真实路径、结果检查和复位安排清楚，替身边界及证据局限明确。
- ID 仅作元数据/附录追溯，既有编号与定位有效；req/dev/verify 可按原契约找到设计、附录中的唯一用例主定义和各自证据。
- 模块公开接口、数据所有者、协议来源与数据流相互一致；所有新增/替换有复用调查及影响依据。
- [开发规范](references/development-rules.md) 中每条规则及项目附加规则都有“适用/不适用 + 原因”，适用规则有落实位置和验证依据。
- 区分已执行检查、代码阅读证据与计划在实现阶段执行的测试。没有实现时写明预期判定标准，不伪造通过结果，不为产出证据先写业务实现或安装工具。
- 所有关键问题、阻塞及草案状态清楚；模板注释、占位符和空示例已删除。

交付摘要简要给出输出路径、关键决策及影响、待确认问题、主要验证结果/局限和交接状态。完整基线、确认记录、协议、用例与覆盖矩阵通过文档链接定位，存在覆盖缺口时直接说明。草案请用户审查，确认状态依据实际用户结论更新。

## 确认与 x-req 对接契约

技术方案先输出为待确认草案。用户确认关键架构、协议、数据归属及影响方案后，记录实际确认结论、来源与对应设计版本/条目；只确认部分时保留剩余待确认项，不能宣称整体已确认。普通函数、局部变量等实现细节由开发者按已确认设计决定，无需逐项交给用户审批。

通过本技能交接给 req 拆任务时，提供：已确认的 spec 路径/基线、`tech-design.md` 路径/基线及关键条目的确认依据、本轮全部场景 → 用例的覆盖索引、适用 C 编号 → D 机制 → 用例编号的映射及已知阻塞。用例的理由、数据、流程与判据在主定义中可定位，任务引用该主定义。场景用例缺失、关键设计未确认或功能歧义未解决时，补齐对应来源后再交接。

本技能是主线必经环节：`x-req` 的就绪检查要求同目录存在关键条目已确认的 `tech-design.md`，否则阻断拆解。本技能仍不自动调用 x-req、不创建任务、不编写业务实现。后续实现若需改变已确认的重大架构、协议或数据归属，先更新受影响设计并请求用户确认，再按新结论实施。

## spec 后续变更

对照记录的 spec 基线分析变化。纯措辞且行为、数据、接口均未改变时，记录影响判断即可，不重做设计。行为、数据或接口变化时，先列出受影响场景、设计编号和已有任务路径/编号（尚未拆任务则注明）；变更后的功能 spec 未确认时只报告影响和待澄清项，确认后再更新相关设计。关键决策变更标为待确认，已确认且不受影响的条目保留。缺少旧基线时如实报告无法完整判断，不把旧确认套用到新内容，也不自动改写后续任务。
