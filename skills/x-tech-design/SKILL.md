# x-tech-design

把已确认的功能需求转成可供用户审查、后续任务拆解引用的技术设计。功能行为以 `spec.md` 为唯一事实源，技术决策与编号测试用例的主定义以独立的 `tech-design.md` 维护；关键约束正文留在 spec，后续任务和报告只回指约束/用例 ID。

主 agent 在 spec 确认后继续使用本技能编写技术设计，并向用户讲解和组织确认。x-spec 与 x-tech-design 的独立性指技能职责和产物划分，两个阶段由同一主 agent 连续完成。

面向用户的设计正文和讲解都用大白话：讲清准备怎么做、为什么这样做、数据从哪里来并经过哪些环节、失败时如何处理。必要术语首次出现时解释含义及在本方案中的作用，避免用术语堆叠代替说明。协议、数据结构、数据归属与编号测试的依据、预期和禁止结果仍保留精确定义或权威引用，通俗解释与这些定义保持一致，保证开发可执行、结果可验收。

## 输入与产物

| 输入 | 要求 |
|---|---|
| 项目根目录 | 可访问的明确路径；代码、规范和设计中的仓库路径相对此目录 |
| spec 路径 | 已落盘的功能 spec；通常为 `docs/spec/<spec-name>/spec.md` |
| spec 确认状态 | 用户确认的结论、来源及对应版本/内容基线；文件存在或完成编写不等于用户已确认 |
| 约束 | 用户明确的范围、技术限制、开发规范及尚未解决的问题；没有额外约束也要注明 |
| 现有设计 | 相关架构/协议/数据归属文档路径及确认状态；若无，注明并从代码调查现状 |

产物固定为输入 spec 的同目录 `tech-design.md`，通常是 `docs/spec/<spec-name>/tech-design.md`。记录 spec 路径、版本/内容基线、确认依据、设计状态与本轮范围。默认状态为 **待用户确认**，不能把完成编写或通过自检当作批准。

若 `tech-design.md` 已存在，先读取其内容、状态和用户已有修改，基于原文做本轮设计差异；保留无关内容，不盲目覆盖已确认决策或其他人的编辑。项目采用不同 spec 路径时仍取该输入文件的父目录，不另建平行功能文档。

## 工作流

### 1. 核对输入与功能边界

完整读取 spec，核对确认依据是否覆盖当前落盘内容与范围。缺少项目根目录、spec 文件、确认依据或必要约束，以及 spec 仍待确认时，停止设计编写，报告缺项和阻塞原因；以实际可核查的确认记录为准，不编造用户批准。

读取项目适用的 `AGENTS.md`、相关 `.agents/skills` 和开发规范。设计前读取 [开发规范](references/development-rules.md)，结合项目已有规范逐条判定适用性；引用已有权威规范，不复制维护多份。冲突会影响设计时列出来源与影响，返回澄清。

场景用 `featNN 场景M` 回指（如 `feat02 场景3`），已有 Scenario ID 时沿用；关键约束用 spec 的 C 编号回指，不复制概述或 GIVEN/WHEN/THEN。发现功能行为、边界或数据含义存在歧义，向用户报告具体回指、分歧和影响，交回需求澄清；不得用技术假设补完产品行为。可继续调查不受影响的现状，受影响设计标为阻塞，不能宣称整体可交接。

C、D、用例 T 是追溯元数据示例，各自在约束、设计、用例范围内唯一；已有 ID、章节定位及链接锚点沿用，不为了重组正文改号。正文以功能和描述性中文名称组织，稳定 ID 放元数据或追溯附录，供 req/dev/verify 定位，用户阅读和确认方案无需记住这些编号。旧 spec 没有 C 章节时从已确认场景和现有约束提取依据，不新造用户决定；新增约束先交 x-spec 确认。

### 2. 调查现有架构

围绕 spec 范围读取现有目录、模块公开入口、依赖、协议/schema、数据读写、配置与测试。区分“代码当前如此”“用户已确认”“本轮建议”，为现状和复用结论给出可定位的文件/符号证据，不把建议写成既成事实。

优先复用现有模块、技术栈与权威协议。新增模块、引入技术或替换现有方案时，说明现有方案为何不足，以及依赖、调用方、数据迁移、兼容性与维护成本的影响；只写本需求涉及的影响，不借机重构全仓。

### 3. 编写技术设计

读取 [精简模板](templates/tech-design.md)，按本次新增或修改的 feat 组织正文，每节用功能名称作标题并回指 spec。先说明本轮设计差异与代码依据，已有不变设计引用原出处，需求正文和 GWT 留在 spec；共享模块、结构和协议只定义一份，由相关功能引用。feat 按功能划分，模块可服务多个 feat。

每个 feat 就近按以下顺序说明，适用内容可以合并，简单改动删除无关小节并简短说明依据：

1. **方案与理由**：准备怎么做、为什么这样做、沿用和新增什么；关键选择的备选、代价、兼容/迁移影响及待确认项放在相应功能旁。
2. **职责、数据流与失败处理**：具体模块/目录、公开入口、调用方、允许依赖和禁止越界处；从入口、边界校验到处理、状态变化/持久化、返回的路径。按实际风险讲清异步完成、重复请求、并发、取消或恢复，检查单向依赖与循环。调用顺序复杂时就近放 Mermaid 时序图，数据流难以讲清时可用 flowchart；简单改动用文字即可，不硬凑图。
3. **关键数据结构与配置（按需）**：本轮新增/变化的结构、重要字段含义及适用约束（可空性、单位、标识、关系、不变量），数据所有者、值的权威存储；派生值及缓存/索引/快照的更新、失效、重建策略。具名配置写清单位、默认值依据和使用位置。未变定义只链接原 schema/设计；新结构写设计示意及正式实现的计划位置，落地后改为权威引用。
4. **API、事件或网络协议（按需）**：先讲功能用途，再给生产者/消费者、输入、输出及错误行为，包含校验边界、权威来源；跨语言说明生成/同步和漂移检查。只展开本轮涉及的变化，简单改动不强造接口或协议。
5. **测试场景与预期**：在该 feat 的方案后就近放描述性中文场景名称，最少写依据（spec 场景/已确认约束和相应设计）、前提/触发、预期结果、禁止结果、拟验证层级或证据及局限。用户已给具体场景时回指其 GWT，只展开测试安排；按相关风险选正常、边界、失败、重复、并发、取消、恢复等，不机械套全套。人工观察/代码审查说明证据和局限；尚未确认或机制不可行时列阻塞，不从实现推断预期或放宽标准。

共享测试在最相关 feat 的测试节或按需设置的“共享测试场景”中只定义一次。其他 feat 用“中文名称 + 链接”引用，并明确该场景在本 feat 中实际验证的结果及禁止结果（可链接主定义的对应断言/观察点）；一次经过某 feat 的流程不代表验证了它。设计、约束、场景与用例可以多对多，一个约束也可有多个测试；按能观察目标行为的层级取证，不强制把所有功能串成一个巨型 E2E，测试全绿不等于全部需求覆盖。

例如（仅为写法示意）：在“发送消息”的方案旁说明幂等或结果核对机制，用“发送成功但回执丢失后，重试仍只发送一条”作测试场景名。前提是服务端已成功且回执丢失，触发同一次发送重试；预期最终只有一条且取得该次结果，禁止再次产生发送副作用；拟用保留真实去重/核对路径的集成测试观察记录与结果。结果未知不能假定失败后无条件重发。场景的追溯元数据保留 C1、D01、用例 T1 及 spec 回指，中文标题承担阅读说明。

设计与用例新增条目仍分配稳定 ID（如 D01、用例 T1），沿用已有编号且不重排或复用；“用例 T1”与 checklist 任务行 T1 分别定位。正文元数据或附录登记 ID、中文名称、唯一主定义位置、spec 场景/约束来源、适用 feat 与各自结果/证据位置。附录仅索引定义和证据，不复制维护另一份测试正文；新增用例补在其主定义处，重组时保留既有锚点或提供有效定位，后续 req/dev/verify 仍可按路径和 ID 精确回指。

规范的适用性、设计落实位置和验证依据可在功能旁说明，共用规范 R1–R7 及项目附加规则在附录汇总覆盖。小改动只展开受影响的模块、结构/协议、流程、决策与测试，其余注明“沿用 + 来源”。

### 4. 检查并交付草案

- 正文和交付讲解是否用大白话说明做法、理由、数据流转与失败处理，必要术语是否首次解释，精确技术定义与验收依据是否保留且一致？
- 本轮新增/修改的每个 feat 以功能名称组织，方案、理由、相关结构/协议与中文测试场景就近可读；场景回指真实存在，适用项能追到模块、流程与验证，未变设计有原出处。
- 每条已确认关键约束都有机制和完整用例依据；共享测试只有一份主定义，各 feat 的结果/禁止结果有真实断言或观察点，经过流程不冒充覆盖，未覆盖项及证据局限明确。
- ID 仅作元数据/附录追溯，既有编号与定位有效，req/dev/verify 可按原契约找到设计、用例主定义和各自证据；附录未重复维护测试正文。
- 模块公开接口、数据所有者、协议来源与数据流相互一致；所有新增/替换有复用调查及影响依据。
- [开发规范](references/development-rules.md) 中每条规则及项目附加规则都有“适用/不适用 + 原因”，适用规则有落实位置和验证依据。
- 区分已执行检查、代码阅读证据与计划在实现阶段执行的测试。没有实现时写明预期判定标准，不伪造通过结果，不为产出证据先写业务实现或安装工具。
- 所有关键问题、阻塞及草案状态清楚；模板注释、占位符和空示例已删除。

交付摘要包含：输出路径、spec 基线与确认依据、覆盖的 feat/场景和设计差异、主要复用/新增决策、待用户确认问题（含推荐及影响）、验证结果与未验证项、是否具备交接条件。无待选方案也要请用户审查草案，不能自动标为已确认。

## 确认与 x-req 对接契约

技术方案先输出为待确认草案。用户确认关键架构、协议、数据归属及影响方案后，记录实际确认结论、来源与对应设计版本/条目；只确认部分时保留剩余待确认项，不能宣称整体已确认。普通函数、局部变量等实现细节由开发者按已确认设计决定，无需逐项交给用户审批。

通过本技能交接给 req 拆任务时，提供：已确认的 spec 路径/基线、`tech-design.md` 路径/基线及关键条目的确认依据、适用 C 编号、D 机制与用例编号的映射及已知阻塞。任务继续回指 spec 场景，技术安排引用设计条目，不复制维护协议或设计正文。关键设计未确认或功能歧义未解决时，本技能不得宣告可交接。

本技能是主线必经环节：`x-req` 的就绪检查要求同目录存在关键条目已确认的 `tech-design.md`，否则阻断拆解。本技能仍不自动调用 x-req、不创建任务、不编写业务实现。后续实现若需改变已确认的重大架构、协议或数据归属，先更新受影响设计并请求用户确认，再按新结论实施。

## spec 后续变更

对照记录的 spec 基线分析变化。纯措辞且行为、数据、接口均未改变时，记录影响判断即可，不重做设计。行为、数据或接口变化时，先列出受影响场景、设计编号和已有任务路径/编号（尚未拆任务则注明）；变更后的功能 spec 未确认时只报告影响和待澄清项，确认后再更新相关设计。关键决策变更标为待确认，已确认且不受影响的条目保留。缺少旧基线时如实报告无法完整判断，不把旧确认套用到新内容，也不自动改写后续任务。
