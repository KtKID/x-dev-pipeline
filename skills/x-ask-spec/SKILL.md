# x-ask-spec

这个 skill 的主体是**讨论**，不是写文档。agent 要像苏格拉底那样，通过提问帮用户把需求想清楚：不等用户把话说完就开写，而是主动问、追着问，直到双方对“要做什么、做到什么程度算完”没有疑问。讨论清楚之后，结论才落进 spec。

一份 spec 管一块数据，长期维护在 `docs/spec/<spec名>/spec.md`；按什么划分见 [spec 范围](references/spec-scope.md)。

## 1. 先看现状

先运行 `date -u +%Y-%m-%dT%H:%M:%SZ` 记下开始时间，这一期的 token 用量从这里算起（见 [token 用量](../x-dev/references/test-reporting.md#token-用量)）。

读用户的要求、`docs/spec/README.md` 边界表和相关 spec、相关代码或界面，弄清现在实际怎么做、已经定过什么。代码和已有 spec 能回答的，不拿去问用户。

## 2. 苏格拉底式讨论：agent 主动问，直到没有疑问

这一步不能跳过。用户的第一句话通常只是一个想法，agent 的任务是把它问成一个能验收的需求。

**每一轮这样做：**

1. **复述理解。** 用大白话说出你现在理解的需求：给谁用、他要做什么、做完他能看到什么。让用户能一眼看出你哪里理解偏了。
2. **列出还没想清楚的地方。** 逐项过一遍下面五类，每类要么已经有答案（写明答案从哪来），要么列成问题：
   - **正常情况**：最常见的那次使用，输入什么、看到什么。
   - **边界**：数量的上下限、空的情况、刚好卡在临界值的情况。
   - **出错**：输错了、没权限、网络断了、做到一半失败了，用户看到什么、数据变成什么样。
   - **不做什么**：这次明确不管的事，免得做多。
   - **怎么算做完**：用什么具体结果判断这次做对了。
3. **提问。** 每轮问 2–3 个最影响结果的问题，不要一次甩一长串。能给选项就给 2–3 个选项，并说清每个选项的结果有什么不同；问经历或具体数字时用开放问题。需要用户选择时，用宿主提供的选项式提问工具（如 `AskUserQuestion`、`request_user_input`），只支持对话时直接问。
4. **用回答追问下一层。** 用户的回答常常带出新问题（比如“导出全部”就会带出“几万条怎么办”）。把新结论加进复述，再看还有什么没清楚，接着问。

**提问的规矩：**

- 一个问题只问一件事，用具体例子问。比如不问“导出范围是什么”，而问“列表有 80 条、当前页显示 20 条，导出的是这 20 条还是全部 80 条？”
- 用户已经说清楚的、代码或已有 spec 里查得到的，不重复问，直接写明答案和来源。
- 用户的回答和已有约定冲突时，指出冲突，请用户决定。
- 以用户实际给出的回答为准。没回答、跳过、只是默认选中的，都算没定。用户明确跳过或没接话的问题，不再追着问；记为没定，最后写进 spec 的「待决项」，不挡住其他已经清楚的部分。

**什么时候结束讨论：** 五类里每个问题要么有答案，要么被用户明确留成没定；agent 能说出“我没有要问的了”，把最终复述（连同没定的事）给用户看，用户认可。用户只想讨论、不要文档时，在对话里给出结论就结束。

## 3. 一期最多 5 个 feat

按使用者能独立认出来的功能分 feat；同一功能的正常路径、边界和出错处理归在同一个 feat 里。

讨论下来如果超过 5 个 feat：

- 和用户一起选出本期最重要的 5 个，标“1 期”。剩下的按先后标“2 期”“3 期”，写进同一份 spec，但只写名称、一句话用途和已经确认的要点，不展开场景。
- 明确告诉用户：本期只做这 5 个，其余放进后续迭代，等本期交付后再讨论。
- 已经交付（已验收、已退役）的 feat 不算在内。`xdev validate <spec 目录>` 会检查同一期里没交付的 feat 不超过 5 个。

## 4. 写进 spec

讨论结论落盘的规则：

**先定归属。** 按 [spec 范围](references/spec-scope.md) 逐条场景问“变化的是谁的数据”，得出每条场景的去处（加到已有 / 新建 / 只记变更 / 问用户）。写入前在对话里列出归属表（spec、去处、场景），和这批 spec 增量一起给用户确认。

spec 写好后，运行 `xdev usage start <spec.md> --phase "<N 期>" --what "<功能>：讨论到验收" --since <第 1 节记下的时间>` 在「用量」表加一行。

**新建**用 [spec 模板](templates/spec.md)；**已有文档**先读全文，定位相应 feat、场景和约束，再局部修改：

1. **只写讨论清楚的。** 一条行为的前提、操作和结果都定了才写；还没定的写进「待决项」，注明卡住了什么。
2. **改原定义，编号不变。** 已有行为直接改原场景；新增功能接着用下一个 feat 编号，新增场景接着用所属 feat 的下一个场景编号。删掉的功能留一条带原编号的退役记录和移除后的要求。
3. **场景用 GIVEN / WHEN / THEN** 写前提、操作、看得到的结果。每条新增或改过的场景写一行 `依据与价值：<用户哪句话或哪条已有约定>；<它对目标或验收有什么用>。`
4. **约束写进「关键约束」表**，编号 C1、C2，只在一处写正文。约束只是任务的一部分，只规定“怎么做、不许怎么做”；要做的事在场景里。用户对代码怎么组织的要求（分层、依赖、选型、不许做的事）也是约束，开头写“架构：”；对全项目都成立的写进 `engineering` spec。
5. **标状态和期次。** 新确认的行为标“待实现”或“变更中”，已交付的沿用实际状态；每个 feat 写期次（1 期 / 2 期 / 3 期）。已有设计或任务的行为、约束变了，按 [需求变化同步](../x-tech-design/references/change-sync.md) 列出受影响的 D、T、任务行和测试。
6. **记变更。** 变更记录追加这一批新增、修改、退役了什么，依据哪句确认，当前状态。

写完核对一遍：写进去的和用户确认的一致，原有内容、约束和引用没有被误删。

## 5. 交接

交给 [x-tech-design](../x-tech-design/SKILL.md) 的内容：归属表、当前这一期（还有没交付 feat 的最小期次，通常是 1 期）要做的 feat 和场景、这批新增或修改的约束、影响清单（已有设计或任务时）、本期完成条件、还没定下来的事。后面几期的 feat 留在 spec 里，不往下传，等当前这一期交付后再回来讨论。

用户只要求写需求时，交付更新后的 spec 和待决项清单即可。
