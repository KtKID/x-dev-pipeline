# spec 范围：需求写进哪份 spec、什么时候新建

x-ask-spec 写需求、x-qdev 回写功能时都按本文决定归属。

## 一句话规则

**一份 spec 管一块数据（或一组对外承诺的输入输出）。一条行为写进哪份 spec，看这条行为改变的是谁的数据。**

不按代码目录分，不按页面分，也不按需求分。

## 为什么这样分

| 按什么分 | 会出什么问题 |
|---|---|
| 代码目录 | 一个功能横跨前端、接口、会话、存储好几个目录。按目录分，同一个"登录"行为会被拆进几份 spec。 |
| 页面 | 一个页面是好几个能力的入口：订单页同时展示订单、支付状态和通知设置。按页面分，同一个行为会在几份 spec 里各写一遍。 |
| 需求 | 需求是一次性的，spec 要长期维护。按需求分，每个需求一份 spec，过几个月同一块行为就散在十几份文件里。 |
| 数据 | 一份数据只有一个地方说了算，按它分，每条行为都只有一个归属。 |

没有自己数据的项目（命令行工具、库）按"对调用方承诺的输入输出"来分，比如"命令行参数解析与报错"。

## 边界表：判断归属的唯一依据

`docs/spec/README.md` 的索引表里每份 spec 占一行，必须写"拥有什么"和"不管什么"两列。spec 名用英文小写（它是目录名），表里可以在名字后面用括号注上中文：

```markdown
| Spec | 状态 | 拥有什么 | 不管什么 |
|---|---|---|---|
| auth（账号） | 在用 | 账号、密码、登录会话、权限判断 | 用户资料的展示与编辑 |
| order（订单） | 在用 | 订单的创建、状态流转、列表查询、导出 | 扣款与退款 |
| payment（支付） | 在用 | 扣款、退款、支付记录 | 订单状态 |
| notify（通知） | 在用 | 通知类型、模板、发送渠道、发送记录 | 什么时候该发（由调用方决定） |
| engineering（工程） | 在用 | 构建、依赖、CI、部署脚本、对全项目都成立的架构约束 | 任何使用者能看到的行为 |
```

- "拥有什么"写名词，也就是数据、状态或对外的输入输出，不写目录。
- "不管什么"写最容易被误放进来的相邻内容。
- 旧项目的表里没有这两列时，先读各份 spec 头部的用途说明，把推断出的边界补进表里。补的这几行随本次 spec 一起给用户确认。

## 四种去处

| 去处 | 意思 |
|---|---|
| **加到已有** | 在一份已有 spec 里新增 feat、场景或 C，或修改原有的 |
| **新建** | 新建一份 spec 并写场景，同时在边界表加一行 |
| **只记变更** | 不写场景，只在这份 spec 的变更记录里记一行 |
| **问用户** | 规则判断不了（比如边界表两行重叠），先停下来问，问完再按前三种处理 |

只在主 spec 的 C 里写一句依赖、自己不写场景的 spec，不算去处。

## 判断步骤（逐条场景判断，不是逐个需求判断）

1. 把需求写成场景（GIVEN / WHEN / THEN）。**一条场景的结果改了两块数据，先拆成两条场景**，再分别判断。
2. 对每条场景问一句：**THEN 里变化的是谁的数据或状态？** 只是查询或展示、什么都没改的场景，问：**展示的是谁的数据？** 没有数据的项目问：变化的是哪一组对外输入输出？
3. 拿这个答案去边界表的"拥有什么"列里找：
   - 找到一行 → **加到已有**。
   - 答案落在某一行的"不管什么"里 → 不是这一行，继续找其他行。
   - 所有行都找不到 → **新建**，同时在边界表里加一行。
   - 有两行都说拥有它 → 边界表本身写重了。**停下来问用户**该归哪一份，并把边界表改清楚，不要自己挑。
4. 一个需求的场景落到几份 spec，就写几份。同一个需求不要求放在同一份 spec 里。
5. 另一个领域只是被调用 → 看它对调用方的输入输出变没变：
   - 没变（照原样调用） → 那份 spec 不动，只在主 spec 的 C 里写一句依赖。
   - 变了（新增一种类型、多接收一个参数、多返回一个字段） → 它也要**加到已有**，写清新的输入输出。调用方的代码要跟着改、但它自己的行为没变时，调用方的 spec 不动。
6. 不改变任何使用者可见行为的工程改动（构建、依赖、CI、挪目录）→ `engineering` **只记变更**。
7. 只改外观或文案 → 所属 spec **只记变更**。怎么区分外观和行为：使用者能做的事、能看到的信息变了，就是行为（隐藏一个按钮、去掉一列、改默认值）；只是样子变了才是外观（颜色、间距、按钮文字、错别字）。
8. 修 bug：所属 spec 里已有场景写明了正确行为 → **只记变更**；spec 里没写这条行为 → **加到已有**，补上这条场景。spec 里写的行为本身就不对（用户要的和 spec 写的不一样）→ 这不算修 bug，是**加到已有**里修改原场景。

列完归属表后核对一遍：每条场景都有去处；判断理由里提到要改的每份 spec 都在表里。

**新建 spec 只有一个条件：第 3 步所有行都找不到所有者。** 不能因为"这个需求比较大""单独放更干净"就新建；也不能因为"不想多一份文件"，就硬塞进一份并不拥有这块数据的 spec。

新 spec 用它拥有的数据命名（`coupon`、`profile`），英文小写加横线。不用需求名（`add-coupon-2026`），也不用页面名（`settings-page`）。

## 跨多份 spec 时，task 和技术设计放哪

- task 和 tech-design 放在**主场景**所在的 spec。主场景是使用者直接操作的那一条；没有使用者直接操作时（定时任务、系统自动触发），放在写场景最多的那份 spec；一样多时，放在边界表里排得靠前的那份。
- 其他 spec 的场景在 task、checklist 里回指时带 spec 名前缀，比如 `fine:feat01 场景2`，免得不同 spec 的 feat 编号重号。
- `engineering` 是边界表里固定的一行，预先放好。第一次用到时按模板建最小 spec，不需要用户确认，因为它只记变更、不写场景。
- 用户说出的架构要求（分层、依赖、选型、不许做的事）是一种约束，写进关键约束表，开头写“架构：”：只管一块数据的写进那份 spec，对全项目都成立的写进 `engineering`。内容只来自用户说过的话，写进去时注明来源。
- 往 `engineering` 里新增或修改约束，算“加到已有”，要给用户确认（和别的 spec 加约束一样）。“第一次建不需要确认”只指模板骨架加变更记录行；骨架里同时写了约束，这条约束照样要确认。`engineering` 的约束没有关联场景，“确认依据 / 关联场景”列写来源加“全项目”。
- 任务行、派工单里引用别的 spec 的约束，也带 spec 名前缀，比如 `engineering:C1`，免得和本 spec 的 `C1` 撞号；`xdev validate` 会去那份 spec 里核对。

## 拆分与合并：单独整理，不在做需求时顺手做

- **该拆的信号**：一份 spec 超过大约 10 个 feat，或者里面有两组 feat 从来不会被同一个 task 一起引用。
- **该合的信号**：两份 spec 最近的 task 几乎都是同时改这两份。

拆分和合并是单独的整理任务，需要用户确认。做需求时只按现有边界表判断归属，发现信号就在交付时提一句。

## 正反例子

下面的例子都按上面那张边界表判断。

| # | 需求 | ✅ 正确做法 | ❌ 常见错误 | 为什么 |
|---|---|---|---|---|
| 1 | 登录失败时，区分"密码错误"和"账号已锁定" | 加到已有 auth | 新建 `login-error-msg` | 改的是登录结果，归 auth。按需求新建会让 auth 的行为散到别处。 |
| 2 | 登录页加"记住我"（代码在 `web/pages/login/`） | 加到已有 auth | 新建 `login-page` | 记住我改变的是会话保持时长，会话归 auth。页面只是入口。 |
| 3 | 订单导出完成后发一条站内通知，用现有的"通用提醒"类型 | 加到已有 order，并在 order 的 C 里写"导出完成后调用 notify 通用提醒"；notify 不动 | notify 里也加一条场景 | notify 的输入输出没变，它只是被调用。 |
| 4 | 同上，但要新增一种"导出完成"通知，模板里带下载链接 | 加到已有 order（导出完成时触发）+ 加到已有 notify（新类型和模板） | 全部写进 order | 新增了一种通知类型，notify 对调用方的输入输出变了。 |
| 5 | 用户申请退款后钱原路退回，订单变成"已退款" | 加到已有 payment（退款）+ 加到已有 order（状态变化） | 只写进 order | 退钱改的是 payment 的数据，订单状态改的是 order 的数据，一条需求分两份。 |
| 6 | 订单列表可以按支付状态筛选 | 只加到已有 order | payment 里也加一条场景 | 列表查询归 order；支付状态只是被读取，payment 的行为没变。 |
| 7 | 用户资料页显示头像 | 新建 `profile`，边界表加一行 | 塞进 auth（"反正都和用户有关"） | auth 的"不管什么"写明了资料展示不归它，其他行也找不到所有者。 |
| 8 | 用户可以领取优惠券，并在个人中心看到自己的券 | 新建 `coupon`，边界表加一行 | 塞进 order 或 payment | 券和领取记录是一块新数据，表里没有任何一行拥有它。 |
| 9 | 构建工具从 webpack 换成 vite | engineering 只记变更 | 新建 `build` 并写场景 | 使用者看不到变化，不写场景。 |
| 10 | 订单页按钮颜色改成主题色 | order 只记变更 | 加一条场景"按钮是蓝色" | 只改外观、不改行为。 |
| 11 | 修 bug：导出的文件名乱码，order 里已有场景写明文件名格式 | order 只记变更 | 再加一条一样的场景 | 正确行为已经写在 spec 里，修 bug 只是让代码符合它。 |
| 12 | 订单页去掉"批量导出"按钮，用户不能再批量导出 | 加到已有 order，修改或退役原场景 | 当成外观只记变更 | 用户能做的事变了，是行为。 |
| 13 | 一条场景写成"退款成功后，钱退回并且订单变成已退款" | 先拆成两条场景，再分别加到 payment 和 order | 整条放进 order | 一条场景改了两块数据，要先拆开。 |
| 14 | order 的 spec 写着"导出最多 1000 条"，用户说一直应该是 5000 条 | 加到已有 order，修改原场景 | 当成修 bug 只记变更 | spec 写的就不是用户要的，这是需求修改。 |
