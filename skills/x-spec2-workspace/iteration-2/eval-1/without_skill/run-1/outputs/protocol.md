# 会话与传输协议需求

## 1. 传输约束

- 设备与网关建立一条 TLS 加密、已认证、双向长连接。
- 控制消息采用可版本化的结构化编码；音频数据采用带固定头的二进制帧，避免逐帧文本编码开销。
- 单条连接内可交错发送控制消息、上行音频和下行音频；接收端分别进入有界队列。
- 协议握手协商版本、上/下行编解码、采样率、声道、帧时长、最大消息尺寸、心跳间隔和恢复能力。
- 未知可选字段应被忽略；未知必需消息类型或不兼容主版本应被显式拒绝。

## 2. 消息公共头

每条控制消息和音频帧都应携带适用的公共信息：

| 字段 | 用途 | 约束 |
|---|---|---|
| `protocol_version` | 协议兼容性 | 主版本不兼容时拒绝 |
| `message_type` | 路由与解码 | 枚举，未知必需类型报错 |
| `device_id` | 设备身份 | 由认证上下文校验，客户端不可冒用 |
| `session_id` | 业务会话 | 恢复成功时跨连接保持 |
| `connection_id` | 传输连接 | 每次握手生成 |
| `trace_id` | 端到端关联 | 每个话轮生成，响应继承 |
| `utterance_id` | 上行话轮 | 上行与 ASR 消息必需 |
| `response_id` | 下行响应 | TTS 与播放消息必需 |
| `generation` | 播放代际 | 所有下行帧和取消消息必需 |
| `seq` | 流内序号 | 从 0 单调递增，不复用 |
| `monotonic_ms` | 设备内事件定序 | 基于本次启动的单调时钟 |

## 3. 控制消息目录

| 消息 | 方向 | 最小语义 |
|---|---|---|
| `hello` | 设备→服务端 | 设备/固件/启动标识、能力、恢复请求、认证证明 |
| `welcome` | 服务端→设备 | 协议和音频参数、会话结果、限制、服务端时间 |
| `heartbeat` / `heartbeat_ack` | 双向 | 活性、往返时间、当前状态摘要 |
| `listen_start` | 设备→服务端 | 新话轮、触发来源、generation、音频参数 |
| `audio_ack` | 服务端→设备 | 最大连续接收序号与可选接收窗口 |
| `audio_end` | 设备→服务端 | 最后序号、端点原因、采集时长、丢帧计数 |
| `asr_final` | 服务端→设备 | 最终文本、语言、置信信息、终态 |
| `tts_start` | 服务端→设备 | response、generation、格式、预计或未知总长 |
| `tts_end` | 服务端→设备 | 最后序号、合成终态、总时长 |
| `playback_progress` | 设备→服务端 | 连续接收序号、已播放时间、缓冲水位 |
| `playback_end` | 设备→服务端 | 完成、打断、解码失败或不可恢复欠载 |
| `cancel` | 设备→服务端 | 目标 response/utterance、generation、原因、事件时间 |
| `cancel_ack` | 服务端→设备 | 目标的稳定终态与处理时间 |
| `error` | 双向 | 稳定错误码、作用域、可恢复性、建议动作、关联标识 |
| `flow_control` | 双向 | 接收窗口、暂停/恢复和队列水位提示 |

## 4. 音频帧契约

### 4.1 上行帧

上行帧至少包含 `utterance_id`、`seq`、采集起始偏移、有效时长、编码类型、负载长度和音频负载。服务端应：

- 按序号去重并维护最大连续确认点。
- 在允许的乱序窗口内暂存，超出窗口后报告缺口。
- 拒绝属于已结束、已取消或未知话轮的帧。
- 对格式变化、超长帧、校验失败和时间戳倒退产生稳定错误码。

### 4.2 下行帧

下行帧至少包含 `response_id`、`generation`、`seq`、播放起始偏移、有效时长、编码类型、负载长度和音频负载。设备应按以下顺序校验：

1. 会话仍有效。
2. `generation` 等于本地当前代际。
3. `response_id` 等于当前响应。
4. 序号位于接收窗口内且未处理。
5. 编码参数与 `tts_start` 一致。

任一身份或代际校验失败时直接丢弃负载，并只增加聚合计数，避免日志风暴。

## 5. 幂等、顺序与终态

- `listen_start` 以 `session_id + utterance_id` 幂等；重复消息返回当前状态。
- 同一话轮最多有一个被系统接受的 `audio_end` 和 `asr_final`。
- `cancel` 可在目标完成前后重复调用，响应始终返回目标已知终态。
- `tts_start`、音频帧和 `tts_end` 只对匹配的 `response_id/generation` 生效。
- 终态具有单向性：`active → completed | cancelled | timed_out | failed | connection_lost`，终态之间不互相覆盖。
- 服务端保存终态至少覆盖会话恢复窗口，以消解重试和迟到回调。

## 6. 恢复握手

设备 `hello` 中的恢复摘要包括：

- 上一 `session_id` 与设备启动标识。
- 当前设备主状态和 `generation`。
- 活动 `utterance_id`、最后发送序号、最后确认序号。
- 活动 `response_id`、最后接收序号、已播放位置。

服务端按目标分别返回：

| 结果 | 语义 | 设备动作 |
|---|---|---|
| `resumed` | 上下文和缓存完整，可继续 | 从指定确认点重放或续收 |
| `restart_utterance` | 连接恢复成功，当前话轮无法完整恢复 | 终止当前话轮，提示用户重新唤醒 |
| `reset_session` | 会话不存在、过期或身份不匹配 | 清理所有业务状态，创建新会话并回到 `READY` |

恢复结果必须包含服务端确认点和明确原因。任何缺失或矛盾的确认点均按更保守的终止路径处理。

## 7. 背压与容量

- 服务端通过接收窗口限制上行未确认帧数量；设备达到窗口上限时暂停发送并继续在本地有界缓冲。
- 本地采集缓冲达到硬上限时终止本话轮，错误范围为 `utterance`。
- 设备通过播放进度报告下行水位；服务端限制领先于播放位置的音频时长。
- 播放缓冲低于最低水位时允许短暂停播等待；连续欠载达到阈值后终止响应并报告原因。
- 遥测使用独立低优先级队列，拥塞时按聚合策略丢弃细粒度事件，保留错误与终态。

## 8. 错误分类

| 分类 | 示例 | 作用域 | 期望动作 |
|---|---|---|---|
| `AUTH_*` | 令牌失效、设备禁用 | 连接/设备 | 停止快速重试，进入降级并请求重新认证 |
| `PROTOCOL_*` | 版本不兼容、非法状态、帧过大 | 消息/连接 | 拒绝消息；严重错误关闭连接 |
| `AUDIO_*` | 编码不支持、序号缺口、采集溢出 | 话轮/响应 | 终止当前流并回到可用状态 |
| `ASR_*` | 超时、供应商不可用 | 话轮 | 终止话轮并向设备返回可恢复提示 |
| `RESPONSE_*` | 生成超时、内容拒绝 | 响应 | 使用已批准的降级文本或终止响应 |
| `TTS_*` | 首帧超时、中途失败 | 响应 | 终止播放，清理缓存，允许新话轮 |
| `NETWORK_*` | 心跳超时、连接关闭 | 连接 | 进入有界重连和恢复握手 |
| `RESOURCE_*` | 队列满、限流、内存水位过高 | 对应资源 | 执行背压、降级或终止当前业务对象 |

错误消息不得包含认证材料、原始音频或未脱敏文本。
