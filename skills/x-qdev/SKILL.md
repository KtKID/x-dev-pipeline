# x-qdev — 轻量级快速开发

x-qdev 用最短可靠路径完成小改动。正确性依据来自用户原始请求、既有代码契约、实际 diff 和真实运行证据。

## 工作流程

```text
保存用户原始请求 → 提取 DoD/假设 → 风险分级 → 实现 → 定向验证 → DoD 证据闭环 → 完成或升级
```

## 第一步：理解任务并分级

1. 把用户原始请求逐字保存到任务 README，作为本次任务的第一事实源；凭据、令牌和隐私数据用 `[REDACTED]` 占位。
2. 从用户请求、既有公开契约、调用方和测试中提取 1-5 条 DoD。
3. 把 agent 补充的判断写入“假设”，并标明依据。
4. 检查相关 `docs/` 模块文档和实际代码入口，确认改动边界。
5. 识别会改变 DoD、公开行为或数据语义的歧义，在开发前向用户集中确认。
6. 开发前记录工作区基线：`git status --short`、`git diff --name-only`、`git diff --stat`、未跟踪路径和与任务预期文件重叠的既有改动。
7. 选择风险等级和审查路线。

### 风险等级

| 等级 | 适用条件 | 收尾方式 |
|------|----------|----------|
| Q0 机械改动 | 文档、样式、局部配置、确定性替换；用户可见行为边界稳定 | 主 agent 验证并完成 |
| Q1 标准 qdev | 单模块、入口清楚、有定向测试或可靠人工验收 | 主 agent 证据闭环并完成 |
| Q2 加强审查 | 存在已明示的低影响实现假设、修改已有核心函数、测试覆盖关系不清、存在多个重要失败路径 | 主 agent 验证后派一个综合 reviewer |
| Q3 完整流程 | 鉴权/权限、不可逆数据写入、迁移、公开 API/事件协议/schema、并发/缓存/状态机、跨模块架构、缺少可靠验证方式 | 升级到 x-req → x-dev 完整流程 |

用户明确要求 `x-verify`、`x-qa-gate` 或完整门禁时，按用户指定路线执行，并改用 `skills/x-dev/templates/dev-report-template.md` 生成兼容 x-verify 的命令声明。

影响 DoD、公开行为或数据语义的歧义先由用户确认。低影响实现假设可以进入 Q2，并在 README 中保留来源和错误影响。

预计超过 2 小时或存在 5 条以上独立 DoD 时，在开发前按 Q3 升级，完整保留全部需求。

开发中出现范围扩张或 Q3 信号时，在 README 和 dev-report 写明升级原因，然后切换完整流程。

## 第二步：创建任务记录

在 `dev-pipeline/tasks/<功能名称>/` 下创建：

| 模板文件 | 对应产出 |
|---------|---------|
| `templates/README.md` | 原始请求、假设、风险等级、DoD、证据矩阵、开发清单 |
| `templates/dev-report.md` | 实际 diff、验证命令、DoD 证据和最终审查结论 |

状态和更新规则见 `references/execution-rules.md`。

## 第三步：执行开发

按 P0 → P1 → P2 顺序处理开发清单：

1. 开始任务：`⏳ → ▶️`。
2. 读取 README 引用的模块文档和相关代码入口。
3. 实现当前任务范围内的最小改动。
4. 实现结束：`▶️ → 🟡`。
5. 运行与当前改动直接相关的验证。
6. 验证通过：`🟡 → 🟢`；失败：`🟡 → 🔴 → 修复 → 🟡`。
7. 更新 README 证据矩阵；将实现、验证、风险或范围结论写入 dev-report。

### 子 agent 使用条件

主 agent 默认完成 qdev。以下条件同时成立时可并行派发开发子 agent：

- 当前环境和用户授权允许子 agent；
- 至少两个任务拥有清晰、互斥的文件或模块边界；
- 并行能显著缩短等待时间；
- 每个子任务都能获得自包含的原始请求、DoD、接口约束和验证要求。

子 agent 只修改分配范围并返回变更与验证证据。主 agent 统一检查实际 diff、更新任务记录并做最终判断。

## 第四步：建立验证证据

主 agent 在实现完成后执行：

1. 运行 `git diff --stat`、`git diff --name-only` 和相关文件 diff，对照任务起点基线确认新增范围。
2. 根据变更入口和调用方选择定向测试、build、lint 或人工验收步骤并真实执行一次。
3. 对行为改动验证至少一条用户可见成功路径。
4. 对包含错误分支、状态变化或外部依赖的改动验证至少一条关键失败路径。
5. 检查测试是否真正触发本次修改的行为路径或公开入口，期望结果是否独立于业务实现计算。
6. 把每条 DoD 映射到命令输出、测试、代码路径或人工验收结果。
7. 对起点基线中的重叠文件逐项确认用户既有 diff hunks 保持完整；证据不足时保持 blocked。
8. 基于 `templates/dev-report.md` 写最终报告。

证据强度按以下顺序判断：

```text
真实运行/用户可见验收 > 定向测试 > 公开契约与调用链 > 静态代码检查 > agent 自述
```

测试框架缺失时，记录 `no-test-framework: true`、原因和实际人工验收步骤。仅有 agent 自述的 DoD 保持未完成。

## 第五步：按风险收尾

### Q0 / Q1：主 agent 闭环

满足以下条件后，把清单从 🟢 更新为 ✅：

- 每条 DoD 都有真实证据；
- 实际 diff 与声明范围一致；
- 相关成功路径已验证；
- 适用的关键失败路径已验证；
- 工作区中的用户既有改动保持完整。

### Q2：一个综合 reviewer

派一个只读 reviewer，输入保持简洁且锚定原始事实：

```text
用户原始请求 + 明示假设 + 风险等级 + DoD 证据矩阵
+ git diff 获取命令 + 相关实现/测试路径 + dev-report 路径
```

reviewer 一次回答四个问题：

1. 实现是否满足用户原始请求和既有公开契约？
2. 实际 diff 是否保持任务边界？
3. 关键失败路径和状态副作用是否得到处理？
4. 测试是否真正触发改动行为路径或公开入口，并使用独立期望验证结果？

reviewer 输出 `pass/fail`、带文件位置的证据和 P0/P1 问题。判定规则：存在 P0，或存在尚未处置且会影响正确性的 P1 时为 fail；P0 为空且每条 P1 已修复、已有证据接受或已触发 Q3 升级时为 pass。主 agent 把 mini-report 和每条 P1 的处置追加到 `dev-report.md`。reviewer fail 后，主 agent 修复并重跑受影响证据，再续接同一个综合 reviewer 复审；连续两轮 fail、范围扩大或残余风险仍高时升级 Q3。

当前环境缺少子 agent 能力时，在 `dev-report.md` 标记 reviewer unavailable，并将任务升级 Q3 或保持 blocked 等待用户选择。Q2 完成状态始终需要综合 reviewer pass。

### Q3：升级完整流程

切换到 `x-req → x-dev → x-verify → x-qa-gate`：

1. 保留原 qdev task 目录和全部证据。
2. 新建 `<qdev-task-name>-full` task；用户指定名称时使用用户名称。
3. 在新 task README 写入 `source-qdev: dev-pipeline/tasks/<qdev-task-name>`。
4. x-req 读取原 qdev README 与 dev-report，重新确认需求并生成完整 README、dev-checklist 与按需 diagram。
5. 原 qdev README 记录升级目标路径，dev-report 结论写 `promoted-to-full-pipeline`。
6. 原 qdev 开发清单标记 `↗️ 已升级`，整体完成状态由新 full task 决定。

## 第六步：记录与汇报

README 记录需求、范围与升级路径；dev-report 记录实现、验证、修复和综合 reviewer 结论。

最终向用户汇报：完成内容、修改文件、风险等级、关键验证证据和审查路线。

## 第七步：提醒提交

开发完成后给出与实际改动匹配的提交建议。多个独立改动按范围拆分提交。

## 关键原则

- 用户原始请求保持原文，敏感内容明确脱敏，派生 DoD 和假设标注来源。
- 验证深度随风险和残余不确定性增长。
- 子 agent 只在能增加独立审查信息或显著并行收益时启用。
- 真实运行证据决定任务完成状态。
- qdev 保持单模块、短链路和轻量产物；高风险任务及时升级。
