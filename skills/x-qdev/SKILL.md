# x-qdev · 五规范快速开发

x-qdev 把一次需求变更视为对系统 S 施加变换 T 得到 S′，使其满足新性质并保持旧性质。以下五项规范覆盖「定义正确性」和「验证正确性」的完整闭环。每项规范有明确的产出位置和简化条件；不满足简化条件时必须完整执行，禁止凭直觉跳过。

## 五项规范

| 规范 | 要求 | 产出位置 | 简化条件 |
|---|---|---|---|
| **1. 目标与边界** | 写出可验证的目标和非目标，限定允许改动范围与禁止波及边界 | README `## 目标与边界` | 不允许简化，始终必填 |
| **2. 现状理解** | 动手前读懂 S 的相关切片：涉及模块、契约邻居、隐藏依赖、不变量来源 | README `## 现状理解` | 全新文件且无现有消费者 → 写"无现有 S 约束（纯新增）" |
| **3. 不变量** | 列出修改前后必须持续成立的规则，每条写明执行者和验证方式 | README `## 不变量` | 纯新增无现有行为 → 写"无现有行为需保持" |
| **4. 实现路径** | 把变换 T 切成可验证增量，每项绑定一个 DoD 和一条会失败的测试 | README `## 开发清单` | T 唯一或显然 → 单行"直接实现"，但仍要绑 DoD |
| **5. 测试** | 为每条 DoD 准备证据计划，开发后用真实运行结果填充证据 | README `## DoD 与证据` + `dev-report.md` | 不允许简化；Q0 可用人工验收替代定向测试 |

简化不是省略思考，是省略书写——前提是当前风险等级允许。风险升级时已简化的规范必须重新展开。

规范 1 定义正确性的子空间；规范 2 保证子空间约束基于真实 S；规范 3 和 5 是新性质与旧性质的经验性证明；规范 4 是变换 T 的可验证分解。小需求的 T 搜索空间小，五项规范足以覆盖；命中升级信号（见风险路由）时 T 的分解或不变量已超出单 skill 闭环能力，必须升级。

## 输入与产物

**作用域是单个 task**。task 目录约定为 `dev-pipeline/tasks/<task-name>/`，产物：

- `README.md`：必需。五项规范产出的载体，task 主文档。
- `dev-report.md`：收尾时产出。DoD 证据矩阵、实际验证命令、diff 审查、reviewer 结论。

README 顶部用 `> 创建时间` / `> 类型` / `> 风险等级` / `> 审查路线` 四行 frontmatter 标识 task。状态用清单表格内的 emoji 列表达，见 `references/execution-rules.md`。

## 风险路由

风险等级决定哪些规范必须完整执行、收尾走哪条路线。开发前预判一次，开发中遇到升级信号立即重判并更新 README。

| 等级 | 适用条件 | 必须完整执行的规范 | 收尾路线 |
|---|---|---|---|
| Q0 机械改动 | 文档、样式、局部配置、确定性替换；用户可见行为边界稳定 | 1、5 | 主 agent 验证并完成 |
| Q1 标准 qdev | 单模块、入口清楚、有定向测试或可靠人工验收 | 1、2、3、4、5（2、3 可极简）| 主 agent 证据闭环并完成 |
| Q2 加强审查 | 已明示的低影响实现假设、修改已有核心函数、测试覆盖关系不清、存在多个重要失败路径 | 1、2、3、4、5 全部完整 | 主 agent 验证后派一个综合 reviewer |
| Q3 完整流程 | 鉴权/权限、不可逆数据写入、迁移、公开 API/事件协议/schema、并发/缓存/状态机、跨模块架构、缺少可靠验证方式 | — | 升级到 x-req → x-dev 完整流程 |

用户显式指定 `x-verify`、`x-qa-gate` 或完整门禁时遵循用户路由。预估超过 2 小时或超过 5 个独立 DoD 时开发前升级为 Q3。

## 模型分流

五项规范的产出是模型无关的 IR；不同能力模型在「生成 IR」和「消费 IR」上分工。详见 `references/execution-rules.md`。

- **强模型（高能力）**：在规范 1→2→3→4→5 上游一次性生成五项规范产出 + 关键测试。判断密集，算力花在杠杆点。
- **弱模型（低能力）**：消费已生成的 IR，按规范 4 的开发清单逐项实现 + 过规范 5 的测试。机械执行，客观可验证。
- **单模型**：全程自己走。规范 2 现状理解必须先于规范 4 动手——这是塌方最常见点：没读懂 S 就写 T，规范 3 不变量保证落空。

证据强度排序：`真实运行/用户可见验收 > 定向测试 > 公开契约与调用链 > 静态代码检查 > agent 自述`。仅有 agent 自述的 DoD 标记为未完成。

## 执行流程

### 1. 保存原始请求并建立基线

逐字保存用户原始请求到 README `## 用户原始请求`，凭据/令牌/隐私替换为 `[REDACTED]`。运行 `git status --short` 和 `git diff --name-only` 记录起点基线，保护用户已有改动。

### 2. 填充五项规范（按顺序）

按 1→2→3→4→5 顺序填充 README：

1. **规范 1 目标与边界**：写出可观察、可验证的目标；非目标写明本次排除项；允许改动范围和禁止波及边界各列一行。
2. **规范 2 现状理解**：读取涉及的模块、函数、契约邻居、隐藏依赖和不变量来源。这一步不写代码，只建立 S 的相关切片模型。详见 `references/execution-rules.md` 的 orientation 方法。
3. **规范 3 不变量**：列出修改前后必须持续成立的规则，每条给出执行者和验证方式。
4. **规范 4 实现路径**：把 T 切成可验证增量，每项绑定一个 DoD 和一条会失败的测试。增量间有依赖排序，无依赖可并行。颗粒度由风险等级决定：Q0/Q1 可粗，Q2 必须细到单函数级。
5. **规范 5 测试**：DoD 证据表写出每条 DoD 的证据计划（测试命令、人工验收步骤或契约检查）。

影响 DoD、公开行为或数据语义的歧义**必须在开发前**由用户解决。低影响的实现假设可放入 Q2，在 README 明示假设表记录来源和错误影响。

### 3. 实现与定向验证

按规范 4 的清单逐项实现。每完成一项：

- 更新该项状态（⏳→▶️→🟡）。
- 运行该项绑定的测试，失败则状态置 🔴，按根因修复后回 🟡。
- 每项的测试必须能先于实现失败、实现后通过（TDD 红-绿）。

保持公开契约、失败路径和输入所有权；改动落在声明的允许范围内。扩展配置或 schema 时保留原始样本可运行，新增字段默认兼容。

### 4. DoD 证据闭环

全部清单项 🟢 后，写 `dev-report.md`：

- DoD 证据矩阵：每条 DoD 的实际证据类型、命令、结果。
- 实际验证命令表：命令、cwd、exit、关键输出。
- Diff 审查：基线对比、范围一致性、成功路径、关键失败路径、用户既有改动保护。

项目无测试框架时记录 `no-test-framework: true` + 原因 + 真实人工验收步骤。仅 agent 自述不算证据。

### 5. 风险路线收尾

- **Q0/Q1**：DoD 全绿后主 agent 自检完成条件，标 ✅。
- **Q2**：派一个综合 reviewer（只读、单轮、三 lens）。详见下文 Q2 协议。reviewer pass 后标 ✅。
- **Q3**：保留 README + dev-report 全部证据；创建 `<task-name>-full` 任务交 x-req；本 task 清单项标 `↗️ 已升级`，dev-report 结论写 `promoted-to-full-pipeline`。

## Q2 综合 reviewer 协议

reviewer 输入锚定为原始事实，单轮穷尽：

```
用户原始请求 + 明示假设 + 风险等级 + DoD 证据矩阵
+ git diff 命令 + 相关实现/测试路径 + dev-report 路径
```

reviewer 回答四问（对应 q1-intent / q2-correctness / q3-evidence 三 lens）：

1. 实现是否符合原始请求和公开契约？（q1-intent）
2. 实际 diff 是否保持在任务边界内？（q1-intent）
3. 关键失败路径和状态副作用是否处理？（q2-correctness）
4. 测试是否真实触达改动路径，断言是否独立于实现？（q3-evidence）

通过规则：P0 为空且每个 P1 已修复 / 有证据接受 / 触发 Q3 升级 → pass。存在 P0 或未处置的影响正确性的 P1 → fail。fail 后主 agent 修复、重跑受影响证据、再次交给同一 reviewer；连续 2 次 fail、范围扩大或残余风险高 → 升级 Q3。无子 agent 环境时标记 reviewer 不可用，转 Q3 或阻塞等用户。

## 边界约束

- **不跨任务**：一次调用只处理当前 task，不修其他任务范围的代码。
- **不扩大修改**：不"顺便"重构无关代码、改无关风格、补其他任务遗漏。
- **不吞错**：遇到文件不存在、行号错位等异常，在 dev-report 标记并继续，不静默跳过。
- **不绕过歧义**：影响 DoD 的歧义开发前问用户；低影响假设可记录后继续。

## 完成回执

```
✅ x-qdev 完成 · <task> · risk Q0/Q1 · DoD N/N · 改动文件 M
✅ x-qdev 完成 · <task> · risk Q2 · reviewer pass · DoD N/N · 改动文件 M
↗️ x-qdev 升级 · <task> → <task>-full · 升级原因：<触发信号>
```

回执后提示用户 git commit。本 task 走完风险路线即结束。
