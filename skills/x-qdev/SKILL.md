# x-qdev

小任务的轻量开发闭环：**找功能归属 → 更新功能定义 → 局部设计 → 测试与实现 → 验证 → 同步交付状态**。

功能文档维护当前行为，changelog 维护变化索引，task 记录每次改动的实现与证据。文档深度按任务复杂度展开，验证方式按风险选择。

## 1. 找到功能归属

先读用户要求、相关入口、代码和测试，再查相关 spec、技术设计与模块 README。按功能职责和实际调用关系判断归属，目录和名称作为查找线索。新增小功能落在既有 spec 的职责范围内时，直接补入该 spec 的功能正文。

| 已有资料 | 功能定义放在哪里 | task 放在哪里 |
|---|---|---|
| 已有相关 spec，或上层功能 spec 的职责范围包含本次变化 | 更新该 spec 的 feat/场景 | `docs/spec/<spec-name>/tasks/task-<task-name>.md` |
| 已查对应及上层 spec，尚无可归属 spec；已有模块 README/功能说明 | 更新模块说明中的功能章节 | `docs/task/task-<task-name>.md` |
| 所属模块已有代码，功能文档尚缺 | 在模块现有文档位置补一份最小功能说明，沿用项目命名习惯 | `docs/task/task-<task-name>.md` |

最小功能说明写清模块归属、本次行为的触发条件、可观察结果和相关边界，并提供稳定章节定位。补充范围围绕本次任务，其他历史功能沿用已有资料。

每项行为选定一处功能正文主定义；其他文档通过链接引用。task 的①记录本次变化和回指，功能定义随所属 spec/模块说明持续维护。

需求仍需探索时先澄清；跨模块协调、重大架构/公开协议/数据归属变更，以及鉴权、迁移、并发或不可逆操作等高风险工作，交接已查事实和待办，转 `x-spec → x-tech-design → x-req → x-dev`。

## 2. 更新功能正文和 changelog

在实现前确定本次承接范围，记录用户要求、确认依据及修改前的可读版本。用户已经明确的要求直接沿用；新增业务默认、歧义和关键决策集中澄清，普通局部实现由开发者决定。

| 变更类型 | 功能文档的处理 | task 的回指 |
|---|---|---|
| 新增 feat/场景 | 在所属功能正文中补充目标行为与相关边界；spec 沿用编号体系，模块说明采用稳定章节定位 | 新增定义的路径、编号/章节及本次范围 |
| 修改 feat/场景 | 更新原定义，保留稳定编号；实现恢复既有行为时沿用原定义 | 修改前版本、原定位、修改后定义及变化摘要 |
| 删除 feat/场景 | 从有效功能中移除，保留带原编号/定位的移除记录、历史来源和移除后的可观察要求 | 原版本/定位、当前移除记录和保留行为 |

新增编号接续已有序号，删除记录保留原编号，其他稳定编号继续沿用。共享约束 C 的正文留在原主定义；涉及其范围或判据变化时记录实际确认及受影响行为。

功能文档同时追加简短 changelog：**日期、变更类型、功能/场景、变化摘要、task 链接、状态**。沿用项目已有格式即可。task 回链到功能正文/移除记录，形成双向查找；changelog 中的摘要由正文提供行为依据。

实现前将目标变化标为待实现/变更中，保留需求基线；完成验证后同步当前行为和交付状态。验证失败、待澄清或证据缺失时保留实际状态。功能正文或验收标准后续变化时，记录来源及差异并重新对齐受影响设计、用例和证据。

## 3. 建 task，写局部设计和用例变化

完整读取 [任务模板](templates/task.md)，保持五段：**①需求与变更、②精简技术设计、③测试用例与变化、④技术实现、⑤验证结果**。篇幅按本次差异填写，删除占位符和空示例。

### ② 精简技术设计

先读相关代码、已有设计、项目规范及 [共用开发规范](../x-tech-design/references/development-rules.md)，再说明：

- 沿用的设计路径/条目及本次适用理由；局部补充方案、主要入口与调用/数据流程。
- 计划涉及文件、适用规范及落实/检查方式；共用依据可以合并引用。
- 方案对应的场景、移除要求或约束；需要编号时使用局部 D 编号，已有编号沿用。

已有权威设计以路径/ID 回指，局部补充方案在②维护。改变既有关键决策时先更新权威设计并取得实际确认，超出小任务边界时交回主线。需求、设计和用例预期在实现前保留可读基线；版本记录或内容哈希须能定位相应内容。

### ③ 测试用例与变化

从已确认承接范围、相关边界和既有不变量确定应覆盖集合，再列用例：

- 标出每项用例属于**新增、修改、删除或沿用回归**，记录代码位置/命令及变化依据；分别统计用例变化和需求覆盖。
- 已有设计用例主定义时回指路径/ID；局部用例在③定义前提、触发、预期结果及禁止结果，用稳定 T 编号定位。
- 删除功能时记录旧正向用例的退役依据，补充移除结果验证和保留功能回归；退役用例单列处置状态。
- 按风险选择 unit、smoke、e2e 或人工检查，覆盖本次行为、相关异常和不变量；普通小改动复用项目现有测试方式。

模块说明通过“路径＋稳定章节”回指；已有 feat/scene、C、D、用例 ID 沿用原定位。删除项通过“旧版本定义＋当前移除要求”核对，保留全部受影响要求的验证责任。

## 4. 执行并保留真实证据

1. 自动化新行为先写/调整测试，取得目标行为缺失或违约造成的有效红灯；环境、导入和测试自身故障先排除。已有满足或采用人工方式时记录实际取证理由、步骤和观察。
2. 按②范围实现，在④记录实际文件及与计划的差异。保留待验证机制的真实路径，其他替身说明边界；验收标准的变化追溯到功能/设计主定义。
3. 运行本次相关用例及既有功能回归，⑤记录工作目录、命令、代码/输入基线、退出码、实际执行/通过/失败/跳过数、关键输出或人工观察及证据位置。用例映射与测试框架的执行数量分别核对。
4. 对应每个承接场景、移除要求、适用约束及用例记录结果。取证后代码或相关输入变化时重跑受影响检查；失败、未执行、缺证据及局限分别保留。

## 5. 核对文档并接入公共验收

先自检：功能归属可定位；新增/修改/删除已回写正文；changelog 与 task 双向链接有效；五段记录、前后基线、设计与用例回指完整；需求覆盖、用例变化、实际执行与结论一致；计划和实际改动范围对应。

在本任务授权范围内依次显式调用：

| 技能 | 提供输入 | 取回结果 |
|---|---|---|
| [x-verify-spec](../x-verify-spec/SKILL.md) | task 路径；功能文档/移除记录、确认及前后基线；承接范围；设计/用例指针；⑤执行记录 | 功能来源、变更回写、覆盖、基线和证据的交付对账 |
| [x-verify-tech](../x-verify-tech/SKILL.md) | 项目根目录；②/外部设计及依据/基线；明确场景/章节/D/diff 范围；适用规范；检查权限与副作用边界 | 局部设计与规范的实际技术验收 |

⑤收录本轮实际回执及可定位证据。功能对账读取已有记录，技术验收运行相关检查；两类回执与开发测试证据分别保留。qdev 使用 skill 的单文档适配，CLI `xdev.py verify` 沿用既有契约包流程。

问题按来源补齐或修复，再重核受影响结论。缺输入、技能不可用、待澄清、失败或未验证时如实列项，保留已有通过的适用基线。

交付条件：功能文档及变更索引同步，本次验证和相关回归真实通过，交付对账通过，全部适用技术项通过；技术验收明确无适用项时记录逐项依据和实际结论。

```text
✅ x-qdev 完成 · <任务> · 功能文档已同步 · 新增/修改/删除项及用例变化已核对 · 本次验证与回归通过 · 对账通过 · 技术验收通过（或无适用项及依据）
```

存在未决项时输出“x-qdev 未完成”，列已完成内容、失败/阻塞/待补项及下一步。旧 task 沿原章节和编号核对已有记录，本轮缺少的设计、来源或证据按实际缺口补齐。
