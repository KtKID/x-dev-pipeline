# x-qdev

小任务的轻量开发闭环：**定归属 → 写 spec 增量并给用户确认 → 按需技术设计 → 测试与实现 → 验证 → 同步交付状态**。

功能文档维护当前行为，changelog 维护变化索引，task 记录每次改动的实现、用例对应、覆盖率和交付状态，原始证据放同目录的 `<task>-evidence/`。文档深度按任务复杂度展开，验证方式按风险选择。

## 默认协作方式：spec 确认一次，之后连续执行

qdev 只有一个停点：第 2 节写完 spec 增量后，展示给用户确认。用户确认后，技术设计、用例、实现、自检和公共验收由 agent 连续完成，中途不再停。只记变更、不写场景的改动不停（哪些情况算只记变更见 spec 范围规则第 6–8 步），用 1–3 句话告知改法后直接执行。

用户本轮明确的任务要求就是该范围内的需求依据和执行授权；已有明确结论直接沿用，普通实现选择由 agent 决定并记录。转入完整主线后，x-tech-design 与 x-req 按各自的交接规则执行（tech-design 不需要用户确认）。

除这个停点外，只在三种情况下提问：会实质改变业务结果、且无法从现有要求或惯例判断的歧义；超出已有授权的关键决策或操作；spec 范围规则要求问用户时（比如边界表两行重叠）。提问时说明具体差异、影响和需要用户决定的事项，已明确且独立的部分继续处理。交付时按第 6 节向用户说明结果。

## 1. 定归属：加到已有 spec，还是新建 spec

先用 [x-explore-for-spec](../x-explore-for-spec/SKILL.md) 核对目标、现状、范围、约束和验收条件，把这次要做的行为写成场景。然后按 [spec 范围规则](../x-explore-for-spec/references/spec-scope.md) **逐条场景**判断去处：加到已有、新建、只记变更，或者问用户。判断方法只写在那份文件里，这里不重复。

qdev 只多一条规则：去处决定写完 spec 后要不要停下来给用户确认。

| 去处 | 要不要给用户确认 |
|---|---|
| 加到已有（新增、修改或退役场景或 C） | 要 |
| 新建（连同边界表新行） | 要。第一次建 `engineering` 最小 spec（只有骨架和变更记录行）除外，它算只记变更；同时写进了约束就要确认 |
| 只记变更（spec 范围规则第 6–8 步列出的情况） | 不用 |
| 问用户（比如边界表两行重叠） | 先问，问完按上面三行走 |

- task 和技术设计放在哪份 spec，按 spec 范围规则的"跨多份 spec 时放哪"。task 路径为 `docs/spec/<spec-name>/tasks/task-<task-name>.md`；其他 spec 的场景在 task 各段回指时都带 spec 名前缀。
- 项目已有模块 README 或功能说明、但还没有 spec 时，新建的 spec 正文链到原文件，原文件原地维护。
- 历史 `docs/task/` 下的旧 task 保持原位，按原位置读取；不再新建 `docs/task/`。

开始写 spec 前，按 [风险规则](references/risk-rules.md) 逐条回答是或否。有一条答"是"就不走 qdev：交接已查事实和待办，转 `x-explore-for-spec → x-tech-design → x-req → x-dev`。

## 2. 写 spec 增量和 changelog，展示给用户确认

在实现前确定本次承接范围，记录用户要求、执行授权来源及修改前的可读版本。代码比较基线在开工时由 `xdev start` 记录（第 4 节）。本轮明确要求及已有结论直接沿用；现有产品惯例与授权目标足以确定的细节由 agent 决定并记录。

| 变更类型 | 功能文档的处理 | task 的回指 |
|---|---|---|
| 新增 feat/场景 | 在所属功能正文中补充目标行为与相关边界；spec 沿用编号体系，模块说明采用稳定章节定位 | 新增定义的路径、编号/章节及本次范围 |
| 修改 feat/场景 | 更新原定义，保留稳定编号 | 修改前版本、原定位、修改后定义及变化摘要 |
| 删除 feat/场景 | 从有效功能中移除，保留带原编号/定位的移除记录、历史来源和移除后的可观察要求 | 原版本/定位、当前移除记录和保留行为 |

新增编号接续已有序号，删除记录保留原编号，其他稳定编号继续沿用。共享约束 C 的正文留在原主定义；涉及其范围或判据变化时记录用户明确要求或实际确认及受影响行为，超出授权的变化先澄清。

功能文档同时追加简短 changelog：**日期、变更类型、功能/场景、变化摘要、task 链接、状态**。沿用项目已有格式即可。task 回链到功能正文/移除记录，形成双向查找；changelog 中的摘要由正文提供行为依据。

写完后**停下来给用户确认**，一条消息里给出：

1. **归属表**：每份涉及的 spec、去处（加到已有 / 新建 / 只记变更）、对应场景编号。新建 spec 时附上边界表的新行。
2. **spec 增量原文**：新增场景的全文；修改场景给出改前和改后；删除给出移除记录。
3. **改法和验证**：1–3 句话说明准备怎么改、怎么验证。

用户确认后进入第 3 节，之后连续执行。用户提出修改就改 spec，再展示一次。用户没有答复之前，场景状态保持"待实现"，不开始写代码。确认记录写进 task ①的"spec 归属与确认"。

开发中发现需要改变已确认的场景时，把这一处改动单独再展示一次，确认后按 [需求变化同步](../x-tech-design/references/change-sync.md) 更新②③（用了外部 tech-design 时更新其中的 D 和 T）和已有证据。完成验证后同步当前行为和交付状态；验证失败、待澄清或证据缺失时保留实际状态。

## 3. 按需技术设计，建 task，写用例变化

完整读取 [任务模板](templates/task.md)，保持五段：**①需求与变更、②精简技术设计、③测试用例与变化、④技术实现、⑤验证结果**。篇幅按本次差异填写，删除占位符和空示例。

### 先决定技术设计写在哪

先读相关代码，列出计划改动的源码文件，再按下表选。源码文件指会被构建或运行的文件，配置文件也算；测试文件和文档不算。满足任一条就用 x-tech-design：

| 条件 | 技术设计写在哪 |
|---|---|
| 第 1 节新建了 spec（第一次建 `engineering` 最小 spec 不算） | 调 [x-tech-design](../x-tech-design/SKILL.md)，在 spec 同目录写 `tech-design.md`；task 的②只写路径回指 |
| 场景落在 2 份及以上 spec | 同上，写在主场景所在 spec 的同目录 |
| 计划改动的源码文件超过 3 个 | 同上 |
| 以上都不满足 | 在 task 的②写几行局部方案，不另建文件 |

qdev 里调 x-tech-design 不单独停下来等确认，设计结论随交付一起告知用户。写设计或实现时发现 [风险规则](references/risk-rules.md) 有一条答"是"，立刻停下并交接。

### ② 精简技术设计

走 x-tech-design 时，②只写设计文件路径、本轮引用的 D 和用例编号。在②里写局部方案时，先读相关代码、已有设计、项目规范、[共用开发规范](../x-tech-design/references/development-rules.md) 以及所属 spec 和 `engineering` spec 的关键约束（含“架构：”开头的架构约束；约束只限制怎么做，要做的是本轮场景；方案和约束冲突或实现做不到就停下问用户），再说明：

- 沿用的设计路径/条目及本次适用理由；局部补充方案、主要入口与调用/数据流程。
- 计划涉及文件、适用规范及落实/检查方式；共用依据可以合并引用。
- 方案对应的场景、移除要求或约束；需要编号时使用局部 D 编号，已有编号沿用。

已有权威设计以路径/ID 回指，局部补充方案在②维护，以本轮任务授权、既有设计和项目规范为依据。涉及既有关键决策变化时核对原始任务的授权范围，超出授权的决策先澄清；[风险规则](references/risk-rules.md) 有一条答"是"时交回主线。需求、设计和用例预期在实现前保留可读基线；版本记录或内容哈希须能定位相应内容。

### ③ 测试用例与变化

从用户明确要求及已有结论确定本次承接范围，结合相关边界和既有不变量建立应覆盖集合，再列用例：

- 标出每项用例属于**新增、修改、删除或沿用回归**，记录代码位置/命令及变化依据；分别统计用例变化和需求覆盖。
- 已有设计用例主定义时回指路径/ID；局部用例在③定义前提、触发、预期结果及禁止结果，用稳定 T 编号定位。
- 删除功能时记录旧正向用例的退役依据，补充移除结果验证和保留功能回归；退役用例单列处置状态。
- 按风险选择 unit、smoke、e2e 或人工检查，覆盖本次行为、相关异常和不变量；普通小改动复用项目现有测试方式。

模块说明通过“路径＋稳定章节”回指；已有 feat/scene、C、D、用例 ID 沿用原定位。用例怎么随需求变化新增、修改或退役，按 [需求变化同步](../x-tech-design/references/change-sync.md) 判断。

## 4. 执行并留证据

测试规则和 x-dev 一样，见 [x-dev「测试是硬规则」](../x-dev/SKILL.md#测试是硬规则)：项目全量测试全绿、改动行覆盖率 100%、新写的测试通过真实性检查，三条都满足才算做完；测试要调用项目里真实的代码，不许在测试里重写一遍业务流程。

下文的 `xdev` 指 `python3 <x-dev skill 目录>/scripts/xdev.py`，目标是本 task 的 `.md` 文件。证据目录是同目录的 `<task>-evidence/`，做法见 [证据约定](../x-dev/references/test-reporting.md)。

1. 开工先运行 `xdev start <task.md>`：把当前 git HEAD 记为「代码基线」，之后覆盖率都和它比。
2. 自动化的新行为先写/调整测试，确认失败是因为目标行为还没有（有效红灯）；环境、导入和测试本身的错误不算。已有满足或只能人工验证时，写清理由、步骤和实际看到的结果，存进证据目录。
3. 按②实现，在④记录实际改动的文件及和计划的差异。不 mock 掉被验证的机制；验收标准变了要追溯到功能/设计主定义。
4. 在⑤的「用例对应」表登记③里每个没删除的用例：`用例 | 测试位置 | 层级 | 结果`，测试位置写到函数。
5. 运行 `xdev coverage <task.md> --cmd "<全量测试命令>" --report <覆盖率报告>`。它真的跑测试，算出本次改动的代码行被测试跑到的比例，写进⑤。不到 100% 就按它列的 `文件:行` 补测试，再跑，直到 100%。
6. 涉及 Web 的任务，agent 亲自在浏览器操作实际功能，有问题修复复验，通过后截图；其他界面改动打开最终版本截图。截图和浏览器记录放证据目录，按 [证据约定](../x-dev/references/test-reporting.md#web-与界面验收) 登记。代码因此改了就重跑第 5 步。

## 5. 核对文档并验收

先自检：功能归属可定位；新增/修改/删除已回写 spec 正文；changelog 与 task 双向链接有效；①的修改前定位能找到旧内容；计划和实际改动范围对应。

然后：

1. 按 [测试真实性检查](../x-dev/references/test-integrity.md) 派一个轻量子 agent 检查本次新增和改动的测试，回执存为证据目录里的 `test-integrity.md`，下一步的 `xdev check` 会读它（没有新增或改动的测试时跳过这一步）。不通过就修测试，重跑第 4 节第 5 步，再检查，最多 3 轮。
2. 运行 `xdev check <task.md>`：核对①填了 spec 确认记录、③的用例都对应到真实测试且通过、测试命令通过、改动行覆盖率 100% 且之后代码没再改、真实性检查通过且之后测试没再改。不通过就按它列的问题修，修完从第 4 节第 5 步重来。
   脚本只查确认记录有没有填，接着按 [x-verify-spec](../x-verify-spec/SKILL.md)「做法」第 3 步做人工检查：改了场景却只写“已确认”或开发者自检 → 核对未完成；改了场景却写“未写场景，无需确认” → 核对不通过。
3. 本轮写了场景的，交 [x-qa-gate](../x-qa-gate/SKILL.md) 按 Q1 做一次独立审查（需求对齐、测试是否证明了场景、设计与架构约束）；只记变更、没写场景的，`xdev check` 通过即可。审查发现的问题写进⑤「问题与处置」，交 x-fix 修，修完重跑 `xdev coverage` 和 `xdev check`。

缺输入、待澄清、失败或未验证时如实列项，保留已通过的部分。

## 6. 用大白话交付

每次任务的最终回复必须用大白话说明以下内容，让用户直接看懂这次改了什么：

- **功能与 feat**。说明做了什么、用户能看到或使用什么变化。逐项列出涉及的 feat 编号和名称，标明新增、修改或删除。由模块说明承载的功能引用实际章节。
- **涉及的脚本和文件**。列出本次实际改动的脚本及其他相关文件，简述每个文件改了什么。
- **关键函数**。列出本次改动中承担主要逻辑的函数或方法及其文件位置，用一两句解释每个函数里面做了什么、产生什么结果。仅改文档或配置等、没有函数改动时，直接说明这一点。
- **验收截图**。Web 任务和其他程序界面改动必须在最终回复附上第 4 节采集的截图，说明每张图展示了什么。回复载体无法直接显示图片时，提供可打开的截图链接。

同时给出验证结论和 task 链接。

交付条件：功能文档及变更索引已同步，`xdev check` 通过（测试通过、改动行覆盖率 100%），写了场景的已过独立审查，Web 任务的浏览器验收通过，适用的截图已随回复交付。浏览器验收未通过或截图缺失时说明原因和待补事项，交付状态记为未完成。

```text
✅ x-qdev 完成 · <任务> · 功能文档已同步 · 用例 N 个全部通过 · 改动行覆盖率 100%（K 行）· xdev check 通过 · 独立审查通过（或未写场景，不需要）
```

存在未决项时输出“x-qdev 未完成”，列已完成内容、失败/阻塞/待补项及下一步。旧 task 沿原章节和编号核对已有记录，本轮缺少的设计、来源或证据按实际缺口补齐。
