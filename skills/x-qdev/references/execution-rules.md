# x-qdev 执行规则

## 状态规范

| 符号 | 状态 | 说明 |
|------|------|------|
| ⏳ | 未开始 | 等待处理 |
| ▶️ | 进行中 | 正在实现 |
| 🟡 | 待验证 | 实现完成，等待真实验证 |
| 🔴 | 验证失败 | 证据显示存在问题，等待修复 |
| 🟢 | 证据通过 | 当前验证通过，等待风险路线收尾 |
| ✅ | 已完成 | DoD 证据闭环，所需审查路线已通过 |
| ↗️ | 已升级 | qdev 停止，完整流程 task 接管完成状态 |

状态流转：

```text
⏳ → ▶️ → 🟡 → 🟢 → ✅
             ↓
             🔴 → 修复 → 🟡
⏳/▶️/🟡/🟢 → ↗️ 已升级
```

✅ 是 Q0/Q1/Q2 的终态；↗️ 是 Q3 的终态，最终 ✅ 由新的 `-full` 任务拥有。

## 完成条件

进入 ✅ 需要同时满足：

1. 代码或文档实现完成。
2. README 中每条 DoD 都有最终证据（非 agent 自述）。
3. `dev-report.md` 记录实际 diff 和真实验证结果。
4. 五项规范覆盖与风险等级一致：
   - Q0：规范 1、5 完成；规范 2、3 允许简化。
   - Q1：规范 1-5 完成（规范 2、3 可极简）。
   - Q2：规范 1-5 全部完整，且综合 reviewer pass。
5. 当前任务没有阻塞项。

Q3 使用 ↗️ 终态。原 qdev task 保存交接证据，新 full task 负责最终 ✅。

## 更新时机

- 开始实现时更新为 ▶️。
- 实现完成时更新为 🟡。
- 验证失败时更新为 🔴，并记录失败证据。
- 验证通过时更新为 🟢，并填写 DoD 证据矩阵。
- 风险路线收尾完成时更新为 ✅。
- Q3 交接路径建立后更新为 ↗️。

普通状态切换直接更新 README 清单状态列，避免形成流水账；验证失败、关键决策和 reviewer 结论写入 dev-report。

## 风险变化

- **Q0 → Q1+**：出现用户可见行为变化时重判。
- **影响 DoD / 公开行为 / 数据语义的歧义**：开发前交用户确认，不自行假设。
- **Q1 → Q2**：出现已明示的低影响实现假设、修改核心函数、覆盖关系不清或多个重要失败路径时重判。
- **→ Q3**：出现鉴权、不可逆数据、迁移、公开 API/事件协议/schema、并发/缓存/状态机、跨模块架构或缺少可靠验证方式时升级。
- 每次风险等级变化都更新 README 风险判断章节和 dev-report。

## 模型分流指引

五项规范的产出是模型无关的 IR。不同能力模型在「生成 IR」和「消费 IR」上分工，但 IR 本身固定。

### 强模型（高能力）

承担 IR 生成——判断密集、低频、高杠杆的工作：

- 一次性生成规范 1 目标与边界、规范 2 现状理解、规范 3 不变量、规范 4 实现路径、规范 5 关键测试。
- 颗粒度选择：给强模型的规范 4 清单颗粒度可以粗（整特性级），让它自己分解 T；细颗粒度清单反而会把强模型降级成执行器。
- orientation 自取：强模型能自己探索上下文提取相关代码和隐藏不变量，给它入口比给它投喂更能发挥。

### 弱模型（低能力）

承担 IR 消费——高频、机械、有明确判定的工作：

- 按已生成的规范 4 清单逐项实现，每项绑定的测试先红后绿。
- 颗粒度要求：给弱模型的规范 4 清单必须细（单函数/单文件级），每项输入输出明确，它服从清单。
- orientation 死穴：弱模型读不懂大上下文，无法自行从代码库提取相关代码和隐藏不变量。如果上游没有把规范 2 现状理解预处理成 IR 喂给它，它必然在这里翻车。这是弱模型最需要工具或强模型辅助的规范。

### 单模型退化模式

单模型全程自己走时，五项规范顺序强制：

1. 规范 2 现状理解**必须先于**规范 4 动手。没读懂 S 就写 T，规范 3 不变量保证落空——这是塌方最常见点。
2. 规范 3 不变量在动手前锁定，否则会在写完后才"发现"自己破坏了什么。
3. 规范 4 清单由规范 5 测试反向定义颗粒度：能否写出 N 个独立的、会失败的测试？能 → 清单就是这 N 个测试的执行顺序。

### 信任锚

无论哪种模型，规范 1 目标与边界、规范 3 不变量、规范 5 测试三项是信任锚——它们让流程可以信任输出，信任来自客观验证而非模型能力。弱模型的下限由这三项兜住；强模型的上限由规范 2、4 两项释放。

## orientation 执行方法

规范 2 现状理解按以下顺序展开，只读不写：

```text
主模块入口
→ 契约邻居（调用方与被调用方）
→ 状态与权限所有者
→ 入口适配层
→ 副作用与下游消费者
→ 证据与测试
```

每一层记录：

- 可信输入与非可信输入。
- guard、状态写入、副作用。
- 失败返回和资源生命周期。
- 本次变更会经过的入口、guard、状态写入和副作用路径。

orientation 的产物写入 README `## 现状理解`，并提取出 `## 不变量` 需要的规则。不动手写代码是这一规范的硬约束。

## README 与 dev-report 记录范围

README 记录任务开始、五项规范产出、风险变化和流程升级；dev-report 记录验证失败、关键决策、实际 diff 和 reviewer 结论。普通状态切换只更新 README 清单状态列，避免流水账。
