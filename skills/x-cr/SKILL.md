# x-cr · 查代码对不对

手动触发的正确性调查。两种用法走同一条路：

- **查已知问题**：用户给了现象（“刷新 token 后还是失败”），要找到原因。
- **检查代码**：用户让看一个模块、文件、diff 或 PR，主动找真会出错的地方。

## 和别的 skill 的分工

| 发现的是 | 归谁 |
|---|---|
| 能走到的错误：结果错、状态错、数据错、越权、隔离被突破、公开接口行为变了 | x-cr |
| 结构、分层、重复、死代码、文档过期、性能，现在还走不到错误结果 | x-code-audit |
| 命名、格式、风格 | x-code-audit 的 L1（交给 lint） |
| 每个任务开发后的验收 | x-verify-spec |

## 流程

```text
1 定范围 → 2 找判尺 → 3 逐条造反例 → 4 查原因（只在原因不明时）→ 5 写报告 → 6 自检
```

### 1. 定范围

- 用户给了文件、目录、模块、diff、PR 或现象，就查这些，并顺着调用关系看到维持规则所需的上下游。
- 用户只说“x-cr / review / 检查一下”，查当前 git diff。
- diff 是空的，用户也没给范围，问用户要查什么。

### 2. 找判尺

判尺就是“这段代码必须做到什么”。按这个顺序找，用原来的编号，不另起编号：

1. **有 spec**：常规 task 从 `dev-checklist.md` 的 `> spec:` 找到 spec，qdev task 从 task 文件头的 `> 所属 spec：` 找。读本轮相关 feat 的**场景**（GIVEN/WHEN/THEN）、**关键约束 C**，再读同目录 `tech-design.md` 的 **D 规则**。编号写成 `<spec 名>:C2`、`<spec 名>:feat03-场景2`、`<spec 名>:D04`。
2. **没有 spec**：用接口文档、协议或 schema、调用方的用法、已有测试（尤其是负向测试）。编号写 `新1`、`新2`，来源写清文件位置。
3. **spec 没写但代码里明显该守的规则**（比如服务端不能信客户端传的 role）：也记下来，编号 `新N`，来源写“spec 没写”加代码证据。报告里提醒用户补进 spec，不自己改 spec。

去哪里找 spec 没写的规则，看 [references/invariant-review.md](references/invariant-review.md)。

spec 和用户现在说的不一样时，这条规则的结论写“来源不一”，列出两边原文，等用户定。

### 3. 逐条造反例

对每条规则：

1. 想一个最小的反例：最少的前置状态、一个动作、一个能看出规则被打破的结果（GIVEN / WHEN / THEN）。
2. 顺着代码路径走一遍：入口 → 校验 → 改状态 → 副作用（写库、发消息、执行命令）。能跑就真跑测试或命令。
3. 给结论：

| 结论 | 含义 |
|---|---|
| 守住了 | 反例被正确拒绝或处理，有代码或测试证据 |
| 被打破 | 有一条能走到的路径让规则失效 |
| 没法验证 | 缺关键代码、日志、运行环境 |
| 没走到 | 这次范围不经过这条规则（写依据） |
| 来源不一 | 两处来源说法不同，不知道该按哪个判 |

“被打破”“没法验证”“来源不一”都要开一个问题（B1、B2…）。后两种一般是 P2，问题里写清补什么证据、问谁确认。

### 4. 查原因（只在已知 bug、原因不明时）

规则被打破了、但不知道为什么，或者用户给的现象还对不上代码时，列 2–4 个可能原因，逐个找证据，排除或坐实。做法见 [references/bayesian-review.md](references/bayesian-review.md)。原因一眼就清楚的不做这一步。

### 5. 写报告

按 [references/report-template.md](references/report-template.md) 写一份报告：

- 在常规 task 里：`docs/spec/<spec>/tasks/<task>/reports/cr/cr-YYYYMMDD-HHmmss.md`
- 在 qdev task 里：`docs/spec/<spec>/tasks/task-<name>-evidence/cr/cr-YYYYMMDD-HHmmss.md`
- 其他：仓库根目录 `reports/cr/cr-YYYYMMDD-HHmmss.md`

每个问题写：严重度、位置（文件 + 函数 + 行）、反例、证据、影响、怎么改。位置要让人能直接打开找到，比如 `src/loan/renew.py` 的 `renew()`，第 12–14 行。

严重度只看影响：

| 等级 | 影响 |
|---|---|
| P0 | 越权或隔离被突破、数据损坏或丢失、核心功能用不了、失败被报成成功且产生了副作用 |
| P1 | 能走到的用户可见错误，影响可恢复或范围有限（边界输入出错、错误被吞掉、公开接口行为回归） |
| P2 | 现在走不到错误，但缺证据或缺规则：spec 没写、测试测不出错、来源不一、没法验证 |

### 6. 自检

```bash
python3 skills/x-cr/scripts/validate_report.py <报告路径>
```

不通过就改报告结构，再交付。

## 交付

- 用户只要调查：给报告路径、P0/P1/P2 各几条、最严重的一条是什么。
- 用户要修：交 x-fix，传报告完整路径。
- 有“新N”规则时，列出来提醒用户哪些该补进 spec。

## 不做的事

- 不报风格、命名、排版和纯抽象偏好。
- 测试通过只说明被测到的路径没问题；判“守住了”前确认测试真能抓住错误实现。
- 不改代码、不改 spec，只出报告。
