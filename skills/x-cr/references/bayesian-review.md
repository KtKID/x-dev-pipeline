# 原因不明时怎么排查

只在“查已知问题”、而且原因一开始对不上代码时用。原因一眼就清楚的不用。

## 做法

1. 把用户看到的现象当第一条证据，写清期望和实际。
2. 列 2–4 个可能原因，每个写一句“如果是它，应该还能看到什么”。从这些方向想：
   - 实现和 spec 写的不一样，或者漏做、做偏、改坏了
   - 边界输入：空值、超长、非法类型、特殊字符、路径穿越
   - 信了客户端传来的身份、角色、租户
   - 状态：没初始化、只初始化一半、终态被复用、请求之间串了
   - 依赖：超时、空响应、数据格式变了、部分失败
   - 并发：重复提交、重试、乱序、缓存过期
   - 配置、环境或数据本身有问题
   - 测试没抓住错误实现
3. 挑最省事的证据先看：读代码、跑测试、看日志、查配置默认值、看调用方有没有兜底。
4. 每看一条证据，就更新每个原因：更可能、更不可能、或没影响。被证据推翻的标“排除”。
5. 最可能的那个，再反过来找一次能推翻它的证据（调用方保护、服务端校验、已有测试、默认值）。推不翻才写“成立”。

结果写进报告的「原因排查」表：每个可能原因、看了什么证据、结论（成立 / 排除 / 还不确定）。还不确定的，问题里写清补什么证据能定下来。
