# 找 spec 没写的规则

spec 的场景、C 约束和 D 规则先查完，再用这份清单找 spec 没写、但代码明显该守的规则。找到的编号 `新1`、`新2`，来源写“spec 没写”加代码证据，报告结论里提醒用户补进 spec。

## 先看清楚这几件事

顺着这次范围的代码，从入口看到副作用，每一处问一句：

| 看什么 | 问什么 |
|---|---|
| 输入 | 哪些来自客户端、外部服务、文件或环境，不能直接信 |
| 校验 | 谁负责登录、权限、格式校验、状态检查 |
| 状态 | 谁拥有这份状态，哪些变化允许，失败后是什么状态 |
| 副作用 | 写库、执行命令、发消息、写缓存发生在哪里，是否在校验之后 |
| 出错 | 超时、取消、重试、部分失败、并发时怎么收场 |

## 常见的漏写规则

- **权限只能收窄**：批准的范围在解析、通配、前缀匹配、缓存、持久化之后不能变大。例：只批准了 `git status`，记住的规则却放行了 `git push`。
- **服务端不信客户端**：身份、角色、租户、资源归属由服务端从可信状态推出来，客户端传的同名字段改变不了访问主体。
- **隔离**：用户、租户、会话、线程、工作目录之间互不串。例：缓存键少了租户这一维。
- **失败不留半截**：被拒绝时状态不变；真正提交后才返回成功；部分失败能恢复。
- **重试不重复**：同一个请求重试，副作用只发生一次；并发更新守版本或锁；取消后的迟到结果不改终态。
- **公开接口不悄悄变**：调用方依赖的输入、输出、错误码、退出码、字段、默认值保持原意。
- **资源收得回来**：连接、锁、文件句柄、临时目录、后台任务在成功、失败、取消、超时时都释放。

## 把规则写成能判对错的话

- 弱：“权限处理要安全。”
- 能判：“用户批准命令 C 后，记住的规则放行的命令只能是 C 范围内的。”
- 弱：“服务端校验用户。”
- 能判：“服务端从登录会话取 user_id 和 tenant_id；请求里传的同名字段改变不了查谁的数据。”

## 反例示例

```text
新1：一次批准放行的命令只能在用户批准的范围内
GIVEN 用户只批准了 `git status`
WHEN 记住的审批规则被拿去匹配 `git push`
THEN 必须拒绝；放行就说明规则被打破
路径：解析命令 → 规范化 → 匹配审批 → 保存规则 → 执行
```
