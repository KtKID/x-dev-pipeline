# 模块不变量检查法

本文件定义 x-cr 如何先读取 spec 不变量，再寻找设计阶段可能遗漏的规则。目标是把“感觉这次修改有风险”转成可判定的规则、最小反例和执行路径。

## 1. 先读取 spec

task 的 `dev-checklist.md` 使用 `> spec:` 指向归属 spec。优先读取：

1. `影响边界与不变量`：提取本次目标、上游、下游和相关模块的不变量。
2. `判断依据`：保留 J-ID、来源和确认状态。
3. `建模覆盖声明`：确认数据流、状态、时序、资源、不变量和故障的已有覆盖。
4. task 引用的 Scenarios：取得可观察结果和已设计反例。

每条相关 spec 规则使用 `INV-SPEC-NN` 登记。保持原文语义和依据，避免用代码现状改写 spec。

## 2. 建立模块正确性模型

按顺序展开调查范围：

```text
主模块
→ 契约邻居
→ 状态与权限所有者
→ 入口适配层
→ 副作用与下游消费者
→ 证据与测试
```

对每一层记录：

| 项 | 问题 |
|----|------|
| 输入 | 哪些输入可信，哪些来自客户端、外部服务、文件或环境 |
| guard | 谁负责认证、授权、schema 校验、状态检查和范围收窄 |
| 状态 | 谁拥有状态，哪些转换允许，终态和失败态如何处理 |
| 副作用 | 数据写入、命令执行、消息发送、缓存和持久化发生在哪里 |
| 故障 | 超时、取消、重试、部分失败和并发交错如何收口 |
| 证据 | 哪些测试、日志和调用方能证明真实路径 |

模块模型用于找到 spec 表格与真实执行路径之间的空白。

## 3. 寻找遗漏候选不变量

遗漏检查使用上位原则加实例，实例保持开放集合。

### 权限与能力范围

授权后的能力集合保持在明确批准范围内。解析、规范化、通配、前缀匹配、缓存和持久化都保持范围单调收窄。

常见实例：命令审批、API scope、文件路径权限、工具 allowlist、租户角色。

### 服务端信任边界

身份、角色、租户、资源所有权和权限结果由服务端可信状态推导或校验。客户端字段作为声明进入验证，授权完成后才发生副作用。

常见实例：登录、刷新 token、管理接口、回调参数、资源 owner 字段。

### 隔离

用户、租户、会话、线程、workspace、cwd、设备和请求之间保持明确边界。

常见实例：跨租户查询、跨线程状态污染、审批规则跨 cwd 复用、缓存键缺少租户维度。

### 状态与持久化

拒绝路径保持状态不变；成功只在要求的提交点之后返回；部分失败保持可恢复且证据可追踪。

常见实例：数据库事务、事件日志、文件 replace/fsync、队列确认、迁移和删除。

### 幂等、并发与时序

重试保持副作用唯一；并发更新遵守版本和锁规则；取消、终态和乱序完成保持状态机约束。

常见实例：request_id、乐观锁、重复提交、回调乱序、取消后的迟到结果。

### 公开契约与兼容

调用方依赖的输入、输出、错误、退出码、字段和副作用保持已声明语义。

常见实例：API response、CLI JSON、事件 schema、配置默认值和协议版本。

### 资源与故障收口

资源在成功、失败、取消和超时路径中遵守生命周期；依赖失败传播为可判定结果。

常见实例：连接、锁、文件句柄、临时目录、后台任务和流式响应。

候选规则使用 `INV-CAND-NN`，随后判断：

| 关系 | 处理 |
|------|------|
| 已被 spec 覆盖 | 合并到对应 `INV-SPEC-NN` |
| spec 缺口 | 保留仓库证据并进入 P2 或关联的正确性问题 |
| 待确认 | 写出不同答案对实现与验收的影响 |
| 来源冲突 | 列出冲突来源和最短确认路径 |

## 4. 把规则写成可判定陈述

推荐句式：

```text
对所有允许到达模块的输入与状态，
当执行动作 A 时，
规则 P 在修改前后持续成立，
并可通过结果 R 观察。
```

弱规则：“权限处理要安全。”

可判定规则：“用户批准命令 C 后，持久化审批规则允许的命令集合保持为 C 明确范围的子集。”

弱规则：“服务端校验用户。”

可判定规则：“服务端从已认证会话推导 user_id 和 tenant_id；客户端同名字段无法改变数据访问主体。”

## 5. 为每条受影响规则构造最小反例

最小反例包含：

1. 最小初始状态。
2. 一个触发动作。
3. 一个足以证明规则失效的可观察结果。
4. 对应入口、guard、状态所有者和副作用路径。

### 审批范围示例

```text
INV-AUTHZ-01
规则：一次批准产生的可执行命令集合保持为用户明确批准范围的子集。
GIVEN：用户只批准 `git status`。
WHEN：审批结果被用于执行 `git push`。
THEN：执行必须被拒绝；放行即可证明不变量破坏。
路径：解析 → 规范化 → 审批匹配 → remember rule → dispatch。
```

### 服务端信任示例

```text
INV-TRUST-01
规则：服务端从可信会话和服务端数据推导或校验身份、角色、租户和所有权。
GIVEN：合法 token 与被篡改的 role/tenant_id/owner_id。
WHEN：请求读取或修改资源。
THEN：伪造字段被拒绝或忽略，且没有越权副作用。
路径：request schema → authentication → authorization → data filter → write/response。
```

## 6. 与贝叶斯审查衔接

不变量说明“哪条规则可能失效”，候选根因 H 说明“为什么失效”。

审批范围被扩大时可建立：

- H1：命令规范化丢失子命令。
- H2：remember rule 持久化成根命令。
- H3：matcher 使用过宽前缀。
- H4：dispatch 绕过审批结果。

分别读取代码、测试、日志和调用链作为证据 E，更新各 H 的置信度。

## 7. 覆盖完成条件

模块 review 完成时满足：

- spec 中相关不变量全部进入覆盖表。
- 每个受影响不变量都有最小反例和执行路径。
- 每个补充候选都有 spec 关系。
- 每个结论都有保持、破坏、未验证、来源冲突或未触达状态。
- 破坏项映射到稳定 Bn；未验证和来源冲突项给出最短补证路径。
