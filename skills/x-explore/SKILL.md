# x-explore

围绕用户当次目标，把模糊意图探索到足以确定本次范围、验证证据和完成条件。遵循剃刀法则：如无必要，勿增实体。用户要求 MVP 验证时，聚焦待验证假设、最小功能和可信证据；局部改动与正式交付按各自目标确定深度。

## 五条姿态

这是姿态，不是流程——没有固定步骤、顺序、必须产出。不是任务清单式的探索。

1. **姿态，不是流程**。不设阶段、不设必经问题序列、不强求产出。探索本身是开放的，按用户共鸣的方向流动。

2. **一起澄清本次目标**。基于用户原话和现有证据讨论，只澄清会影响本次结果、范围或验证结论的不确定点。已有明确结论直接采用。

3. **讨论深度随目标收敛**。用户主动要求发散或比较方向时提供相关选择；执行目标已明确时围绕最小必要范围收敛，取得足以开展本次工作的结论即结束探索。

4. **扎根真实代码库**。探索时要落到实际：读文件、搜代码、调研架构、看现有产物（docs/spec/、openspec/、dev-pipeline/tasks/）。不要只在抽象层面空谈——空谈产不出可建模的结论。

5. **不自动落盘——提议保存，由用户决定**。结论成型时，提议写到 proposal/spec/design 对应位置，等用户确认。绝不自动创建或修改产物文件。

## 何时结束 / 何时转交

转交 x-spec 的判据（同时成立才算探索完成）：

- 用户要改变的系统结果说得清，不再是模糊方向
- 关键约束和不可破坏的不变量识别出来了
- 系统边界（做什么、不做什么）有共识
- 真正的不确定点被显式列出来（不是被绕过去）
- 本次需要的验证证据与完成条件明确；MVP 的结论限定在约定环境和数据范围

以上判据均以本次目标为边界；已有明确结论可直接转交 x-spec。仍有实际缺口时只澄清影响本次工作的部分，其他不确定性保留为本次验证的局限。x-spec 使用统一格式记录结论，按每份最多 3 个 feat、场景总数最多 10 个的容量拆分。
