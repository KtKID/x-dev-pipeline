## 问题详情

### B1: 关键意图的来源

目标章节能写清目标、适用范围、验证证据与完成条件。场景必要性可提供部分间接追溯。用户明确排除或暂缓的范围，以及为何采用某种验收证据，缺少对应的留痕要求。跨会话时，下游可能只能读到概括后的范围。[目标梳理](../../skills/x-spec/SKILL.md#1-按本次目标梳理需求) · [产物模板](../../skills/x-spec/templates/spec.md#本次目标与完成条件)

最短补证是给目标与范围添加可定位的用户依据，并在确有明确范围边界时保留该边界。

### B2: 产品裁决及确认基线

关键约束有稳定 C 编号、来源及场景回指。普通产品取舍，例如导出当前页还是全部筛选结果，可以写回 GWT；用户确认的消息、裁决的适用范围、被替代的旧结论和对应文档版本则缺少固定位置。模板要求移除已解决待确认项，指令另行要求记录实际确认，完整示例只展示裁决前的功能正文。设计入口要求核对当前文档与实际确认覆盖范围。[确认之后](../../skills/x-spec/SKILL.md#确认之后) · [产物模板](../../skills/x-spec/templates/spec.md) · [技术设计输入](../../skills/x-tech-design/SKILL.md#输入与产物)

最短补证是在 spec 中留一条可定位的确认记录，包含用户结论、消息来源、受影响的场景或范围和可读的内容版本。部分确认与行为变更按受影响范围分别处理。

### B3: 当前 feat 格式的校验边界

在两个临时目录中分别写入 skill 自带的 CSV 示例，以及同一示例加一条“导出当前页或全部筛选结果，等待用户决定”的待确认项。对两份输入分别运行 `python3 skills/x-dev/scripts/xdev.py validate <临时目录> --json`，两次均识别为 `capability`、报告 0 个问题并退出 0。旧版 `判断依据` 就绪检查由专用 spec 类型触发。技术设计仍有独立的确认依据检查。[校验分派](../../skills/x-spec/scripts/validator.py) · [旧版 spec 校验](../../skills/x-spec/scripts/spec.py) · [设计入口核对](../../skills/x-tech-design/SKILL.md#1-核对输入与功能边界)

最短补证是在设计交接前使用实际用户确认记录核对状态、范围与版本。将通用校验回执作为结构检查证据。
