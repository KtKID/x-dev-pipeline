# StackChan 设备双工传输边界更新评估

## 结论

候选修改属于**原地细化**，应在现有 x-spec2 包中更新。需求本质、系统目标和系统不变量全部保持稳定，变化集中在设备侧传输能力的实现归属与模块边界。

新证据已逐项覆盖 `D3` 重评条件中的能力清单：音频帧序号、累计确认、背压、控制消息优先级和断线续传。`D3` 的完整重评条件还包含“达到本包验收”；当前证据只确认 SDK 原生能力，验收达标仍需契约测试、网关集成测试、目标板 HIL 与故障注入结果。因此当前状态是：**重评已触发，合并方向成立，正式删除独立模块需等待验收证据闭合**。

验收证据闭合后，可把“设备双工传输”并入“交互会话协调器”，并在协调器内部保留一个 SDK 适配端口作为实现缝隙。该端口不作为独立 x-spec2 模块；`current_turn_id`、`cancel_epoch` 和轮次终态继续由协调器唯一拥有，连接窗口、确认游标和重连句柄由 SDK 适配端口封装。

## U/J/D 追溯

| 追溯项 | 包内含义 | 对边界判断的作用 |
|---|---|---|
| `U3` | 设备采集语音并发送到服务器 | 要求设备侧持续、可靠地承接上行音频 |
| `U5` | TTS 语音流式回传并由开发板播放 | 要求设备侧同时承接低延迟下行音频 |
| `U6` | 端到端低延迟 | 要求传输路径可独立度量并满足 P95 预算 |
| `U7` | 播放期间可打断，旧播放与旧音频永久失效 | 要求取消控制抢占音频数据，并按 turn/epoch 过滤迟到帧 |
| `U9` | 网络和服务波动下可恢复，覆盖重连、背压与部分失败 | 要求确认、窗口、续传、退避与有界资源形成完整恢复契约 |
| `J2` | 单条持久 TLS WebSocket 是暂定传输基线 | 为原独立传输模块提供连接与协议假设；SDK 接入后仍需确认底层协议和网关兼容性 |
| `J3` | 上行 16 kHz PCM、下行 24 kHz PCM、20 ms 帧是暂定音频基线 | 决定帧大小、带宽、窗口、缓存和背压压力，合并后仍是 SDK 验收输入 |
| `J6` | RTT≤100 ms、丢包率≤1% 是暂定参考网络 | 决定低延迟与恢复测试基线，合并后仍是 SDK 验收输入 |
| `D2` | 交互会话协调器独立拥有设备轮次状态与 cancel epoch | 合并后继续保护业务状态事实源，SDK 的连接状态只能作为输入事件 |
| `D3` | 设备双工传输独立承载帧、确认、背压、控制优先级和续传 | 本次重评的直接决策记录，其备选正是合并进交互会话协调器 |

新证据属于用户原话之外的平台事实。原包更新时应新增 `J8`，记录 SDK 原生能力、SDK 版本、可定位的 API/文档或探针证据、确认状态及验收状态；更新后的 `D3` 应引用 `J8`，同时保留 `U3/U5/U6/U7/U9` 与 `J2/J3/J6` 作为行为和验收依据。

## 原边界恢复

### 原选择

`D3` 选择“设备双工传输”作为独立模块，集中承载帧序号、累计确认、接收去重、发送窗口、控制优先级、背压、心跳、退避重连与续传游标。它通过 `DeviceStreamTransport` 对协调器暴露连接状态、确认游标、下行帧和恢复事件。

### 独立的理由

这组能力形成完整的网络可靠性策略，能够在 `J3` 的帧与带宽基线、`J6` 的参考网络下独立压测，并可在 `J2` 的协议基线变化时独立替换。业务协调器关注 wake、turn、epoch、取消终态与资源租约；传输模块关注 socket、窗口、重传、乱序、背压和 resume。原拆分使弱网状态与业务轮次状态分别拥有清晰的测试面和数据 owner。

该边界直接保护五类要求：`U3` 的可靠上行、`U5` 的流式下行、`U6` 的低延迟、`U7` 的取消优先与旧帧失效、`U9` 的有界恢复。

### 原备选与否决原因

原备选是把传输能力合并进“交互会话协调器”。原决策认为，应用自行实现网络重试、窗口和背压时，这些状态会与 turn/epoch 状态耦合，扩大协调器状态机，提升竞态、测试和协议替换成本，因此选择独立模块。

### 原重评条件

`D3` 的重评条件是：目标平台 SDK 原生提供帧序号、确认、背压、控制优先级和断线续传，并达到本包验收。该条件表达了原边界的核心依据：独立模块用于拥有可靠性机制；平台 SDK 成为这些机制的权威实现后，应用层独立模块可收缩为协调器内部适配端口。

## 新证据评估

| D3 重评项 | 新证据覆盖 | 仍需闭合的验收证据 |
|---|---|---|
| 帧序号 | SDK 原生提供 | stream 内单调、重复去重、有限乱序窗口、缺口显式失败 |
| 累计确认 | SDK 原生提供 | 游标只前进、EOU 等待连续确认、重连只重传未确认帧、ASR 不重复创建 |
| 背压 | SDK 原生提供 | 上下行队列和窗口有界、窗口归零行为、溢出错误与指标、固定内存预算 |
| 控制消息优先级 | SDK 原生提供 | `CancelTurn` 具有独立额度，先于新 turn 音频发送，barge-in 静音 P95≤200 ms，旧音频永久失效 |
| 断线续传 | SDK 原生提供 | 3 秒短断恢复、resume 游标对账、旧 epoch 拒收、播放断线后旧 TTS 不续播、退避上限与抖动 |
| 本包整体验收 | 当前证据未给出结果 | 参考网络下分段及端到端 P95、100 轮基线、30 分钟故障注入、资源回落与全链路可观测 |

建议用 SDK 契约测试固定上述五项语义，再运行设备—网关集成测试和目标板 HIL。证据闭合前，更新后的协调器模块状态使用“方案确认”；证据闭合后更新为“可进入 x-req”。

## 原地细化判定

- 需求本质保持为可打断、可观测、可恢复的双向流式语音闭环。
- 系统目标保持为同轮次关联、P95 延迟可复算、本地先静音与旧音频失效、波动下有界恢复。
- 系统不变量保持完整：唯一播放权与 I2S/DMA owner、关联标识、取消终态、stream 内序号单调、有界队列、取消先于新音频、失败后资源释放。
- 新证据改变“可靠性机制由哪个设备侧模块拥有”，属于仓库事实更新和边界细化。

因此继续更新现有 spec 包。新建 spec 包只适用于需求本质、系统目标或不变量发生变化的情形。

## 同步更新范围

### `spec.md`

1. 在“判断依据”新增 `J8`，记录 SDK 能力、版本、证据位置、验证状态和验收状态。
2. 复核 `J2/Q2`：SDK 若继续承载 TLS WebSocket，则补充映射证据；SDK 若采用其他持久双工协议，则更新传输基线与协议待确认项。
3. 保留 `J3`、`J6` 及现有 Requirement/Scenario 的行为语义，把它们作为 SDK-backed 路径的容量、延迟和弱网验收输入。
4. `音频采集与上行`、`流式合成与播放`、`可测量低延迟`、`播放期打断`、`端到端可观测`、`波动恢复与稳定运行` 的 Requirement 文本保持；验证实现来源和模块覆盖改为合并后的协调器。

### `modules.md` 的 J/D 与模块总览

1. 更新 `D3`：选择改为“SDK 传输能力作为交互会话协调器的内部适配端口”；依据增加 `J8`；备选改为恢复独立设备双工传输模块；选择理由写明 SDK 已拥有可靠性状态、应用侧重复 owner 会增加状态同步面；重评条件改为 SDK 缺少验收语义、缺少可观测/取消钩子、资源上限无法证明或协议替换需求出现时重新拆分。
2. 更新 `D2` 的边界说明：协调器继续唯一拥有 `current_turn_id`、`cancel_epoch`、业务终态和恢复决策；SDK 只拥有连接、窗口、确认与 resume 的内部状态。SDK 回调必须经过协调器的 turn/epoch 校验。
3. 从模块总览和模块详情移除独立“设备双工传输”项，把其 Requirement 回指并入“交互会话协调器”。
4. 合并后协调器的 Requirement 覆盖为：`唤醒进入监听`、`音频采集与上行`、`流式合成与播放`、`可测量低延迟`、`播放期打断`、`端到端可观测`、`波动恢复与稳定运行`。
5. 协调器职责增加 SDK 生命周期、能力握手、消息 envelope 映射、音频/控制发送、下行接收、背压通知与 resume 编排；排除范围继续保留音频驱动细节和服务端 ASR/TTS 逻辑。
6. 协调器依赖改为 `设备音频运行时`、目标平台 SDK 和 `服务端语音网关`；`服务端语音网关` 的设备侧对端依赖改为协调器暴露的协议契约；`端到端遥测` 的生产者列表移除独立传输模块并加入协调器内部 SDK 事件。
7. `InteractionSessionBoundary` 增加 `CapturedAudioFrame`、`Ack/WindowChanged`、`Connection/ResumeStateChanged`、`TtsAudioFrame`、`StreamEnd/Error` 等输入，以及 `OpenTurn`、`AudioFrame`、`EndOfUtterance`、`CancelTurn` 和 resume 操作等输出。内部保留窄接口 `PlatformDuplexPort`，用于隔离 SDK 类型与业务状态机。
8. 数据归属同步为：协调器拥有 session/turn/epoch/终态/恢复决策；SDK 端口拥有 connection handle、发送窗口、确认游标、接收重排状态、心跳和退避句柄；音频运行时继续拥有 I2S/DMA 与上下行音频缓冲。

### Requirement 覆盖与验证

1. Requirement ↔ 模块映射删除独立传输模块，六项原 `D3` Requirement 全部由合并后的协调器承接。
2. 现有 Scenario 的可观察结果保持稳定：有序上行、累计确认、去重、有界缓冲、流式下行、取消抢占、旧帧拒收、短断续传、服务失败收敛和 30 分钟稳定性测试继续作为边界验收。
3. 增加 SDK 适配层契约测试证据，逐项证明序号、确认、窗口、优先级和 resume 语义与包内消息契约一致；HIL 继续证明静音、播放和端到端延迟预算。

### `design.md` 动态模型

1. **数据流**：主链路第 2、6 步改为协调器通过内部 SDK 端口上送/接收帧；核心消息契约的设备侧生产者/消费者同步；消息字段、turn/epoch/stream 过滤和网关契约保持。
2. **状态流转**：设备轮次状态事实源继续是协调器；SDK 连接、背压、ack 和 resume 回调映射为状态机事件；`Recovering` 的进入、短断恢复和终态收敛规则继续由协调器决定。
3. **时序**：正常交互中的首帧直发、barge-in 中 `CancelTurn` 抢占和新 turn 音频排序改由协调器调用 SDK 优先通道；本地停 DMA 的前置顺序保持。
4. **资源**：`双工连接与发送窗口` 的设备侧 owner 改为“交互会话协调器内的 SDK 端口”；容量、控制独立额度、确认游标和释放证据继续显式列出，避免 SDK 内部无界缓存成为不可观测资源。
5. **动态不变量**：保留协调器的 turn/epoch 唯一 owner；增加“SDK 回调先经过当前 turn/epoch 校验”和“SDK 控制通道不受音频窗口阻塞”；保留旧音频永久失效与所有队列有界。
6. **故障与恢复**：上行短断、长断、下行溢出、barge-in、CancelAck 丢失和 TTS 断流路径的执行者改为协调器内 SDK 端口；检测、恢复结果、终态与可观测证据保持。
7. **遥测**：传输指标的 module 字段映射到协调器的 SDK 子组件，继续输出 ack 游标、窗口、重传、resume、优先队列延迟和资源高水位，保障轮次重建能力。

完成上述同步并取得本包验收证据后，`D3` 可正式落为合并决策，现有 x-spec2 包继续作为唯一需求与边界真源。
