# Grader Rubric: StackChan ESP32-S3 低延迟语音链路

> Grader-only：本文件及同目录文件不得传给 executor。executor 只接收 `evals/problems/stackchan-esp32s3-voice-link.md`。

## 基本信息

- Case ID: `stackchan-esp32s3-voice-link`
- 目标 skill: `x-spec2`
- 类型: 系统级需求建模与方案包生成
- 目的: 验证 `x-spec2` 能否把跨设备、网络和服务端的动态语音链路压缩为三个可追溯、可验收、可直接交给 `x-req` 的产物。

## 测试题目

请为下面需求创建一个系统级需求包，直接生成可交给 `x-req` 的方案文档，不进入 task 拆解，不写代码。将不确定项写成明确假设或待确认项。

设计一个基于 StackChan 的 ESP32-S3 开发板语音收发模块。用户通过唤醒词触发 listen；设备采集语音并发送到服务器；服务器完成 ASR 转文字，再根据文字生成 TTS 语音并流式发送回开发板播放。链路要求低延迟、用户可随时打断播放、全过程可观测、网络与服务波动下可恢复并稳定运行。

## 预期产物

输出目录只包含：

- `spec.md`: 原子需求、用户原话追溯、模块影响、验收标准、建模六元组适用性和落点。
- `modules.md`: 模块职责、边界、接口、依赖、关键决策、双向需求覆盖、状态词汇和所有权。
- `design.md`: 纯动态模型，覆盖数据流、状态、时序、资源、不变量和故障恢复，可引用 modules.md 中的 D。

不得创建 `task.md`、`tasks.md`、`README.md`、checklist 或实现代码。

## 必须保真的用户要求

1. 基于 StackChan 与 ESP32-S3 开发板。
2. 唤醒词触发 listen。
3. 设备采集语音并发送到服务器。
4. 服务器执行 ASR，将语音转换为文字。
5. 服务端根据文字生成 TTS 语音并流式回传，开发板播放。
6. 端到端低延迟；给出可测量预算，或把具体阈值列为待确认决策并定义测量口径。
7. 用户可在播放期间打断；打断后旧播放与旧音频不得恢复。
8. 全链路可观测；设备与服务端通过会话或关联标识串联日志、事件与指标。
9. 网络和服务波动下可恢复并稳定运行，覆盖超时、重试或重连、背压与部分失败。

## 六元组适用性预期

本题六个元组全部适用，每个元组都要给出理由、落点和可验证证据：

| 元组 | 本题建模重点 |
|---|---|
| 数据流 | 麦克风音频 → 设备缓冲/编码 → 上行 → ASR → 文本 → TTS → 下行音频 → 播放。 |
| 状态 | 至少覆盖 idle、listening、uploading/streaming、waiting、playing、interrupted、recovering 等生命周期及合法转换。 |
| 时序 | 唤醒、首包、ASR/TTS、首音播放、barge-in 取消与超时恢复的顺序和延迟预算。 |
| 资源 | 麦克风、扬声器、I2S/DMA、音频缓冲、网络连接和执行任务的所有权、容量与释放。 |
| 不变量 | 单一播放所有者、同一会话的取消传播、已取消或过期音频永不恢复播放。 |
| 故障 | 断网、服务超时、流中断、缓冲溢出、服务降级、重连/重试及可观测证据。 |

## U/J/D 基准映射

- `U1`–`U9`：九类必须保真的原子用户要求，均属于行为型 U，分别回指唯一 Requirement。
- `J1`：目标板全双工、AEC、RAM/PSRAM 能力待确认，供设备音频边界决策消费。
- `J2`：TLS WebSocket 是暂定传输基线，供传输模块决策消费。
- `J3`：PCM 格式与帧长是暂定默认，供传输模块决策消费。
- `J4`：ASR/TTS 的真实流式、取消与幂等能力待确认，供两个适配器决策消费。
- `J5`：单连接 owner 串行化轮次是 LLM 推断，供会话协调器与服务端网关决策消费。
- `J6`：参考网络条件是暂定默认，供传输模块和延迟验收消费。
- `J7`：元数据观测与音频/全文不落日志是暂定隐私默认，供遥测模块决策消费。
- `D1`–`D7`：分别解释设备音频运行时、交互会话协调器、设备双工传输、服务端语音网关、ASR 适配器、TTS 适配器、端到端遥测为何形成独立边界；D 的唯一真源位于 modules.md。
